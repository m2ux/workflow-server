# GitNexus Area Comprehension Conformance

A specimen of one form: one library run held to a positive case, a negative case and a third, so the measurement, the promised fallback and the promised recovery are evidenced side by side.

The run is `gitnexus::area-comprehension`, which names the graph holding an area, brings it current through a nested reference to the index refresh, finds the execution flows the area's concept ranks into, and then iterates twice — once over the symbols those flows run, reading each one's connections, and once over the flows themselves, reading each one's ordered trace. The positive case names `technique loader composition`, a concept the workflow-server graph's flows rank into, so the query lands processes and process symbols and both passes fill their lists. The negative case names `zzqx quiddity nonesuch`, a concept no flow ranks into, so the query report lands with no process and no process symbol — its definitions may still fill — and both passes run zero times, leaving the contexts and traces empty. That is the fallback the run promises for a concept outside the graph, and the report names it as such rather than as an area read and found unconnected.

The stale-graph case names `main greeting flow` over a checkout it prepares for the purpose. The activity opens by applying the shared [prepare-stale-fixture](/conformance/techniques/prepare-stale-fixture.md) operation, which stands a throwaway tree up under `/tmp` holding two source files that call across each other, builds its graph, and commits one further change so the graph trails the tree; the operation names the path and the graph, and the activity sets the address the run works under from that name. The nested refresh then reads the staleness flag true, rebuilds the graph from the tree, and reads again, so `index_stale` lands the rebuilt graph's verdict and the ranked flows, connections and traces are taken from the graph as rebuilt. That is the recovery the run promises for a stale index, and the report names the rebuild that preceded the answers rather than reading them as taken from a graph that was current from the start.

Preparing the subject is what keeps the case true on its hundredth walk. The rebuild the case evidences is itself what brings a graph current, so a repository chosen for being behind is behind once and current from then on, and every later walk reads the gate false while the case still claims a rebuild. The prepared checkout moves a commit past its graph each time the operation runs, so the gate reads true every walk and no repository anyone works in is touched.

The run's first output is the graph it resolved, and all three reference sites bind it under the one name `repo_name`, which is the address each case works under. The workflow holds the current graph's name as a standing value beside that address, and the stale-graph case takes its own from the preparation that built it. The report reads both, so its header names both graphs and every row names in its graph column the one that answered it, with the prepared checkout's path beside the stale-graph row's outcome.

What the walk evidences is the reference under three bindings: the same run resolves under `gitnexus::area-comprehension` three times, its steps — a nested run and two per-item passes among them — splice into each activity under that activity's prefix, and its six outputs land under the names the reference sites bind. The closing activity reports all three against the shared [case report](/conformance/resources/case-report.md) guide.
