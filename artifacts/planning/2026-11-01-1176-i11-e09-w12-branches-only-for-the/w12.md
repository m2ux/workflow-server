**Component:** workspace:skills/work-planner/scripts/deliver.py

## Overview

A unit of an epic with several bases is given a task branch and worktree only for the bases whose long-lived branch its rows change. Each row's work item names that branch in its Component declaration, and the delivery survey reads it, so a session is planned against the bases it changes and no others.

## Problem

The delivery survey (`deliver.py`, `survey` and `task_branches`) gives every unit a task branch and worktree for every epic base. E09 has four bases (`docker`, `main`, `workflows`, `workspace`), so every E09 unit is planned against all four although nearly all change `workspace` alone. Nothing a unit carries says which long-lived branch it changes: a Component declaration is a bare path, and paths such as `scripts/` or `.github/` exist on several long-lived branches, while a component a task creates exists on none yet.

## Proposal

- **Scene.**
  A delivery survey reaches a free unit of an epic with bases `i07/e00/main`, `i07/e00/workflows` and `i07/e00/workspace`. Its one row's work item declares `workspace:skills/plan.py`.
- **The Component declaration names the long-lived branch.**
  The declaration takes git's `<revision>:<path>` shape, `<long-lived branch>:<path>`, such as `workspace:skills/work-planner/scripts/deliver.py`. The branch is stated by the planner, because it cannot be inferred: paths repeat across long-lived branches and a created path exists on none.
  - Rejected: the rows' declared component as an epic-table column. The Work Breakdown table has no such column, and adding one changes the epic format every epic and `format.py` read.
  - Rejected: inferring the branch from which long-lived tree holds the path. Ambiguous for shared paths and silent for created ones.
- **The survey reads it.**
  A free row links its work-item file. `deliver.py` takes `--engineering`, the engineering worktree, reads each linked file's declaration through `deps.read_components`, and keeps the epic bases whose long-lived branch the unit's rows name. One base keeps the unsuffixed branch, as Task Branches states.
- **One base needs no declaration.**
  A unit of an epic with one base changes that base; there is no choice for a declaration to make.
- **A missing declaration is reported.**
  In an epic of several bases, a row whose work item cannot say which base it changes prints an `undeclared` line with why (no work-item link, no `--engineering`, unreadable file, no branch in the component, or a branch with no epic base). Its unit is not offered, and the run exits 1, as an unresolvable dependency does.
- **Prose follows.**
  Work Item's Component field and template, Task Branches, the delivery plan's inputs, Work Units, Report Lines and command, and Deliver Mode's survey step.
