# Source Analysis — Workflow Server `docs/` documentation set

**Document:** `docs/` in worktree `.worktrees/plain-language-docs-audit` (15 files, ~3,482 lines, ~29,354 words) · **Findings:** 46

The set is well cross-linked and quantified, but four documents describe mechanisms the code no longer has, one 931-line document specifies a language the server cannot load, one development guide names eleven source and test files that do not exist, and the prose habit throughout is to name a concept before explaining it.

Ground truth for every count restated below: 18 MCP tools registered (14 in `workflow-tools.ts`, 4 in `resource-tools.ts`), 5 HTTP routes, 6 architecture models, 15 markdown files in `docs/`.

### Four findings that need more than a cell

**Finding 1 is the one that costs a reader real work.** `orchestra-specification.md` is the largest document in the set at 931 lines and roughly 4,400 words. It reads as a finished contract: formal EBNF grammar, Alloy constraint blocks, a complete worked activity, and twenty numbered validation rules with severities. A workflow author who follows it produces a file the loader rejects, because the language it specifies was designed and never built. The real activity language is visible in any activity the server delivers — an array of steps discriminated by `kind`, with `transitions[]` at the end. The specification's own metadata says `Status: Draft` and marks three of its four primitives "TBD", but that signal sits in a table above the fold and is contradicted by every document that links here.

**Findings 5 through 13 share one cause.** The checkpoint handle, the agent-held session token, the `bcp` gate field and the worker's README duty were all removed from the implementation, and four documents still teach them. The `.session-token` file that remains is a server-side seal over `session.json`, not a credential an agent carries, and `state_management_model.md` describes that correctly. So the set already contains the right account of persistence; the work is deleting the older one from `checkpoint_model.md` and `workflow-fidelity.md` rather than writing something new.

**Findings 16 and 37 through 42 make `development.md` the least reliable document in the set.** Its project-structure tree names eight source paths that do not exist and describes an encryption primitive the code does not implement; its test-suite table names three test files that do not exist and accounts for ten suites where the repository holds seventy-four; its benchmark section cites the wrong fixture date and the wrong corpus commit; and its coverage command cannot run because the coverage package is not installed. This is a contributor's first stop. Every one of these is a hand-maintained inventory of something the filesystem already knows, which is the failure mode the repository's own no-brittle-counts convention exists to prevent — applied there only to tallies, not to lists.

**Finding 36 is what let the other 45 accumulate.** Nothing in `docs/` records when a document was last checked against the code, so a stale document is indistinguishable from a current one at a glance. The single date stamp in the set reads "last reviewed 2026-05-14" and sits on the document that has diverged furthest. A per-document verification date is the cheap instrument; the alternative is to keep none and rely on the guard suite, which does not cover prose.

The tooling gap is worth recording alongside it. A docs-drift tally guard exists, but `README.md` sits outside the globs it inspects, which is why the wrong tool count there has survived. Nothing at all checks whether a path named in prose exists, which is how eleven dead paths accumulated in one document.

### Recorded as follow-ups, outside this rewrite

Two things surfaced that the profile puts out of scope, so the rewrite leaves them and names them here. `README.md` claims the server registers 17 MCP tools across five concerns; the true count is 18, and the file is outside `docs/`. And `package.json` carries version `0.2.0` while the server reports `2.1.0` through `SERVER_VERSION`, so an operator checking their install against the health endpoint sees a number that matches no released artifact — a code inconsistency rather than a documentation error, since `development.md` records the default correctly.

## Strengths

These hold up and the rewrite preserves them.

**`documentation-system.md` is the anchor of the set.** It states the two-layer model, maps every source to its audience, says where new documentation belongs, and codifies four conventions: present tense, no brittle counts, stable filenames, everything reachable. Three of the findings above are breaches of conventions this document already states, so the rewrite enforces the set's own rules rather than importing new ones.

**Every link in the set resolves.** A sweep of all relative markdown links across the fifteen documents found no broken file target and no broken heading anchor, including the links that reach out of `docs/` into `site/`, `scripts/`, `schemas/`, `src/` and `examples/`. Every model document links its siblings and the hub, and the "Where detail lives" table in `api-reference.md` is a genuine router rather than a courtesy list. The house link style changes how these links read, not where they point, and the rewrite must not cost the set this property.

**Measured numbers are carried, not rounded away.** 159,093 characters batched against 232,954 standalone, 57% of budget, a +24.5% regression, 69 triage verdicts, 14 reported pairs, 31.3% in 32 days. These are evidence and they survive the rewrite. The currency test removes hand-maintained inventory tallies — tool counts, test-file lists — which are a different thing.

**`technique-protocol-specification.md` opens the right way.** Its "Before the formal rules" block gives the reader who it is for, the whole idea in one sentence, and a three-step practical path, all before the normative sections start. That is the explain-then-name shape the reader profile asks for, and it becomes the template for the other documents.

**`development.md`'s guard sections are task-shaped.** "One sweep, one registry", "Did *my* change cause this?", "Corpus debt", "Sessions in flight" each lead with the command, then explain what it does and why an exit code means what it means. Headings are written as the reader's question. This is the register the rest of the set should move toward.

**The integrator documents are already short and current.** `engineering-storage.md`, `install-projects-worktrees.md` and `ide-setup.md` are command-first, carry the same path formulas as each other, and state the engineering-versus-domain boundary consistently. They need style work, not correction.

**`resource_resolution_model.md` §11 models a hard idea well.** "What counts as 'already holds'" states the rule, gives the three cases, then says what makes a marker valid. Keep the structure; thin the symbol density.
