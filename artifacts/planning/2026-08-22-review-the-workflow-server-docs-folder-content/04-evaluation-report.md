# Evaluation Report — Workflow Server `docs/` documentation set

**Round:** 0 · **Open issues:** 16

The work that was done is good and the corrections are real, but the pass reached about half the set: of the fifteen documents the profile places in scope, seven carry a plain-language rewrite and eight carry a link repoint, a single new opening paragraph, or nothing, which leaves the primary reader — the contributor — reading pre-rewrite prose in the two largest behavioural models.

## Verdict by principle

| Principle | Verdict | Basis |
|-----------|---------|-------|
| Relevant | open | The profile puts all fifteen documents in scope and holds each to five tests. Measured against the branch, `architecture`, `checkpoint-model`, `dispatch-model`, `workflow-fidelity` and `development` carry a substantive rewrite, `orchestra-specification` carries its reframing and `api-reference` carries corrections. The other eight carry between zero and three changed lines. Content selection also fails inside the source map, which is the table the profile cites as the repository's own record of who each document serves: two of the fifteen documents appear in no row of it. ([Relevance](plain-language-standard#relevance) — select the content readers need; the document type and content match the readers' needs) |
| Findable | open | Three structural problems. The set now runs two heading conventions at once, with five documents numbering their sections and ten not, and surviving cross-links depend on the numbers. Two documents still close on a bare `## Related` link list. And one mechanism has two homes: the session-file description, the atomic-write ordering and the resume-is-one-call paragraph appear in full in both `state-management-model.md` and `workflow-fidelity.md`, with the second linking to the first for "the full file layout" it has just restated. ([Findability](plain-language-standard#findability) — structure for readers; use headings consistently) |
| Understandable | open | The set uses two vocabularies for the same three agent roles, two conventions for joining words in a document title, and still names three terms of art before describing the situation they answer. The rewritten documents say the user-facing agent, the orchestrator and the worker; `state-management-model.md` and `artifact-management-model.md` still say Meta Orchestrator, Workflow Orchestrator and Activity Worker, capitalised as proper nouns, in seven places. ([Understandability](plain-language-standard#understandability) — use the same word for the same meaning; explain a specialized term at first appearance; ensure coherence) |
| Usable | open | Two of the four reader groups cannot finish their task from the document that serves them. A contributor following the development guide's setup section runs a command that fails against the current repository. An integrator reading the install-layout and IDE-setup pages gets untouched note-form prose — two of the four documents the profile assigns to that group. ([Usability](plain-language-standard#usability) — reread with the readers' purpose and context in mind and revise on the result) |

## What is not an issue

Three references to `docs/state_management_model.md` survive in `workflows/meta/README.md` and `workflows/meta/resources/README.md`. Both files live in the `workflows` submodule, held at a detached HEAD in this worktree, so they need a change on that submodule's own branch. Recorded, not counted.

The Orchestra reframing and the five renames are settled scope decisions and are not reopened here. Issue 10 concerns the convention text the renames leave standing, not the renames.

`npm run check:site` and `npm run check:anchors` both pass, and no reference to an old snake_case filename survives outside the submodule. The claim that "utilizes" and "leverages" appear nowhere in `docs/` holds — zero occurrences.
