# W05 — Delivery Cost Gate With a Verdict of Its Own

## Overview

Engine CI reports what a change costs to deliver only when the suite passes. The gate sits behind `npm run test:ci` as the last step of one job, and GitHub ends a job at its first failing step, so a change that reddens one test is reviewed with no statement about its delivery cost at all. This task gives the gate a job, so its verdict stands whatever the suite concludes.

## Problem

- **A failing suite leaves the gate unrun.**
  [`verify.yml`](https://github.com/m2ux/workflow-server/blob/86d79e8a/.github/workflows/verify.yml#L158-L170) runs `npm run test:ci` and then the delivery-cost gate as consecutive steps of the `verify` job. The step after a failing one is recorded as skipped.
- **It is the ordinary outcome, not a rare one.**
  Measured 2026-10-13 over the latest `Verify` run on each branch the workflow pushes to: the gate was skipped behind a failed suite on [i14/e03/main](https://github.com/m2ux/workflow-server/actions/runs/38354783630), [i08/main](https://github.com/m2ux/workflow-server/actions/runs/37887174548) and [i10/main](https://github.com/m2ux/workflow-server/actions/runs/37581356554).
- **The gate's subject is not the suite's.**
  The suite drives the server against the paired definitions checkout. The gate walks `delivery-fixture` under `tests/fixtures/token-bench` against `benchmark/fixtures/token-benchmark-baseline.json`, and reads neither the suite's result nor that checkout. A suite failure says nothing about whether the walk still delivers what the baseline records.
- **The documentation states two jobs.**
  [`docs/development.md`](https://github.com/m2ux/workflow-server/blob/86d79e8a/docs/development.md#L120) describes engine CI as two jobs and puts the delivery gate in the one that holds the suite.

## Proposal

A job is the unit GitHub reports a verdict for, so a question that deserves its own verdict needs a job. Engine CI asks three of a change, and the delivery-cost question is the one whose inputs are entirely inside this tree: a fixture walk against a recorded baseline, with no corpus and no server run behind it. It can be answered whether or not the suite passes, which is exactly when a reviewer most wants the answer.

- **The delivery-cost gate is a job.**
  `delivery-cost` checks this tree out, installs, and runs the fixture walk against `benchmark/fixtures/token-benchmark-baseline.json`. It names no `needs`, so it starts with the other two and its pass or fail is a check of its own.
- **It resolves no definitions.**
  The walk reads `tests/fixtures/token-bench` under `--fixture-corpus`, so the job carries neither the pairing step nor the definitions checkout. The corpus tip cannot move this verdict.
- **The suite keeps the job it has.**
  The typecheck, the schema check and the suite share one subject and one checkout, and a failure among them is a statement about this tree that the steps behind it have no answer to.
- **The documentation states three jobs.**
  `docs/development.md` names the three and what each concludes on.

## The instrument

A run with the suite red needs a tree one test fails on, and a base that carries the workflow being compared against. Two branches carry it, and they are deleted once the two runs are recorded:

- `i98/e00/main` — the `i14/e07/main` tip at `86d79e8a`, which carries the two-job workflow, plus the failing test. The push that creates it is the control run.
- `i98/e00/w05-delivery-cost-job` — this branch's head plus the same failing test. A pull request opens it against `i98/e00/main`, and that run is the observation.

The failing test is a file of its own rather than an edit to a real one, so the suite's failure is a single assertion with no second effect on the tree, and the two runs differ in the workflow alone. Neither branch pairs with a corpus of its own: the pairing step finds no `i98/workflows` and falls back to the `workflows` tip, which both runs read alike.

`npm run --silent bench:token -- --workflow=delivery-fixture --fixture-corpus --label=ci --context-mode=fresh --gate --reference=benchmark/fixtures/token-benchmark-baseline.json`

```text

```

Exit 0. The gate the new job runs holds on this tree, so a green check on the instrument runs is the gate's own verdict and not an absence of one.

The walk delivers a third of what the reference records, and the gate fails on a regression alone, so a fall of that size passes it. The reference has not been re-recorded since `ea4fc46f`, 2026-09-25. That is a property of the baseline rather than of the job this task delivers, and it is raised as an issue of its own.
