## Overview

One skill holds the scheme. Its summary names every mode it offers, each mode is stated in a file of its own, and every shell operation a mode performs is a named command spec that mode cites. Work raised outside the structure reaches a place inside it, and an epic is created only once its tasks are whole.

## Problem

- **The scheme had no home.**
  The rules for initiatives, epics and tasks lived in the conversation that applied them, so each run restated them and no two runs restated them alike.
- **One file for every mode.**
  A single body loaded the whole scheme for a request that used one part of it, and a change to one mode's rules meant reading all of them to find where it belonged.
- **Operations written out at each site.**
  Each mode spelled out its own shell calls, so the same operation drifted between modes and a correction reached only the copy it was made in.
- **Work outside the structure.**
  An issue raised without a prefix belonged to no initiative, so it reached no board, no dependency check and no review.
- **Epics started on unfinished plans.**
  An epic could be created while a task had no work file, no tests and no Joins settled, and the gap surfaced only once the work began.

## Proposal

- **A mode per file.**
  The skill summary lists the modes and what each covers; the agent reads only the file for the mode the request calls for.
- **Command specs.**
  Every operation a mode performs is a named spec with its exact call, cited from the modes that use it, so one correction reaches every caller.
- **Shared authoring guidelines.**
  The guidelines that govern how a skill is written live in one file that each skill in the repository reads, rather than once per skill.
- **Hoist.**
  A mode places work raised outside the structure: into an existing task, a new task, a new epic or a new initiative, or it stays standalone. What a placed issue recorded is kept, in its new body or in a reference to it.
- **Readiness before creation.**
  Planning completes each task's work file, its tests and every eligible Joins pair before any issue of the epic exists.

## Acceptance Criteria

- [x] **AC1.** Each mode the skill offers is named in the skill summary and stated in a file of its own.
- [x] **AC2.** Every shell operation a mode performs is a named command spec, and the mode cites that spec rather than writing the call out.
- [x] **AC3.** The authoring guidelines a skill is written to live in one file that each skill in the repository reads.
- [x] **AC4.** An issue raised outside the structure reaches an initiative, an epic, a task or the standalone layout, and what it recorded is kept in its new body or in a reference to it.
- [x] **AC5.** A request to revise the skill is served by a mode that applies the skill's own guidelines to the skill.
- [x] **AC6.** No issue of an epic is created while a task lacks a work file or its tests, or while a pair eligible to share a pull request names neither.
