## Overview

This epic makes every run read what the plan records. The test plan is the merge gate and the one table of Test, Description, Coverage and Pass, the Work Breakdown is the dependency graph, and nothing yet reads the marks the plan holds, repairs a plan written to an earlier shape, tells an unreadable plan from an untested criterion, reads a row whose Task cell carries more than one link, or tells a dependency entry it cannot read from a prerequisite that has not landed.

## Problem

- **Nothing reads the Pass marks.**
  `plan_claims` in `sync.py` destructures the Pass cell and discards it, feeding only the disagreement report. A merged pull request leaves its epic's criteria unticked, and the evidence that would settle each one sits in the pull request unread.
- **An alignment brings no plan current.**
  The step that repaired a pull request's test plan went with the two-structure mismatch it policed, and nothing replaced it. A pull request carrying the retired checked list and `Test | Criteria` table is never brought to the shape the skill states.
- **The gap is silent and it accumulates.**
  Twelve merged pull requests on one private initiative carried the retired shape. No check reported them, and each was converted by hand.
- **An unreadable plan reads as an untested criterion.**
  A plan no parser can read yields no claims, which reports as a criterion nothing tested, so the message names the wrong cause and the repair it implies is the wrong repair.
- **A reference may carry a private URL into a public ticket.**
  A References section copied from a private repository's planning record reaches a ticket anyone can read.
- **A doubly linked row leaves the dependency graph.** A unit spanning two trees links a pull request per tree, so its Task cell repeats its id. [The row filter](https://github.com/m2ux/workflow-server/blob/360f0081/skills/work-planner/scripts/deps.py#L66-L68) in `deps.py` matches the whole cell against one id and skips the row, which then contributes no node and no edge:
  - every dependency and Joins entry naming it is reported unknown;
  - the levels, the longest chains and the whole-epic report are computed over a table with holes in it;
  - a run over I04's fourteen epics reported eight such problems across six epics, each naming a row that exists and is delivered.
- **A malformed task id passes unnamed.**
  A Task cell carrying an extra digit resolves to the row its first three characters spell, and one carrying too few is skipped, so a typo in the column that holds a row's identity becomes the wrong row or no row at all.
- **An unreadable dependency entry is a hard problem to one tool and an unmet prerequisite to the other.**
  `deps.py` [names it and exits nonzero](https://github.com/m2ux/workflow-server/blob/267d4c4e68d453686107825e7a8f449efb9eae42/skills/work-planner/scripts/deps.py#L121), while [`met` in `board.py`](https://github.com/m2ux/workflow-server/blob/267d4c4e68d453686107825e7a8f449efb9eae42/skills/work-planner/scripts/board.py#L220-L223) appends `links no issue` to `unresolved` and returns `False`, the answer it gives a prerequisite that has not landed. The two are indistinguishable downstream, so a planner who runs only the queue sees a row that stays blocked and no statement of why.
- **A permanent condition is modelled as a temporary one.**
  An entry naming an issue that does not exist, a row its epic does not carry, or nothing parseable at all can never become satisfied, and `False` says only that it is not satisfied yet. Twenty-three of twenty-three cross-epic cells on one private initiative were unreadable for the length of four epics, with the queue placing rows throughout.
- **The joins advisory invites the assertion it is meant to prevent.**
  The [advisory](https://github.com/m2ux/workflow-server/blob/267d4c4e68d453686107825e7a8f449efb9eae42/skills/work-planner/scripts/deps.py#L180) names every independent pair, and the cheapest way to silence it is to name the pair in Joins, asserting a pull request they will never share, as two epics of that initiative did, one with thirteen rows each naming the other twelve. The planning-record entry that properly resolves the line silences nothing, and nothing checks that it exists.

## Proposal

- **A passed check ticks the criterion it observes.**
  Sync Epic reads the Pass cell of each linked pull request's test plan and ticks the epic criteria those passed checks name.
- **Alignment repairs a plan written to an earlier shape.**
  Align mode converts a retired checked list and `Test | Criteria` table into the one table, and reports each pull request it converted.
- **An unreadable plan is diagnosed as unreadable.**
  A plan that yields no claims is reported as a plan nothing can read, distinct from a criterion no test observes.
- **A reference is checked against the repository that will hold it.**
  A References entry citing a private repository is a finding when the issue is public.
- **A row is read by the id at the head of its Task cell.**
  The repeated-id form, the single-link form and the bare id all name one row. A cell whose links disagree on the id is a defect in the table, reported rather than skipped.
- **A task id is a W and two digits.**
  Every id a Task cell carries is held to that form, and one that departs from it is reported with the epic and the id as written.
- **A dependency entry that cannot resolve is its own outcome.**
  `met` returns unresolvable for an unparseable entry, an issue it was not given and a row an epic does not carry, distinct from the answer a prerequisite that has not landed receives.
- **One field carries one verdict across the tools that read it.**
  Whatever severity the dependency check assigns an unreadable entry, the board queue assigns the same: it names the row and the entry and leaves the row unplaced rather than reporting it as waiting.
- **The advisory names both resolutions, and the record is held to the one it claims.**
  The printed line states that an independent pair either shares a pull request and names it in Joins or is accounted for in the planning record, and a pair in neither is reported.

- [x] **AC5.** A Work Breakdown row whose Task cell links the same task id more than once is read as that row, as the skill's fixture suite shows against a table carrying the repeated-id, single-link and bare-id spellings.
- [x] **AC6.** A Task cell whose links name different ids is reported as a problem, as the skill's fixture suite shows against a table carrying one.
- [x] **AC7.** The dependency check reports no unknown dependency and no unknown Joins entry naming a row the table carries, as a run over the repository's open epics shows.

- [x] **AC9.** A `Depends on` entry that cannot resolve is reported as unresolvable by the board queue and by the dependency check alike, as the skill's fixture suite shows against a plan carrying an unparseable entry, an issue that is not given and a row its epic does not carry.
