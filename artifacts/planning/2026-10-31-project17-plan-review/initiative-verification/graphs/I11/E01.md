## Overview

An issue body reads the same whoever wrote it. Each item opens with a bold lead on its own line, states the design in at most two lines, links code from the words that carry it, and says what the system is rather than what changed. A Problem states the friction as it stands now, a pull request body states each functional change under its own lead, and a work file is prose rather than a table.

## Problem

- **Bodies that read as prose dumps.**
  An item ran to a paragraph with no lead, so a reader scanning for one facet read all of them.
- **A lead joined to its body.**
  A bold lead on the same line as its sentence left the two competing, and the lead stopped working as a label.
- **Links buried at the end.**
  A code reference sat after the sentence it supported rather than on the words that named it, so a reader followed the link to find out what it was for.
- **A Problem that described the plan.**
  Problems were written as what would be done, so nothing recorded the friction the work answers and a reviewer had no baseline.
- **Feedback answered in bulk.**
  A reply to review feedback restated the position rather than answering each point, so a reviewer could not tell which points were taken.
- **Work files as tables.**
  A task's own file repeated the epic's table instead of stating its design, so the detail a table cannot hold had nowhere to go.

## Proposal

- **Bold leads.**
  Each Problem and Proposal item opens with a bold lead, and the body sits on the line after it. A lead introducing sub-bullets keeps its introduction on the lead line.
- **Succinct items.**
  An item is at most two lines. Detail beyond that is a criterion of one invariant.
- **Links where the words are.**
  A code reference is linked from the words it supports, not appended to the item.
- **Present tense.**
  A Problem states the friction as it is now. No body carries the narrative of its own change.
- **Point by point.**
  A reply to issue feedback answers each point in turn, precisely and factually.
- **Pull request bodies.**
  Each functional change in a pull request body sits under its own bold lead.
- **Work files.**
  A task's file is paragraphs and bullets stating its design, not a table.

## Acceptance Criteria

- [x] **AC1.** A bold lead sits alone on its line, and the body it labels begins on the line after it.
- [x] **AC2.** A bold lead that introduces sub-bullets carries that introduction on the lead line.
- [x] **AC3.** A code reference is linked from the words that name it, not appended to the item.
- [x] **AC4.** A Problem or Proposal item runs to at most two lines, and detail beyond that is a criterion of one invariant.
- [x] **AC5.** A Problem states the friction as it stands, with no account of the change that answers it.
- [x] **AC6.** A reply to issue feedback answers each point raised, in the order raised.
- [x] **AC7.** A pull request body states each functional change under a bold lead of its own.
- [x] **AC8.** A task's work file states its design in paragraphs and bullets, carrying no table.
