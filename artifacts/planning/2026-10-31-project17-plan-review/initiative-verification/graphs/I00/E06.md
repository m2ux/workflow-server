## Overview

This epic adds a durable cursor to the live session file — the current step, with a frame per enclosing loop — and drives iteration against each loop's declared limit. A walk opens with nothing retired, and a fan opens only on an exit the graph binds.

## Problem

The session file records what has happened but not which step a run is on. When the server delivers an activity it marks every included step as started at the same instant, and the uniqueness key records nothing about order, so position cannot be derived from the history. Nothing drives a declared loop: the end-to-end walker walks a loop body exactly once, on purpose. History event types for a loop starting and a loop iterating exist and are never emitted.

An activity's step list is not always what its file holds. A `kind: routine` step is replaced at load by the run it names, with every identifier inside it prefixed from the reference site, so the steps a session is positioned among are produced when the definitions load rather than authored. Two consequences fall on a cursor. A position expressed as an index into the step list is an index into a list that materialisation lengthens, so the same index means different steps either side of a definition change that adds or removes a reference. A position expressed as an identifier is a generated one, so renaming a reference site changes it without anything in the activity's own file changing.

The corpus carries five routines referred to from sixteen sites, so this is a live population rather than a shape to design against. One identifier population is already positional in this way and shows what the choice costs: checkpoint responses are keyed by activity and checkpoint id, and a gate inside a materialised run carries a prefixed id there — rename the reference site and the stored answer's key names no gate, so the gate asks again and the stored answer stays as data nothing reads.

A walk resumed while a fan is open carries one branch. Meta's activity loop resumes on the first activity the client session holds in flight, and its fan path runs only off an advance's envelope, so no step spawns the other outstanding branches and the join waits on them.

- **A second walk opens on the previous activity.**
  The activity loop resets only the current activity, so the retired activity and the worker result still name the earlier walk, and the engine refuses the first advance.
- **An entered session advances twice.**
  The bootstrap and a resume from in flight call for the next activity, and the loop advances again.
- **A fan opens with no graph binding.**
  The engine accepts that destination with a warning, reports no join, and the walk stalls after the branches return.

## Proposal

Carry the current step and a frame per enclosing loop on the live session. Drive `forEach`, `while`, and `doWhile` against the declared limit. Continue an interrupted run at the next unexecuted unit. Treat a second report for a recorded position as a no-op or a refusal. Refuse a running session whose position record is missing. Say what a recorded position means for a step list produced at load, and what a session in flight does when a definition change moves one. Resume a walk standing inside an open fan over every outstanding branch, entering the join once.

- **A walk opens with nothing retired.**
  Opening clears the retired activity and the worker result. An entered session leaves the first advance to the client.
- **A yielded checkpoint resumes.**
  take-activity resumes at the gate when the reply is set. The fan-opening call and take-activity declare the trace tokens they capture.
- **No unread loop input.**
  No call site binds an activity-loop input that no step reads.
- **The engine refuses an unbound fan.**
  A fan named on the opening, or off an exit the retiring activity does not declare, is refused.
- **The walk's prose matches the run.**
  Option text, technique descriptions, specimens and the terminal commit state what the run does.
