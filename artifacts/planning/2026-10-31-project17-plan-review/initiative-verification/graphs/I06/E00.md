## Overview

Every agent in a run reads two different kinds of thing. One describes the work: which activities a workflow has, what each step does, which artifact it writes, which resource it consults. The other describes how to be an orchestrator or how to be a worker: how a session opens, how a worker is dispatched and awaited, how a gate is yielded and then resolved, what an envelope owes, where a commit runs. The first differs per workflow and a workflow author writes it. The second is identical on every run of every workflow — nothing an author writes changes it, and what does change it is a server release or a move to a different host program.

This epic moves the second kind out of the corpus and into the mechanism a host already has for holding standing instruction for an agent — a skill, one for the orchestrator and one for the worker — which leaves the technique system holding definitions and nothing else.

## Problem

Both kinds arrive the same way, as techniques resolved into the response of a workflow-server tool call, because the technique is the only construct those responses can carry. The roles are not workflow content and the corpus is the wrong home for them.

- **The opening call is almost all contract.**
  The opening `get_workflow` call resolves 23 operations into 163,684 characters, against a workflow definition of 1,595 — ninety-nine percent contract. With the pre-session text and the session response the fixed block an orchestrator reads before its first decision is 168,976 characters against a stated budget of 172,000. The same call goes out at 165,358 characters against a 60,000-character bound on what one tool result may carry, and the server logs the overage rather than acting on it. Every one of those 23 operations is role contract; not one of them describes the work the workflow does. A worker pays a separate 47,650-character baseline, and pays it again for each identity a run dispatches under.
- **Bootstrap is circular.**
  The role contract is what an agent needs before it can act, and the channel that delivers it needs a session, and opening a session is itself part of the role contract. The server breaks that circle by hand: one corpus resource is read raw and returned before any session exists. A guard exists solely to police what that text may contain, because an agent holding no session index has no way to open a corpus file — so on that one surface a markdown link into the corpus, a dotted rule address and a bare rule name are all refused, though the house style sanctions each of them everywhere else. A file on disk has no such surface, and every link in it is one the reader can follow.
- **Every run ships every host's adapter.**
  The harness adapters cost 31,304 characters, of which 11,276 describe a host the run is not on. This is structural rather than an oversight. The adapter group declares the harness kind as an input and states in its own rules that the value has no producer — no workflow variable holds it and no step sets it, because the executing agent is the only party that can observe which program it is running inside. The server therefore cannot bind it, cannot select an adapter, and ships all four so the agent can select its own through a lookup table whose entire content is four links and an instruction not to duplicate them. Three further constructs exist around the same fact: a rule forbidding any technique or activity from naming host syntax, a server-side list carrying all four adapter files plus one further operation that no other delivery path reaches, and a guard whose header records that the set is enumerated in two places that must agree and that a fifth adapter has to be added to both.
- **Progressive disclosure is hand-built.**
  Several server mechanisms share one job: stop sending a reader content it already holds or can never reach. A delivery ledger keyed on agent identity collapses a repeat to a content-hashed unchanged-marker. The fan operations ride only a workflow whose graph actually fans, and a fan-only rule is withheld from an activity whose exits fan onto nothing. The checkpoint pairs ride only a run that declares a gate. A separate set bounds what a fetch by id may reach. A rule tells a worker to fetch a step's technique on reach rather than up front. A skill gets the same behaviour from the host: the description sits in context, the body loads on trigger, a linked file is read when the reader reaches the link.
- **One fact cannot reach one reader.**
  A rule cannot be requested by reference at all — a three-segment reference resolves as not-found, a two-segment one expands to every rule its technique holds, and rule references filter output that has already resolved rather than asking for it. Selective delivery of one fact to one reader exists only as resource section citation. That is why a 2,993-character file describing the dialect a gate is written in costs 7,449 characters to deliver. A file on disk is read at whatever grain the reader asks for, and needs no construct at all.
- **Meta's techniques are two things under one name.**
  The corpus holds 515 technique files, 55 of them in the meta workflow. Most are the role: only the meta workflow itself and the conformance specimens ever bind them. Four are a shared library that client workflows genuinely reach — artifact conformance in fifteen workflows, scatter-gather in ten, the orchestration patterns in five, and variable binding in every workflow there is. The corpus already has a construct for the second kind, at the root: a library is a namespace of shared operations that declares no workflow of its own.

## Proposal

**Settle the cut once, in writing.**
A definition describes work and stays a technique, an activity or a resource. A role contract describes how to be the agent that walks a definition, and is the same text on every run — it becomes skill content. The separating question is whether a workflow author could ever write it differently; if not, no workflow should be carrying it. The four shared-library operations are the worked negative cases, so the test can be stated with both sides shown.

**One skill per role.**
An orchestrator skill holds the bootstrap, session binding, the activity loop, worker dispatch and prompt composition, transition evaluation, persistence and commit, checkpoint presentation and resolution, sub-workflow handling, fan-out and the orchestrator's own conduct. A worker skill holds dispatch verification, step execution, the language a gate and a loop are written in, variable binding, checkpoint yield and resume, activity finalisation, the batch bound, envelope discipline and the worker's own conduct. Conduct that binds both roles is a file each skill links. Dispatch and resume primitives are written inline in the host's own syntax, because the host is known when the file is authored.

**Ship one skill directory per host format.**
The Claude and Cursor formats already have install paths — the workspace template writes both a skills directory and a rules directory, and refreshes them on demand. It ships one skill today, and the repository carries a second in the Cursor format, so installing role skills is one more directory through a path that exists and is exercised. A host with no skill mechanism takes the same content as an always-applied rule. Which hosts are supported is a statement in one place.

**Give the remainder a library.**
Artifact conformance, scatter-gather and the orchestration patterns are bound by client workflows and belong at the corpus root as a library, reached by namespace exactly as the git and github libraries are. Variable binding goes the other way: it reaches workers today only because every workflow happens to declare it, which leaves an engine rule as a workflow's choice, and it is worker-skill content.

**The server stops shipping the contract.**
The two core role lists, the fan and checkpoint conditional lists, the withheld fan-only rule, the fetch-bound set and the workflow-bundle ledger entry are all in service of delivering role contract through the server, and they retire with the bootstrap resource and the tool that returns it. What `get_workflow` returns is the workflow, and the budget this repository states is the size of a definition plus a session response. The opening call sits inside the bound on what one tool result may carry.

**A handshake keeps the one guarantee server delivery gives for free.**
A contract resolved by the server that will serve the calls cannot disagree with that server. A skill on disk can lag a release. The pre-session response already carries the server name and version; it states the role-skill version it requires, the skill states what it implements, and a mismatch stops the run at bootstrap naming the refresh command. Without this the change trades a large recurring cost for a silent-failure mode.

**The guards cover the content where it lives.**
The guard policing the adapter set has no subject once the adapters go. The guard policing what the pre-session text may cite has no subject once the reader can open files. The reference, citation-grain and protocol-shape guards keep their subject and read the skill directories as well as the corpus, so role content does not leave the checks behind when it leaves the corpus.

**Build on the gate dialect already on main.**
The gate-dialect technique (`workflow-engine/step-control.md`) and the drift check pinning it against the evaluator it describes are live on main (corpus [#866](https://github.com/m2ux/workflow-server/pull/866), server [#869](https://github.com/m2ux/workflow-server/pull/869)). The dialect is the language a worker reads a definition in, which is worker-skill content, cited at whatever grain the reader asks for with no delivery wiring at all. W03 lifts `step-control.md` into the worker skill, W06 points the drift check at the skill, and W07 removes the three gate-dialect core-list entries: `workflow-engine::step-control`, `variable-binding` and the withheld `step-control::loop-control`.

**Ownership.**
The worker skill carries today's gate-dialect text until [I07 E01](https://github.com/m2ux/workflow-server/issues/937) W10 generates it from the `when` grammar; from then it carries that generated reference, and I07's regeneration guard replaces W06's gate-dialect drift guard. Where W03 or W07 change who receives which content, or a delivery limit, the rule changes on the `language` branch first ([I07 E03](https://github.com/m2ux/workflow-server/issues/939)).

**Scope.**
The 55 meta technique files, split between two skills and one new library. The workflow definition for meta itself, whose own content is two activities and a graph once the role leaves. The server-side core-operation lists, conditional bundles, withheld rules, fetch bound and bundle ledger. The bootstrap resource and the tool that returns it. The budget test, whose subject changes. The guard suite. The workspace template and its deploy script, which already install skills. The remaining 460 technique files are definitions and stay as they are.

## Acceptance Criteria

- [ ] **AC1.** The cut between a definition and a role contract is stated in one place, with the separating question and the four shared-library operations shown as worked negative cases.
- [ ] **AC2.** An orchestrator skill and a worker skill hold the whole role contract, conduct that binds both roles is one file each skill links, and variable binding and the gate dialect are worker-skill content.
- [ ] **AC3.** The workspace deploy installs and refreshes the role skills as one directory per supported host format, a host with no skill mechanism receives them as an always-applied rule, and the supported hosts are listed in one place.
- [ ] **AC4.** A skill that lags the server it runs against stops the run at bootstrap, naming the refresh command.
- [ ] **AC5.** The operations client workflows bind are reached as a corpus-root library by namespace, and no client workflow binds a meta operation.
- [ ] **AC6.** The reference, citation-grain and protocol-shape guards read the skill directories as well as the corpus, and the gate-dialect drift guard fails when the worker skill's dialect text disagrees with the evaluator.
- [ ] **AC7.** What `get_workflow` returns is the workflow, and the budget test shows the opening call inside the bound on a single tool result.
- [ ] **AC8.** No server list, conditional bundle, withheld rule, fetch bound, ledger entry, bootstrap resource, tool or guard exists whose only subject is delivering or policing role contract, and no meta technique holds role content.
- [ ] **AC9.** The budget test measures a workflow definition plus a session response.
- [ ] **AC10.** A binding-census guard registered in `check:all` reports every technique bound only by the meta workflow and the conformance specimens.
- [ ] **AC11.** The binding-census guard reports every client workflow that binds a meta operation.
- [ ] **AC12.** The tests of the citation-grain, protocol-shape, corpus-link, markdown-reference and gate-dialect drift checks each seed a violation in a role-skill fixture and assert the check fails on it.
- [ ] **AC13.** An end-to-end walk in `tests/e2e/` bootstraps against a role skill older than the server requires and asserts the run stops, naming the refresh command.
- [ ] **AC14.** The budget test fails when the fixed block carries harness-adapter text.
- [ ] **AC15.** The budget test fails when the opening `get_workflow` call exceeds `DEFAULT_MAX_RESPONSE_CHARS`.

## Open questions

- Whether a meta session survives as a state container once the role leaves, which decides what the meta workflow definition keeps in W07.
- Whether the delivery figures still hold, to settle before E00 starts. The 163,684, 168,976, 165,358 and 47,650 character figures do not reflect [#885](https://github.com/m2ux/workflow-server/pull/885) and [#921](https://github.com/m2ux/workflow-server/pull/921); re-measure them on main and restate the baseline of AC1 on [#908](https://github.com/m2ux/workflow-server/issues/908).
