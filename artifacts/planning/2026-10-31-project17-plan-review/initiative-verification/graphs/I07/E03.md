## Overview

This epic states the execution model as a member of the complete set a designer works from. A definition can satisfy every grammar and constraint and still fail when it runs, because what each agent receives, and how much can be delivered, decide whether the design works. The model covers who sees what, which audience a rule reaches, how technique contracts combine, and what fits.

## Problem

The execution model shapes every design decision, and none of it is in the set a designer is given:

- **Visibility.**
  An orchestrator receives the workflow bundle. A worker receives its activity and the skills its host loads, and never the workflow file. A rule placed where its reader never looks is silently ineffective.
- **Audience.**
  Workflow rules split into `workflow`, `activity` and `universal`, each reaching a different role. Technique contracts inherit inputs, outputs and rules from ancestor `TECHNIQUE.md` files, and bindings resolve by name match. A designer who does not know these rules duplicates or misplaces content.
- **Delivery size.**
  A single tool result is bounded at 60,000 characters (`DEFAULT_MAX_RESPONSE_CHARS`, `src/config.ts:232`). The opening context is budgeted at 172,000 (`tests/bootstrap-budget.test.ts:54`), and eager bundling spends a budget per activity. A design can be valid and too large to deliver.

The model is written for maintainers in `docs/delivery.md`, `docs/dispatch.md`, `docs/resolution.md` and `docs/state.md`. No design-facing statement exists, and none of the size limits is reported against a draft.

## Proposal

State visibility, audience and contract inheritance as rules in the constraint model on the `language` branch, alongside the runtime semantics in E01. State delivery size as registered, measurable rules. The validator in E04 reports a draft's cost per role and per activity against those limits. Generate a design-facing execution reference from these rules, and link it from the workflow-design skill as the sixth member of the set. One cost measure serves the validator and [I00 E09](https://github.com/m2ux/workflow-server/issues/534) AC11.

The model is expected to change under [I06](https://github.com/m2ux/workflow-server/issues/908), which moves role contracts into skills, and under [I00 E08](https://github.com/m2ux/workflow-server/issues/532), which moves orchestrator-only rules out of the worker bundle. Each change there updates these rules spec-first. The rule changes on the `language` branch in a `language/vX.Y.Z` release, and the server change that implements it bumps the tag the server declares ([E00](https://github.com/m2ux/workflow-server/issues/943) W02).

How bindings resolve (name-match binding, remaps, provenance) belongs to [E01](https://github.com/m2ux/workflow-server/issues/937) W08. This epic owns visibility, audience, contract inheritance and delivery size.

## Acceptance Criteria

- [ ] **AC1.** Which role receives each kind of authored content is stated as rules under rule ids.
- [ ] **AC2.** Rule audience is stated as rules under rule ids.
- [ ] **AC3.** Every delivery size limit is a registered rule with a stated value and severity.
- [ ] **AC4.** A draft's delivery cost is measured per role and per activity and reported against those limits.
- [ ] **AC5.** A design-facing execution reference is generated from the rules and linked from the workflow-design skill.
- [ ] **AC6.** A change to delivery or dispatch behaviour that alters a stated rule fails conformance until the rule is updated on the `language` branch and the declared tag covers it.
- [ ] **AC7.** Dispatch depth and nesting are stated as rules under rule ids.
- [ ] **AC8.** Contract inheritance is stated as rules under rule ids.
