## Overview

This epic gives the language a home of its own: an orphan `language` branch, separate from the server and the corpus. The language is a contract. The server's loader and guards, the walker, the runner and a later typed language implement it; corpus authors and the workflow-design skill consume it. The branch holds everything about the language and nothing else.

Existing artifacts move unchanged and every consumer is rewired, so the new structure is tested end to end on the artifacts it already holds.

## Problem

Language material has no home of its own:

- **Schemas.**
  The published definition schemas are generated into `schemas/` on `main`, which makes the server look like the language's owner.
- **Canon.**
  The design principles, anti-patterns, convention conformance and construct inventory sit in the corpus under `corpus/canon/`. The corpus is meant to hold workflows, not the rules for writing them.
- **Prose.**
  Language descriptions are spread across server `docs/` and corpus `docs/` (`design-canon.md`, `identifier-conventions.md`).

A spec written on `main` would inherit the same confusion. A registry that checks an implementation against a spec needs the spec upstream of every implementation.

These artifacts have consumers on every branch, and a move that misses one breaks it:

- **Deployment.**
  The deployed image copies `schemas/` from `main` at build time (`COPY schemas ./schemas` in the `docker` branch's `Dockerfile`). Deployed hosts refresh only the `workflows` checkout (`update-workflows.sh`).
- **`workspace`.**
  The `workflow-canon` skill names `corpus/canon/resources/…` paths and tells an agent to confirm that folder exists.
- **CI and provisioning.**
  Both assume schemas on `main` and canon in the corpus.

## Proposal

**Move unchanged.**
Create the orphan branch, worked through `.worktrees/language` as `workflows` and `engineering` are. Move the existing artifacts unchanged:

- the canon, from `corpus/canon/`;
- the language documents, from corpus `docs/`;
- the published definition schemas: workflow, activity, routine, technique and condition.

Session and assembled-object schemas are server internals and stay on `main`; the resolved tree is language, not an assembled object.

**Versioned by tag.**
A language release is a house semver tag, `language/vX.Y.Z`, and each release adds one rule family. The first tag marks the moved artifacts. The server declares the tag it implements.

- **Pinned:**
  CI, provisioning and the image build check out that declared tag.
- **Head:**
  read only to report rules newer than the declared tag as pending.

This deliberately departs from the corpus rule of tracking the branch head, because a spec leads its implementation: a newer rule is expected before the server enforces it, and must not turn `main` red. The server bumps its declared tag when it implements the next family.

**Rewire every consumer**, at the declared tag:

- **Development:**
  provisioning creates the worktree. The server reads schemas through `SCHEMAS_DIR` pointed at the language worktree, and resolves the `canon` namespace from the language worktree as a second namespace root. `check:schemas` compares the schema rendered from Zod against the language copy. Sandbox roots include the worktree.
- **Consumers on every branch:**
  a sweep of `main`, `workflows`, `workspace` and `.project` guides finds every reference to canon or schema paths, including the `workflow-canon` skill, and repoints each.
- **CI:**
  server CI and corpus CI check out the declared tag beside the corpus.
- **Deployment:**
  the image build checks out the declared tag and copies the language artifacts in, as `schemas/` is copied today. The server and the language version it implements ship as one unit, and hosts need no new script.

**Prove nothing changed.**
Before the move, the served schema and `canon` resources are snapshotted at `main/v0.29.0` and `workflows/v0.33.0`. After rewiring, the server must reproduce that snapshot exactly.

**Delete the originals** once the rewired image has shipped, so nothing has two homes. The legacy `workflow-design` corpus workflow, which cites canon paths, is deleted with them rather than repointed.

**Pending rules.**
Conformance runs at the declared tag and reports each rule introduced after it as pending. That report is part of the conformance registry ([E01](https://github.com/m2ux/workflow-server/issues/937) W04). The workflow-design skill checks against the same declared tag.

The workflow-design skill stays on the `workspace` branch and links to the language artifacts as MCP resources the server serves.

## Acceptance Criteria

- [ ] **AC1.** An orphan `language` branch exists, is provisioned as `.worktrees/language`, and carries `language/vX.Y.Z` tags, each adding one rule family.
- [ ] **AC2.** The canon, corpus language documents and published definition schemas live only on the language branch.
- [ ] **AC3.** The server reproduces, from the language worktree, the schema and `canon` resource snapshot taken at `main/v0.29.0` and `workflows/v0.33.0`.
- [ ] **AC4.** `check:schemas` fails when the schema rendered from Zod differs from the language copy at the declared tag.
- [ ] **AC5.** Server CI, corpus CI, provisioning and the image build all check out the declared tag, and every test and guard passes after the originals are deleted.
- [ ] **AC6.** A deployed server built from the image serves the same schema and `canon` resources as a development server at the same declared tag.
- [ ] **AC7.** A sweep of every branch finds no reference to a moved path.
- [ ] **AC8.** A change on the language branch after the declared tag never fails `main`.
- [ ] **AC9.** Server `docs/` holds no description of the language that the language branch also holds.
- [ ] **AC10.** The language branch runs its own verify job on every change.
- [ ] **AC11.** The legacy `workflow-design` corpus workflow is deleted from `workflows`, so a sweep of every branch finds no moved path cited from it.
- [ ] **AC12.** The first language tag holds the canon, corpus language documents and published definition schemas unchanged from `main/v0.29.0` and `workflows/v0.33.0`.
- [ ] **AC13.** The development sandbox's roots include the language worktree.
- [ ] **AC14.** The docs site build reads the language prose from the language branch.
- [ ] **AC15.** A scripted live check fails when the schema and `canon` resources a deployed host serves differ from a development server's at the same declared tag.
- [ ] **AC16.** The cross-branch language sweep fails when a language artifact exists on any branch other than `language`.
- [ ] **AC17.** The cross-branch language sweep fails when a consumer checks out the language at anything other than the declared tag.

## Open questions

- Whether the move carries history, through a path-filtered split, or starts the branch from a single import commit.
- Whether the second namespace root is specific to `canon` or general to any namespace the language branch holds.
