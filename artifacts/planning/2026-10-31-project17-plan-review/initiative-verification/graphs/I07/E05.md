## Overview

This epic creates a workflow-design skill: the host skill a designing agent loads to author a workflow. Its content is the complete set of contingent information the definition language requires, meaning its rules and its execution model, plus a catalogue of the reusable parts the corpus already holds. The skill links each source and restates none of them.

## Problem

No single place holds what a designer needs. The schema states structure and nothing else. The grammar lives in parser source and prose. Constraints are spread across Zod, loaders, runtime checks and guards. The execution model is written only for maintainers. Design principles (47) and anti-patterns (186 headings) live in the corpus canon. About eleven further prose homes restate parts of all of these and disagree with them:

- corpus docs route with a `transitions` field that does not exist;
- `format-conventions.md` prescribes `condition` and `to` on exits;
- link form, singular `## Output` and flat protocol lists are each allowed in one home and rejected in another;
- five files link a `schemas/README.md` that does not exist.

A designer also cannot see what already exists. With no index of the corpus's techniques, routines, libraries and resources, a designer re-authors operations the corpus already holds, which is itself an anti-pattern. The skill, the generated reference, the running server and the corpus branch can each be at a different version, so a designer can apply a rule from a version newer or older than the one the server enforces.

The existing `workflow-canon` skill is an audit procedure over the canon homes, not an authoring reference. It carries one of those dead links.

## Proposal

Define the complete set and what each member contributes:

| Source | Contributes | Epic |
| --- | --- | --- |
| Definition-file schemas | What an author writes, and nothing the server builds | E01 |
| Grammar | Syntax inside values, the technique outline, resource files | E01 |
| Constraints | Rules spanning fields and files, including registered conventions | E01 |
| Execution model | Who sees what, which rules reach whom, what fits | E03 |
| Design principles | Authoring stance | E02 |
| Anti-patterns | Detectable faults and their fixes | E02 |

A generated catalogue of the corpus's reusable techniques, routines, libraries and resources sits beside the set, so a design reuses before it authors.

Build the skill with progressive disclosure: a short body that routes by construct through the construct index from [I09 E05](https://github.com/m2ux/workflow-server/issues/1029), and links into the generated reference from E01 and E03 and into the canon. The skill's source stays on the `workspace` branch with the other skills, and ships through the host skill install path.

**Links are MCP resources.**
The skill links the reference, canon and catalogue as MCP resources the server serves at the `language/vX.Y.Z` tag it declares ([E00](https://github.com/m2ux/workflow-server/issues/943)). A resource resolves in a development checkout and against a deployed server alike, and always matches what the server enforces. A worktree path resolves only in a development checkout, and can run ahead of the server. The skill states the tag it was written against. A mismatch with the tag the server declares stops the designer and names the refresh command, as I06 does for role skills.

An agent reads EBNF reliably and Alloy much less so, and neither format carries meaning on its own, so the skill does not send an agent to the formal files first. It routes in this order:

1. The per-rule reference entry, which gives a plain statement, a fix and checked examples.
2. The formal file as the authority, with the notation primers from E01.
3. Draft verification from [E04](https://github.com/m2ux/workflow-server/issues/941), run on the draft to confirm it.

Whether the skill is sufficient, and whether it needs a design method, is decided by [E06](https://github.com/m2ux/workflow-server/issues/942). E06 W06 adds the method to the skill if the measures call for it.

Disposition every prose home outside the canon that restates a member of the set: point it at the source, or delete it. This includes `workflow-canonical.md`, corpus `docs/README.md`, `format-conventions.md`, `yaml-authoring.md`, `workflow-authoring/resources/yaml-style.md` and `techniques/workflow-definition/audit-canon.md`. Disposition the `workflow-canon` skill against the new one.

## Acceptance Criteria

- [ ] **AC1.** The complete set is stated in one place, with what each member contributes and why nothing outside it is needed to author a workflow.
- [ ] **AC2.** A designing agent with the skill loaded can reach every construct's structure, value syntax, rules, execution behaviour, governing principles and anti-patterns.
- [ ] **AC3.** The skill links each source and restates none of them.
- [ ] **AC4.** The skill installs through the host skill path for every supported host format.
- [ ] **AC5.** No prose home restates a member of the set in place of pointing at its source, and no link names a home that does not exist.
- [ ] **AC6.** The `workflow-canon` skill carries a disposition: retired, or narrowed to what the workflow-design skill does not hold.
- [ ] **AC7.** Every source the skill links is an MCP resource the server serves, and a guard fails when a linked resource does not exist.
- [ ] **AC8.** The skill routes an agent to the per-rule reference first, the formal file as authority, and draft verification to confirm a draft.
- [ ] **AC9.** A generated catalogue of reusable techniques, routines, libraries and resources is linked from the skill and regenerates with the corpus.
- [ ] **AC10.** A skill whose tag differs from the `language/vX.Y.Z` tag the server declares stops the designer and names the refresh command.
- [ ] **AC11.** The skill routes an agent by construct to that construct's sources.
