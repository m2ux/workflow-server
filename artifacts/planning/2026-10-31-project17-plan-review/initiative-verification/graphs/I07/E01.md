## Overview

This epic states the definition language's grammar and constraints formally, and checks the implementation against them. The spec is the source, a registry binds each rule to the code that enforces it, and the design-time reference is generated from both.

## Problem

There are twenty-three micro-grammars; only three have a single definition. The rest are parsed by hand-written code and regexes in several places, and the copies disagree:

- the `{token}` grammar is declared about twelve times, and one copy rejects the dotted form the renderer accepts;
- technique references are reimplemented in two guards, one of which replaces only the first `::`;
- the technique markdown outline is re-parsed by about fifteen guards with differing heading regexes;
- checkpoint response keys are matched by prefix, so activity `review` also picks up `review-code`;
- the rule against mixing `&&` and `||` is checked only outside parentheses, so `(a && b || c)` passes.

Constraints are enforced by six mechanisms under six identity schemes: guard ids, loader `L1`–`L16` comments, runtime `T` comments, `AP-NN`, issue numbers, and bare messages. The value-set rule blocks in Zod, warns at runtime, and fails two guards under different ids. The fan ceiling is checked at load and again at runtime. `enforcement.json` marks `exits` and `initialActivity` advisory, yet the loader blocks on both. Nothing checks that metadata against behaviour.

JSON Schema cannot state any of this. A `pattern` cannot match balanced parentheses, and no schema keyword spans two fields or two files.

What a designer is shown is also not what a designer writes:

- **Server-only shapes.**
  The published schemas mix authored fields with fields the server builds. `WorkflowSchema` carries the assembled `activities` list, and `TechniqueSchema` carries delivery-only `source`, `destination`, `provenance_note` and `inherited_*`. `artifactPrefix` is server-computed.
- **Two forms.**
  Routine steps are materialised at load, so a rule can hold of the authored form and not of the materialised one, or the reverse.
- **Rules outside every set.**
  Ten convention guards fail a corpus change on prose shape, section framing, citation form and checkpoint presentation, and belong to no stated set. Resource files and cross-references are authored and checked, and no grammar covers them.
- **Silent skips.**
  The loader skips an activity file that lacks its `NN-` prefix, with no error, so a misnamed file disappears and no rule fires.

## Proposal

**Formal spec.**
The spec lives on the orphan `language` branch ([E00](https://github.com/m2ux/workflow-server/issues/943)), at its root in `grammar/`, `constraints/` and `schemas/`. The branch's definition-file JSON Schemas are the statement of structure: one per file kind, distinct from the assembled-object schema, holding only what an author writes. Zod on `main` stays hand-written as the implementation, and the registry checks its rendering against the language copy. W3C EBNF grammars (`grammar/*.ebnf`) state syntax inside values, the technique outline, and resource files with their cross-references; the `ebnf` package runs each file as the reference parser. Alloy (`constraints/*.als`) states static semantics: uniqueness, reference resolution, graph and exit binding, fans, variable provenance, loop shape, routine signature closure and value sets. Alloy 6 temporal states session transitions. The formats follow the 2026-02-10 experiment; its content describes a model the language does not follow, and is not reused. The Alloy Analyzer checks the model on its own terms.

**Every rule** carries:

- a semantic rule id;
- a one-line statement;
- a one-line fix;
- the form it applies to, authored or materialised.

Convention rules that neither notation can express are registered with a precise statement and fixture-backed examples. A spec release is a `language/vX.Y.Z` tag adding one rule family ([E00](https://github.com/m2ux/workflow-server/issues/943)).

**Complete by construction.**
Every error path, finding and skip in the loaders, routine resolver, runtime tools and guards carries a registered rule id or a recorded disposition. No authored file is skipped silently: a file the loader cannot place is a finding under a rule.

**Conformance registry.**
One generated constant per rule id; a hand-written map from each rule to its enforcers (Zod, loader, runtime, guard, parser). The build fails on four conditions:

- **Coverage:**
  a rule without an enforcer, or an unknown id, which is a compile error.
- **Severity:**
  two enforcers disagree on a rule's severity.
- **Grammar conformance:**
  a registered parser or regex disagrees with the reference parser. The comparison runs on sentences generated from the grammar and on their near-miss negatives. The `ebnf` package parses but does not generate, so the sentence generator is built in W02.
- **Constraint conformance:**
  the real loader and guards fail to reject, under the rule's id, an Analyzer-generated instance that violates exactly one fact.

A regeneration guard fails on drift, extending `check:schemas`.

**Written for agent readers.**
A formal file is the authority, but a designing agent reads it reliably only with support around it:

- **EBNF:**
  each `.ebnf` file opens with a header naming the dialect, the whitespace rule and whether choice is ordered. Every production that carries meaning has a one-line meaning comment and one valid and one invalid example. Rules that can be syntactic are productions, such as separate and-chain and or-chain productions.
- **Alloy:**
  the `.als` files keep to a restricted subset with named helper functions in place of long operator chains. A one-page primer covers that subset. A generated table maps each signature field to its schema path.

**Generated reference.**
One reference per construct, covering structure, value syntax and rules, served as an MCP resource and rendered on the site. Each rule entry holds:

- its id and a plain statement;
- its fix;
- a link to its formal source;
- a minimal passing and failing example.

The failing examples are the Analyzer-generated conformance fixtures, so every published example has been checked against the real loader and guards. Validating a draft against these rules is [E04](https://github.com/m2ux/workflow-server/issues/941).

**The spec moves with the language, spec-first.**
The spec describes the language as it stands. A change to the language lands on the `language` branch first. That includes [#709](https://github.com/m2ux/workflow-server/issues/709), [#750](https://github.com/m2ux/workflow-server/issues/750), [I00 E01](https://github.com/m2ux/workflow-server/issues/529), [I00 E02](https://github.com/m2ux/workflow-server/issues/699), [I00 E03](https://github.com/m2ux/workflow-server/issues/530), [I00 E04](https://github.com/m2ux/workflow-server/issues/698) and [I00 E07](https://github.com/m2ux/workflow-server/issues/531). The server declares the `language/vX.Y.Z` tag it implements (E00 W02), and conformance runs at that tag with newer rules reported as pending (W04). The rule catalogue and generated constants come from the language branch at the declared tag. The rule-to-enforcer map, the conformance tests and the regeneration guard stay on `main`, beside the code they check.

**Ownership.**
W08 owns how bindings resolve and where values come from: name-match binding, remaps and provenance. [E03](https://github.com/m2ux/workflow-server/issues/939) owns visibility, audience, contract inheritance and delivery size. [I00 E03](https://github.com/m2ux/workflow-server/issues/530) W01 and [I00 E04](https://github.com/m2ux/workflow-server/issues/698) W03 unify the slug, reference and token implementations; W06 states their grammar and binds the one implementation each. The gate-dialect text in the worker skill [I06 E00](https://github.com/m2ux/workflow-server/issues/868) W03 writes is generated from the `when` grammar by W10, and the regeneration guard holds it in place of I06's gate-dialect drift guard.

**One gate language.**
W02 specifies `when` only. No grammar or constraint is written for a construct about to be removed: `condition` on steps ([#750](https://github.com/m2ux/workflow-server/issues/750)), the structured condition on loops and actions ([I00 E01](https://github.com/m2ux/workflow-server/issues/529) W05) and the `kind` field ([#709](https://github.com/m2ux/workflow-server/issues/709)). If #750 or I00 E01 W05 has not landed when W08 starts, the condition it retires is specified in W08 and deleted with it.

## Acceptance Criteria

- [ ] **AC1.** Every grammar governing authored values, the technique outline and resource files is stated once, in a W3C EBNF `.ebnf` file that runs as the reference parser.
- [ ] **AC2.** Every constraint on authored definitions is stated once, as an Alloy fact or as a registered convention rule, under a semantic rule id.
- [ ] **AC3.** A string field whose value has syntax names the production that defines it in the generated JSON Schema.
- [ ] **AC4.** Every finding, loader error, runtime error and refinement cites a registered rule id by generated constant.
- [ ] **AC5.** The build fails when a rule has no enforcer, or when two enforcers of one rule disagree on severity.
- [ ] **AC6.** The build fails when any registered implementation of a grammar accepts or rejects differently from the reference parser on generated sentences and near-miss negatives.
- [ ] **AC7.** The build fails when an Analyzer-generated single-violation instance is not rejected under its rule id, or a satisfying instance does not load clean.
- [ ] **AC8.** The build fails when a generated artifact differs from the spec.
- [ ] **AC9.** Each construct has a generated reference, served as an MCP resource and rendered on the site.
- [ ] **AC10.** Mixed `&&`/`||` chains without parentheses are rejected at every nesting depth.
- [ ] **AC11.** Every `.ebnf` file declares its dialect, whitespace rule and choice semantics, and every production that carries meaning has a meaning comment with a valid and an invalid example.
- [ ] **AC12.** The `.als` files keep to a documented Alloy subset, with a primer, and a generated table maps every signature field to its schema path.
- [ ] **AC13.** Every rule's reference entry carries its fix and a passing and a failing example, and each failing example is a conformance fixture the real loader and guards reject under that rule.
- [ ] **AC14.** Each file kind has a published definition-file schema holding only authored fields, and every rule states whether it applies to the authored or the materialised form.
- [ ] **AC15.** Every convention guard's checks are registered rules, each with a statement and fixture-backed examples.
- [ ] **AC16.** Every error path, finding and skip in the loaders, routine resolver, runtime tools and guards carries a registered rule id or a recorded disposition, and no authored file is skipped without a finding.
- [ ] **AC17.** Each spec release is a `language/vX.Y.Z` tag adding one rule family, and the generated reference and constants carry the tag they were built from.
- [ ] **AC18.** No grammar or constraint is written for `condition` on steps unless #750 has not landed by W08, or for the structured condition on loops and actions unless I00 E01 W05 has not landed by W08.
- [ ] **AC19.** Rules introduced after the declared tag are reported as pending, not failed.
- [ ] **AC20.** Session transitions are stated in Alloy 6 temporal logic, and the Analyzer checks the model's temporal properties.
- [ ] **AC21.** Rule severity is stated once, in the registry, and no separate enforcement file exists.
- [ ] **AC22.** For every rule the gate form states, an artifact fails when that rule is violated.
- [ ] **AC23.** A rule whose only home is a description string is rejected.
- [ ] **AC24.** A second token grammar fails the change that introduces it.
- [ ] **AC25.** Each value syntax and the technique outline has one parser implementation.
- [ ] **AC26.** Each build-failure condition the registry defines has a test that seeds one disagreement and shows the build failing on it.
