## Overview

This epic composes the existing per-graph operations into one named run that evaluates the reach of a code-level concern across every member of a repository group, a set of repositories indexed together, not just the repository it was raised against.

## Problem

- **One graph per answer.**
  Every impact and context answer is addressed at one named graph.
- **No cross-repository reach.**
  Repository groups offer merged concept search and an HTTP-contract registry joining publishers to consumers, but a symbol consumed across repositories through a language-level dependency is invisible to both. Macro-generated and type-level edges never enter a graph, so a concern's cross-repository reach has no named operation.

## Proposal

- **One answer per member.**
  The run brings every member graph and the contract registry current, then records, for every member, whether the concern reaches it and what that member consumes the home as. A member's graph holds no node for a name its tree imports, so that reach is an answer about the member, not an edge that leaves its graph.
- **Home, then boundary.**
  The run locates the concern in its home graph and takes its blast radius there. The boundary another member could reach it by is the exported surface, the routes and tools served from it, and the packages the home is consumed under.
- **Probe and derivation.**
  The run probes every other member and records one answer per member, naming the graph consulted and the instrument that settled it. Where the graph holds no edge, the entry records a search of the member's tree and names that instrument.
- **Symbol reach and the registry.**
  Reach settles from symbols in the member itself. The registry's declared library link sits beside that reach as what the member consumes the home as.
- **Boundary.**
  The epic does not change the GitNexus engine or the graph schema. Single-graph operations stay as they are.
