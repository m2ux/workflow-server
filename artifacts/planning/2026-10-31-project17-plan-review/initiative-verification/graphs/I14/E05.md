## Overview

Neither `main` nor `workflows` is a protected branch, so a pull request merges whatever its checks concluded. Three merged with a failing check and left `main` red in twenty tests across four files. Separately, the corpus job runs two of the server's test files rather than the suite, so a corpus-only change that breaks one of the others passes its own checks and surfaces later on `main`.

## Problem

- **Nothing enforces a green check.**
  `GET /repos/m2ux/workflow-server/branches/main/protection` and the same call for `workflows` both return `Branch not protected`. No check is required, so a red merge needs no override and leaves no record that one happened.

- **Three pull requests merged red, and `main` carried all four failures at once.** Each check conclusion is the one recorded against the head commit at merge:
  - [#1149](https://github.com/m2ux/workflow-server/pull/1149) → `workflows`: `Guard sweep against the corpus under review` — failure.
  - [#1154](https://github.com/m2ux/workflow-server/pull/1154) → `workflows`: `Guard sweep against the corpus under review` — failure.
  - [#1151](https://github.com/m2ux/workflow-server/pull/1151) → `main`: `Typecheck, tests, and the fixture delivery gate` — failure.

- **The failures were detected, not missed.**
  `main` at `db95c384` ran 20 failing tests over `batch-loop-walk`, `binding-triage`, `docs-drift` and `e2e/snapshot`. Every one of them failed on a check that had already run before the merge that introduced it. Detection held; the merge gate is what is absent.

- **The corpus job names two server test files, not the suite.**
  [`verify-corpus.yml`](https://github.com/m2ux/workflow-server/blob/38bc4aea/.github/workflows/verify-corpus.yml#L104-L108) runs `tests/e2e/snapshot.test.ts` and `tests/e2e/all-workflows-walk.test.ts` beside the guard sweep. The suite holds further tests that read corpus files — `tests/batch-loop-walk.test.ts` reads `meta/routines/activity-loop.yaml`, `tests/binding-triage.test.ts` reads `ledgers/binding-fidelity-triage.json` — and a corpus change that breaks either passes the corpus job.

- **A corpus-only change has no second chance to be caught.**
  `main`'s job checks out `workflows` as its corpus, so a corpus change paired with an engine change is measured there. One raised against `workflows` alone is measured only by the corpus job, and reaches `main` at the next unrelated merge.

## Proposal

- **Run the corpus-reading tests in the corpus job.**
  The two named files become the set of server tests that read the corpus, so the job measures what a corpus change can break. Which tests those are is derivable — they resolve `WORKFLOWS_DIR` through `liveCorpusRoot()` — so the set can be selected rather than listed and kept in step by hand.

- **Protect both long-lived branches, with the checks each already runs required.**
  `main` requires `Typecheck, tests, and the fixture delivery gate`; `workflows` requires `Guard sweep against the corpus under review` and `Every declared checkpoint option is reached`. A red merge then needs an explicit, recorded override.

- **Keep the job's shape.**
  It already checks out the paired engine branch and runs `npm ci`, so the added files cost the runner their own duration and no new setup.
