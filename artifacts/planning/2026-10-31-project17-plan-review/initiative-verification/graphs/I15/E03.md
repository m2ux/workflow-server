## Overview

A session's planning folder is named for the work it holds, at the moment the folder is made. The name is composed from the request before the session opens, so no later step has a rename to do, and the path that renamed a folder after the fact retires with it.

## Problem

Every planning folder the server created from 14 September onward is named for the engine that opened the session. The planning root holds `2026-09-14-meta`, `2026-09-17-meta`, `2026-09-21-meta-2`, `2026-09-24-meta`, `2026-10-01-meta`, `2026-10-01-meta-2`, `2026-10-03-meta`, `2026-10-07-meta`, and `2026-10-02-mvw` — nine of the last thirteen folders a session created, each naming the workflow id rather than the work. The folders before them read `server-owned-session-setup`, `session-records-which-path-drove`, `time-to-client-dispatch`.

- **The server named the folder before anyone knew what the work was.**
  `start_session` made a session durable as soon as it had a `working_directory` and named its folder `YYYY-MM-DD-<workflow_id>`. Under the bootstrap that id is always `meta`, never the client workflow and never the subject. Collisions walked to `-2`, `-3`.
- **Naming it durably killed the path that named it properly.**
  The descriptive slug reached the folder through `dispatch_child`, which promoted a *transient* parent. A parent that was already persistent takes no promotion, so the argument carrying the descriptive slug stopped being read. Its own schema said so: "Ignored if the parent is already persistent."
- **The technique that composed the name was swept out as an orphan.**
  `derive-planning-slug` was bound by no activity, because its only caller `create-session` was itself unbound once the client session began arriving embedded in the `start_session` response. The sweep was correct; nothing replaced it.
- **One work package got two folders.**
  `setup-planning-folder` composed a planning path of its own and overwrote `planning_folder_path` in the bag. The server's folder held `session.json` and the engine's artifacts; the agent's descriptive folder held the rest. `2026-10-07-meta` holds the intake for work whose specification lives in `2026-10-06-work-planner-retrospective`.
- **Evidence.**
  The two causes are independent and neither is visible from the other's tree: the server named folders after the engine from 11 September, and the corpus lost its naming technique on 5 October. A folder named for the date and the engine tells a reader when a session opened and nothing else.

## Proposal

**The caller names the folder, because the caller holds the request.**
The bootstrap composes a planning slug as `YYYY-MM-DD-<issue-or-pr-ref>-<kebab-name>`, dropping the ref segment for work that carries none, and passes it to `start_session`. The server cannot do this: it has no language model, and mechanical slugification of a free-form sentence yields a worse name than the one it replaces.

**The server resolves the root, so the caller composes no path.**
`planning_slug` is a single path segment. The planning root sits under the top-level project folder, which for a worktree or a second clone is neither the working directory nor any ancestor the caller can see, so a bare slug is the only thing a caller can supply correctly.

**A session that names nothing gets a folder named for nothing.**
`YYYY-MM-DD-<token>`, six random base32 characters. The date keeps the planning root sortable; the token means two unnamed sessions never contend. Specimen walks mint a folder per walk and are the main consumer of this path, so it is collision-free rather than refused.

**The folder is named once, at the open, and keeps that name.**
A session resolves its planning root when it opens, from the checkout under work or from the repository it binds, so none waits in a temp folder to learn where it belongs. A child embeds under its parent and takes the parent's folder, and every `session_index` resolves through the workspace enumeration.

**`setup-planning-folder` writes into the folder the session opened.**
Composing a path there gave one session two homes, and only the server's was the one the session recorded.
