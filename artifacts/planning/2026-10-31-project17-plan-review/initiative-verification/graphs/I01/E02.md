## Summary

Twenty-four work-package runs closed with a retrospective between 1 July and 5 August 2026. Reading
all of them together against the live definitions shows a pattern the individual runs could not: the
review path keeps producing the same handful of hand-caught items, run after run, and each
retrospective closed them out as "informational only". Eighteen of those items survive. None came
from a closed issue, so none belongs to the corpus-backlog epic; none is a server capability, so none
belongs to the engine epics. They are the review path's own definition debt.

Each is small. Together they are what a reviewer does by hand on every run because no step does it:
comparing failing CI against the base branch, checking whether a relocated manifest stranded the
dependency bot, noticing that a config file and its readme disagree, building a call-site inventory
that a later activity then rebuilds. The cost is a few minutes per review, every review, plus the
occasional finding that only got caught because someone was paying attention.

This epic makes the review path catch by definition what its reviewers keep catching by hand.

## Where these came from

Eleven review runs between 07-07 and 08-05 raised them, several independently raising the same one.
The full accumulation — 70 items, each traced to its source retrospective and checked against the
definitions as they stand — is in the
[July–August retrospective review](https://github.com/shieldedtech/midnight-agent-eng/blob/mike/.engineering/artifacts/planning/2026-08-06-workflow-retrospective-review/README.md).
Of those 70, thirty-one are already fixed, twelve belong to open epics as additions and are recorded
there, five are already named in an epic's work items, and four are not workflow work at all. These
eighteen are the remainder.

## The work

**W01 — The review says what it did, and on what basis.** A review work package's terminal state is
"review posted, awaiting the author's disposition", not a merge the workflow will never perform, so
a finished run stops reading as incomplete. The rating cap gains a second carve-in: a review with
zero code defects whose every requested action is author communication may recommend a comment-style
outcome directly, rather than reaching request-changes and relying on a user override at the
approval gate. `submit-for-review` checks the pull request's merge state before composing the
summary and selects post-merge-advisory framing explicitly — one run had its PR squash-merged
mid-review and reframed the deliverable by hand. And when the local suite cannot run, the validation
artifact names CI at the reviewed head as the authority for every claim about the suite, rather than
leaving the basis implicit.

**W02 — Five hand-checks become steps.** Each is a check a reviewer performed from memory, on a run
where forgetting it would have changed the verdict.

- Failing CI on a feature branch is dispositioned only after comparison against the base branch. A
  bot comment alone was insufficient on the run that surfaced this; the base comparison was the gate.
- A pull request that relocates a package manifest is checked for dependency-bot directory entries
  that still point at the old path. Caught twice on one PR, in prior-feedback triage and again in
  code review.
- A configuration-only pull request is checked for documentation that contradicts the configuration
  it documents — a readme claiming one key while the keystore holds another.
- Facts only an operator can confirm, such as whether a CI secret is present, are recorded as a
  recommended operator confirmation rather than treated as a reviewer blocker; a read-only review
  cannot settle them either way.
- A specification document reviewed against an implementation carries an acceptance criterion
  pinning it to an implementation commit. A merge into the base moved the implementation out from
  under a spec on one run, and the drift was found by reconciling assumptions rather than by reading
  the diff.

**W03 — Build each inventory once.** Comprehension produces the inventory a later activity currently
rebuilds: the full call-site list for guard reviews, the key-alignment matrix across environment
file, genesis, keystore and readme for multi-node topology changes, the branch-coverage matrix for
pure-function refactors. Alongside it, two passes stop restating each other — the leanness audit and
the strategic review report the same over-engineering findings today, and on a documentation-only
review the post-implementation and validation passes restate the same blockers across three or four
artifacts.

**W04 — The build path holds its own line.** The implement step gains a comment-proportionality bar:
new comments match the density of the surrounding code, and rationale that already lives in the plan
or design artifacts is referenced rather than restated inline. The leanness audit was tightened for
this in #272 and now catches it downstream; the authoring step still produces it. Separately, when
the implement step cannot run tests, it still updates any test whose invalidation is statically
evident from its own diff — a reordered positional assertion, say — rather than leaving it for a
later pass to discover.

**W05 — Authoring conformance in the definition.** Four items where the definition and its own rules
disagree. Pull-request-body conformance is assessed at intake rather than at strategic review, where
it currently surfaces too late to be cheap. The `follow-ups.md` and `deferred-items.md` registers get
a step that writes them: the resource calls the first "the one canonical home for in-task
follow-ups", and close-out reads both, but nothing creates them, so one run recorded open work in its
close-out and left no register at all. One checkpoint offers five options against a four-option
maximum. And the pull-request description's Changes section is authored as plain-language prose
about the substance of the work — the current guide forbids enumerating file paths, which answered
the complaint, but did not settle the form.

## Why now is cheap

No investigation is owed. Every item is already traced to the run that raised it, with the file and
the failing behaviour named, in a register that also records which of them recurred and how often.
The four work items are independent of each other and of every other open epic, so any one can be
picked up alone. And the cost of waiting is linear rather than compounding: these are minutes per
review, on a path that runs several times a week.

## Acceptance criteria

- [x] A completed review work package's recorded state names the posted review as its terminal
      outcome and does not gate on a merge the workflow cannot perform.
- [x] A zero-code-defect review whose actions are all author communication reaches a comment-style
      recommendation without a user override.
- [x] `submit-for-review` reads the pull request's merge state and selects its framing from it.
- [x] A validation artifact produced without a local run names its actual evidence basis.
- [x] Each of W02's five checks exists as a step or a checklist item with a recorded outcome, and
      none is left to reviewer memory.
- [x] Each inventory in W03 has exactly one producer, and no two passes report the same finding class.
- [x] The implement step carries a comment-proportionality bar, and a test statically invalidated by
      its own diff is updated in the same pass.
- [x] Both registers have a writing step; a run that logs a follow-up produces the register.
- [x] Pull-request-body conformance is assessed at intake; the Changes section's form is stated in
      the guide.
- [x] Schema, reference, anchor and binding-fidelity checks stay clean across every item.

Every criterion above is ticked against the definitions rather than the merge record. One is met by a mechanism other than the one it names: the fifth hand-check is a re-read of a document's claims against the recomputed base when a merge-in is detected, rather than an acceptance criterion pinning the document to an implementation commit. Same drift, caught by the run instead of by a criterion someone remembered to write. The closing comment carries the per-criterion evidence.

## Non-goals

- No change to the review-mode gating decisions being made in the decision-integrity epic; the
  suppressed assumption gates and the self-answering provenance gate belong there and are recorded
  there.
- No change to the posted comment's format, which was settled in #346 and is enforced by the
  review-mode resource.
- No new server capability. Every item here is a definition change.
- The host's inability to compile Rust locally is an environment constraint, not a defect to fix; W01
  only requires that an artifact say so honestly.
