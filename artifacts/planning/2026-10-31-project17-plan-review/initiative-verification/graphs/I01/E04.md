## Summary

The server ships a shared group of ready-made operations for querying GitNexus, the code knowledge graph — the tool that answers structural questions like "what calls this" and "what breaks if this changes". Because the group lives under the shared `meta` workflow, any workflow can wire those operations into its activities without keeping a local copy.

Three gaps sit between that group and the workflows it serves, measured against the current head of the workflows corpus (2026-08-02). This epic covers one work item per gap.

## The three gaps

**Most workflows never consult the graph.** Seven of the seventeen workflows bind zero graph operations — `workflow-authoring`, `requirements-refinement`, `prism-update`, `codebase-wiki`, `cicd-pipeline-security-audit`, `work-packages` and `plain-language` — and none is a stub: each carries four to seven activities. An eighth, `remediate-vuln`, binds none either and stays out of scope: it is the stealth-isolated workflow, its single activity is deliberate, and a guard holds it to having no leakage path, so reaching a shared operation group from it is a decision about that isolation rather than an instance of this gap. Two are pointed cases. `workflow-authoring`, whose whole job is structural reasoning about definitions, sends its workers to plain text search for exactly the questions the graph is built to answer. And `codebase-wiki` exists to build a repository wiki while the GitNexus command-line tool has a native wiki generator that builds one straight from the knowledge graph.

**Sibling-repository graphs are unreachable in practice.** A mono-repo contains submodules of related components, and planning decisions are better when a sibling component's graph is visible — "what does the ledger expose here" should not require knowing tool syntax. GitNexus already provides the mechanics: every tool accepts a repository parameter reaching any of the 17 indexed repositories, and repository groups bundle related indexes with a single merged-ranking search, group-wide staleness, and a cross-repository contract registry (a live 13-repository group already exists). But not one of the 17 shared operations mentions any of it — and the shared indexing operation actively forbids the per-submodule indexes the group mechanism depends on.

**The markdown index is paid for and never used.** 909 of the 1,153 files in this repository's index (79%) are workflow definition files, and the graph holds real structure for them: 7,823 heading nodes searchable by text, 1,746 cross-document link edges whose reverse lookup ("which files reference this definition?") is definition-level impact analysis, and stored full text for 776 files. None of it is exposed by any operation, and the one search tool workers are given only ever returns code results — prose questions come back empty. Embeddings cannot close that gap: they are off by default (which is why every repository reports zero), and headings and files are never embedded at any setting. Verdict: the workflows folder stays indexed — the structure is worth the cost once operations expose it.

## The work

**W01 — Bind the graph where the reasoning is structural.** Audit the six zero-reference workflows (plus the three light-touch ones at 1–3 references) and bind the relevant shared operations onto the activities and techniques whose job is structural reasoning — impact analysis, quality review, scope verification, wiki building. Directives go on worker-visible surfaces: activity rules or a technique's rules section, not workflow-level files workers never see.

**W02 — Open the sibling graphs.** Add operations to the shared group that abstract multi-repository reach: discover which graphs exist, target a named sibling repository, search a whole group at once, and check group staleness before trusting an answer. Reconcile the indexing operation's "never index submodules separately" guidance with the group mechanism that requires per-submodule indexes.

**W03 — Put the markdown index to work.** Add operations for the markdown surfaces that exist today: heading search, and reference reverse-lookup for definition impact. State plainly in the group's contract document what the graph cannot answer for prose, so workers route those questions to text search without a wasted turn; sharpen the existing embeddings caveat to "off by default; never covers prose".

## Why now is cheap

The operations group is shared under `meta`, so each new operation is written once and every workflow can resolve it. The evidence is fresh and reproducible from the live index and corpus head. And the cost of waiting compounds: `workflow-authoring` is authoring new workflows right now with no graph in its own hands, so each workflow it produces inherits the gap by default.

## Acceptance criteria

- [x] No substantial workflow binds zero graph operations without a recorded reason; the six named workflows gain bindings on their structural-reasoning activities.
- [x] A worker can discover available graphs, query a named sibling repository, and search a repository group through shared operations, without knowing the underlying tool syntax.
- [x] The indexing operation's submodule guidance no longer contradicts the group mechanism.
- [x] Heading search and reference reverse-lookup are available as shared operations, and the group's contract document states what prose questions the graph cannot answer.
- [x] The decision to keep indexing the workflows folder is recorded with its evidence, closing the exclusion question.

## Non-goals

- No changes to GitNexus itself: no making its search tool return markdown hits, no adding heading embeddings, no enabling embeddings by default. Everything here works against version 1.6.2 as shipped.
- No re-litigating the caveat documentation delivered via #360 beyond the one embeddings sharpening named above.
- No workflow-design changes — it is deprecated (#339); its successor `workflow-authoring` is covered by W01.
