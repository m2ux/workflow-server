**Component:** [skills/work-planner/scripts/board.py](https://github.com/m2ux/workflow-server/blob/workspace/skills/work-planner/scripts/board.py)

## Overview

The board's dependency resolution gains a third answer. An entry it cannot resolve is told apart from one that is simply not delivered yet, carried to the callers that gate a row on it, and reported in the wording the dependency check already uses, so a queue run that meets one names the row and the entry and leaves the row where it stands.

## Problem

- **Three permanent conditions are reported as one temporary one.**
  `met` walks a `Depends on` cell and returns `False` for an entry whose text links no issue, an issue it was not given and a row the named epic does not carry, which is the answer it gives a prerequisite that has not landed. The note it appends to `unresolved` is the only trace, and the queue prints it among its other notes and exits 0.
- **The first failing entry hides the rest.**
  The walk returns on the first entry that is not met, so a cell carrying two unresolvable entries names one of them.

## Proposal

The three conditions above are the ones the epic's criteria name, and they are decided where the cell is read rather than by the caller inspecting `unresolved`. The scene is one cell, several entries, and three callers that each want a different thing from the answer: the board sync's Ready gate, the initiative's whole-epic gate, and the queue's next-epic gate.

- **One resolution value replaces the boolean.**
  `row_delivered`, `issue_delivered` and `met` return `MET`, `UNMET` or `UNRESOLVABLE`. `met` walks every entry rather than returning on the first that is not met, and answers `UNRESOLVABLE` when any entry is, `UNMET` when any is, and `MET` otherwise.
- **The wording says the entry cannot be resolved.**
  Each of the three notes names the row, the entry as written and why it cannot resolve, so the queue's output and the dependency check's read the same way.
- **A row gated on an unresolvable entry is left where it stands.**
  The queue's next-epic gate reports the entry and proposes no status for that epic, rather than moving a Ready epic to Backlog as an unmet prerequisite would. The run exits nonzero, as the dependency check does over the same cell.
- **The board sync keeps its own severity.**
  An unresolvable entry leaves the row short of Ready there as it does today, with the clearer note; the exit code belongs to the queue run the criterion names.
