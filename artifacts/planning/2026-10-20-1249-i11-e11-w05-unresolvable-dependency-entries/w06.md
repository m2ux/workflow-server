**Component:** [skills/work-planner/scripts/deps.py](https://github.com/m2ux/workflow-server/blob/workspace/skills/work-planner/scripts/deps.py)

## Overview

The joins advisory states both ways a planner may answer it, and the dependency check reads the planning record that holds the second one. A pair the record accounts for leaves the report, so what remains is exactly the set named in neither the epic's Joins nor the record.

## Problem

- **The line names one resolution and rewards the wrong one.**
  `E09:W01 and E09:W06 can share a pull request and do not name each other` reads as an instruction to name them. Filling the Joins cell removes the line and asserts a pull request the pair will never share; writing the planning-record entry that properly answers it removes nothing.
- **Nothing reads the record the rule relies on.**
  An empty Joins cell is correct only once a record names the pair and says why, and no run has ever opened that record, so the column passes whether the entry exists or not.

## Proposal

The scene is one advisory section printed per run, over every pair of tasks in an epic where neither depends on the other. The rule behind it offers two resolutions, and only one of them is visible in the output.

- **The line names both resolutions.**
  It states that the pair either shares a pull request and names it in Joins, or is accounted for in the planning record, so a planner reading it knows the choice being made.
- **The check reads the record.**
  A repeatable input names a planning-record artifact. A pair is accounted for when both of its qualified ids appear on one line of such a file, which is the form a joins artifact already takes.
- **What remains is what is unrecorded.**
  Pairs the record accounts for leave the section, so the section names the pairs in neither and nothing else. With no record given, every eligible pair is unaccounted for, which is what the section says today.
