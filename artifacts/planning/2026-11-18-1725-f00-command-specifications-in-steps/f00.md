## Overview

Each command specification stands in the procedure step that runs it. The shared Commands rules, the shared skill-file check and the work-planner, workflow-canon and gitnexus skills drop the Commands section; each specification moves with its text, template, `○` inputs and `●` output unchanged.

## Problem

A specification sat in a `## Commands` section of the file whose procedure ran it, reached from the step by a `ƒ` link, so one step's command lived in a second place. The finding-classifier already holds specifications in its steps, leaving the shared rules describing a layout one skill no longer uses.

## Proposal

- **Shared rules.** `skills/guidelines.md` places a specification in the step that runs it. One several steps run, or a step of another file runs, is an operation of its own in the procedure section of the file owning its subject. No file takes a Commands section.
- **Shared check.** `check_skill_files.py` reads a specification as a heading holding an invocation, reports a Commands section in every file but a guide, and refuses the `specifications` and `keeps_commands` structure keys. The caller-count placement findings go with the section they placed specifications in.
- **Heading model (work-planner).** A specification one step of its own file runs becomes a sub-section of that step's innermost heading; any other is an operation of its own under the file's Operations or Procedure section. Callers keep their `Run` links.
- **List model (workflow-canon).** A specification one list step runs nests in that step's item under a bold label; one several steps or another file run is a sub-section of the Procedure; one only prose names stands under the section naming it.
- **gitnexus.** gitnexus-cli's commands, which no step runs, each become a top-level section of its SKILL.md.
