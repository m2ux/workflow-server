**Component:** config/branches

## Overview

Each long-lived branch — `main`, `workflows` and `docker` beside `workspace` — commits `config/branches`, naming the same long-lived set. An epic base cut from any of them carries the declaration, so an epic sync reads its long-lived names at that base's own commit.

## Problem

Work Planner reads the long-lived branch names from `config/branches` at the commit a run evaluates, and an epic sync evaluates its epic base. Only `workspace` commits the file. An epic base cut from `main`, `workflows` or `docker` holds no declaration, so its sync is unevaluable and its unmerged, draft and review-reference checks are never made. The configuration-authority contract permits no other revision, working tree or branch-name inference as a source.

## Proposal

- **Scene.**
  An epic sync names an epic base cut from `main`, `workflows` or `docker` as its revision and reads `config/branches` at that commit.
- **Each long-lived branch states the set.**
  `config/branches` on `main`, `workflows` and `docker` holds the four lines `workspace` holds: `docker`, `main`, `workflows`, `workspace`, one per line, sorted.
- **Delivery per branch.**
  The three branches share no history, so each takes its own epic base (`i11/e09/main`, `i11/e09/workflows`, `i11/e09/docker`), its own task branch and its own pull request. Each base reaches its long-lived branch through the user's review merge.
- **Product content is untouched.**
  The `docker` build context admits only the files its Dockerfile copies, so the file does not enter the image.

## Work Breakdown
