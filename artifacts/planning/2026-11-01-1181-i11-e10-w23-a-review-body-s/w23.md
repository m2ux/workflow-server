**Component:** workspace:skills/work-planner/scripts/sync.py

## Overview

A review pull request's body is written across many sessions: each unit that merges into the epic base adds its own bullet under Changes and its own pull request under References. Sync Epic measures the References against the merges and reports a difference naming both sets. This task measures the paths Changes names against the base the review fronts, and states the two prose rules that keep the rest of Changes true: no count of the corpus, and a restatement of each standing bullet a later merge makes false.

## Problem

- **The procedure appends and never revises.**
  [Populate Review Body](https://github.com/m2ux/workflow-server/blob/i11/e10/workspace/skills/work-planner/artifacts/pull-request-body.md#populate-review-body) adds a later task merge's change under its area and cites its pull request. No step asks whether the change contradicts a bullet already standing.
- **Only one of the two sections is measured.**
  [`review_references`](https://github.com/m2ux/workflow-server/blob/i11/e10/workspace/skills/work-planner/scripts/sync.py#L389) compares the pull requests a review body cites with those merged into its base. It reads the References section alone, so Changes is unmeasured prose in a body a reviewer is asked to trust.
- **Two bullets of #1321 were false for two units.**
  Its Changes claimed forty-four specifications stood with their procedures and thirty-four remained in the catalog. A census at the branch head reports forty-nine and twenty-nine; #1391 moved five between them and neither number was revisited.
- **A bullet contradicted a reference in the same body.**
  Changes stated that Work Planner's execution conventions were a file of their own, `command-conventions.md`. R11 of the same body stated that they stand in the entry point, which #1360 delivered. The file named belongs to the sibling skill.
- **A count in a body is a measurement with no date.**
  One taken correctly at one merge reads as current at the next, and nothing says where a count may be recorded.

## Proposal

The scene: a session merges its task into an epic base, then runs Review Pull Request, which populates the review body and records epic delivery through Sync Epic.

- **A path a Changes bullet names is measured against the branch.**
  Sync Epic reads each code span in an open review's Changes section that names a file — one whose last segment carries an extension — and looks it up in the tree at the review's head commit, through `--project`. A path with a directory must stand at that path; a bare file name must stand somewhere in the tree. Each one absent is reported on a `changes` line naming the base, the review, the path and the commit. A head commit the checkout does not hold is reported unevaluable.
- **Changes carries no count of the corpus.**
  [Review Body](https://github.com/m2ux/workflow-server/blob/i11/e10/workspace/skills/work-planner/artifacts/pull-request-body.md#review-body) states that a bullet says what the base does, not how many of something it holds; a count belongs in the unit's planning record with the revision that produced it.
- **The merging session restates the bullets its change makes false.**
  Populate Review Body's later-merge step restates each standing bullet the merged change makes false, then adds its own.
