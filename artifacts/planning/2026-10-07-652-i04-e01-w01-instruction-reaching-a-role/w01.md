## Overview

A check that reads the two role bundles the server ships, the prohibitions each role carries, and the registered tool surface, then reports an instruction reaching a role that turns on a call that role is forbidden to make. The defect lives between three files, so no file-at-a-time guard can see it; a hand-written version found two instances on successive audit walks and nothing since, which is what makes it worth holding with a program.

## Problem

- **The defect is in the relationship, not the file.**
  A worker was told to report where the run goes next; the destination lived only in [`get_workflow`](https://github.com/m2ux/workflow-server/blob/daf819e4/meta/techniques/workflow-engine/finalize-activity.md#L73), and the worker's own role file [bars that call](https://github.com/m2ux/workflow-server/blob/daf819e4/meta/techniques/workflow-engine/activity-worker.md#L51). Each statement is defensible alone. Runs failed intermittently and read as model unreliability.
- **A shared contract reaches both roles.**
  `workflow-engine/TECHNIQUE.md` merges into every technique beneath it, so one rule arrives at an orchestrator and a worker alike. Two rules there described what arrives on calls the orchestrator is barred from making, and were moved to the worker's own file by hand.
- **Half the evidence is server code.**
  What each role receives is [`core-ops.ts`](https://github.com/m2ux/workflow-server/blob/1caa9ff5/src/loaders/core-ops.ts#L54-L118); what the tools are is the registrations themselves. A check confined to the definitions cannot see either, and a check reading a maintained list grades a list rather than the server.

## Proposal

Three readings, then a comparison. The bundles come from the server's own lists, resolved to the files each reference is composed from — the technique, plus every contract above it on the loader's ancestor walk — so what the guard reads is what a role receives. The bans come from the sentences in those files that forbid a call, attributed to every role the file reaches. The tool surface comes from the registrations, through the inventory `check-tool-call-shape` already reads.

- **A ban is a negation on a call verb, in the clause that holds the tool.**
  Clause-scoped, so "call `get_resource` once … — do not issue repeated section fetches" bans nothing: the negation and the tool sit in different clauses.
- **Both shapes of instruction are reported alike.**
  An instruction to make the call, and an instruction to take a value from one — which carries no call verb at all ("the workflow graph from `get_workflow`"). The remedy is the same for both: move what only the other role can act on to that role's own technique, or carry the fact the call stood for.
- **A conditional clause states a case, not a duty.**
  A call named only inside one is read neither as banned nor as an instruction to make it. A sentence that OPENS by naming a case is conditional throughout; a case named mid-sentence governs its own clause. Without this, "Until a stub names one … never issue its `get_activity` on your own initiative" would ban the call every worker makes on every activity, and condemn the worker's own role file for naming it.
- **`before` and `after` are not in the set.**
  Both are prepositional here — "Before executing any step, confirm …" names an occasion, not a case, and the duty is owed on every step.
- **A bundle reference the corpus cannot answer is a finding.**
  Surface the guard did not read is reported rather than passed over silently.
