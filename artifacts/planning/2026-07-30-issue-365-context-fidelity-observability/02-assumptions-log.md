## Open Assumptions

### DP-7: Does closing S2 cross into the corpus?
**Assumption:** S2 is closeable server-side — diff the planning folder against the accumulated manifest at `next_activity` and surface undeclared files to the orchestrator — without changing the corpus persist step.  
**Decision space:** (a) **Server surfaces, corpus honours** — add the diff plus a warning channel server-side and amend `commit-and-persist.md` to stage only declared files, or to stop on an unresolved undeclared set. Closes the defect end to end, but spans two submodules and reaches into what #338 calls the corpus half. (b) **Server-side only** — ship the diff and the surfacing, accept that committing behaviour is unchanged, and file the corpus change as a follow-up. Keeps this package inside one repo and inside the issue's literal checkboxes, but leaves the demonstrated #141 failure still reachable. (c) **Server blocks** — refuse to advance at `next_activity` until every undeclared file is declared or explicitly dismissed. Strongest guarantee and needs no corpus change, but converts an advisory into a hard gate that can strand a run, and no existing `next_activity` warning behaves that way.  
**Why not code-resolvable:** the code tells us where the staging happens; it cannot tell us whether this package's scope crosses the server/corpus submodule boundary, nor whether a hard gate is operationally acceptable. Both are the user's calls.  
**Technical context:** `artifacts_produced` has zero implementation in `src/` — its only definition is `finalize-activity.md`'s envelope contract. `composeActivityArtifacts` (`workflow-tools.ts:98-137`) already synthesizes the *declared* per-activity artifact contract from step techniques' `#### artifact` names, so the comparison target exists. `next_activity` currently reduces both manifests to advisory warnings (`:467-490`). Session state has no accumulated-manifest field (`session.schema.ts:57-165`) and there is no artifact event type in `HistoryEventTypeSchema`, so persisting the accumulation is a deliberate schema addition under every option. The corpus is a separate submodule, empty in this worktree.  
**Agent's position:** (a), scoped so the server half is complete and self-contained and the corpus amendment is a single narrow edit to `commit-and-persist.md` under `workflow-canon`. (b) leaves the exact failure the item exists to prevent still reachable, which makes the item's success criterion untestable end to end; (c) is a larger behavioural change than the issue asks for and can strand a run on a false positive.  
**Reversibility:** path-committing — the choice determines whether the session schema carries an accumulated manifest and whether the corpus contract changes in this package.

### DP-9: Who consumes the cost estimate, and where do prices come from?
**Assumption:** a cost figure returned by `inspect_session view: usage` satisfies S3's third checkbox, with prices hard-coded in the server.  
**Decision space:** (a) **Tool output only, hard-coded prices** — smallest change, no new config surface; but prices rot silently and no artifact carries the number, so the figure is invisible to anyone not calling the tool. (b) **Tool output, prices from config** — prices move to `src/config.ts` or an env-supplied table, so staleness is operable rather than baked in; slightly more surface, and someone must own the table. (c) **Tool output plus the planning-artifact record** — the aggregate reaches the work package's token-usage artifact, which is what makes it visible to a human reader; but writing that record is explicitly #338 W3, so this crosses the same server/corpus boundary as DP-7.  
**Why not code-resolvable:** the code can produce any of the three. Which one counts as "cost estimate derived from the aggregate" depends on who is meant to read it and who owns price currency — neither is stated anywhere in #365 or #232.  
**Technical context:** `usageSchema` is `z.record(z.unknown())` (`workflow-tools.ts:55`), so the recorded rows have no normalized token fields to price yet — a shape decision precedes the cost decision. `projectUsage` (`:256-260`) is deliberately excluded from `projectSummary`, so today the rows surface only under the explicit view. The `inspect_session` Python oracle (`tests/fixtures/inspect-session/inspect_session.py`) implements no `usage` view, so this projection is currently unconstrained by parity — extending it is a free choice now and a parity obligation later. Every delivery event already carries `chars`, giving a server-measured cross-check against harness-reported tokens.  
**Agent's position:** (b) for this package — normalize the usage shape, aggregate, price from config, and stop at the tool boundary. It satisfies the checkbox with an operable price source and leaves (c) to #338 W3 where the epic already puts it. Pairs naturally with whatever DP-7 decides, since both turn on the same boundary.  
**Reversibility:** easily-reversible for the price source; path-committing for the normalized usage shape, which the aggregate, the cost math and any later artifact all read.

### DP-10: Is S4 still the item the user scoped in?
**Assumption:** S4 stays in scope as an "M" item, as the user's scoping message had it.  
**Decision space:** (a) **Measure and report only** — add the fresh-mode benchmark arm, report the residual share honestly, change no dedup code, and let the measurement decide a later item. Smallest, keeps the frozen baseline intact, and directly satisfies the issue's "measure against the fresh-mode gate" instruction; delivers no token saving in this package. (b) **Measure, then change granularity here** — add `provenance_note` to `DEDUP_BLOCKS` and split the invariant `note` from the variant `items` in `inherited_inputs` / `inherited_outputs` so the preamble collapses independently. Captures the actual prize, but redesigns `dedupTechniqueBlocks`, moves the frozen baseline, and touches the wire shape techniques are delivered in. (c) **Defer S4 entirely** — land S2, S3 and S5, and re-file S4 against the reframing. Honest about the item having changed shape, but drops the one item with a direct token-cost payoff.  
**Why not code-resolvable:** the measurement is code-resolvable and is S4's own deliverable; whether a redesign discovered *after* scoping belongs inside the agreed scope is not. The user scoped S4 against "measure what remains", which DP-4 shows is not what the item is.  
**Technical context:** `DEDUP_BLOCKS` (`delivery.ts:90`) covers `inherited_inputs`, `inherited_outputs`, `rules`. `dedupTechniqueBlocks` (`:104-123`) hashes each block whole over `stringifyForResponse({[block]: value})`, which is what makes a mixed invariant/variant block fail to collapse. `provenance_note` is emitted by `projectTechnique` (`technique-loader.ts:39`) and is not a dedup candidate. Option (b) changes what a worker receives, so `tests/reference-delivery.test.ts:751-933`, `hybrid-bundling.test.ts` and the frozen `scripts/fixtures/token-benchmark-a0-reference.json` all move together.  
**Agent's position:** (a) then a gated (b) — take the measurement first inside this package, and let the measured residual decide whether the granularity change is taken here or re-filed. That honours the issue's own instruction to measure against the fresh-mode gate, keeps the user's agreed sizing intact unless the number justifies more, and avoids committing to a wire-shape change on n=1 evidence.  
**Reversibility:** (a) easily-reversible; (b) path-committing — it changes the delivered technique shape and rebases the benchmark baseline.
