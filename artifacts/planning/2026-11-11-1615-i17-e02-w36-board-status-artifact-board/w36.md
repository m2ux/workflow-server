## Overview

Board Status owns the proposed board-change contract and the operations that derive and validate it; Board Delivery and Hot-fix obtain status decisions through those operations with unchanged outcomes, and Board Delivery names no kind of work. The three files change together in one pull request so moved contracts, caller links and roles stay valid. Covers AC6, AC7 and AC8.

## Board Status artifact

### Overview

Board Status owns the proposed board-change contract and its derivation and validation.

### Problem

Board Delivery's Status Changes guidance combines board-state derivation and write jurisdiction with subject-specific lifecycle policy, leaving that derived subject without its own artifact home.

### Proposal

Create the Board Status artifact from the completed ownership audit. Consume supplied state and subject-owned lifecycle decisions through explicit data contracts, and provide proposed changes or blockers. Reuse existing computation/rendering capabilities where adequate. Board Delivery owns evidence gathering, application and readback; the shared artifact contains no issue-kind switch or lifecycle coordination sequence.

### Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | Current Status Changes guidance, its pinned historical source, all consumers, existing script capabilities and the audit's clause-to-owner map. |
| Plan | Define issue/item identity, current/desired status or membership action, write jurisdiction, reason and blockers; identify substantive shared derivation/validation capabilities. |
| Implementation | Create board-status.md with operations, command specifications before Fields, concrete data shapes and context linked at use. |
| Review | Each rule has one owning subject; capabilities have real callers, and only shared ordered changes across artifacts qualify for a separately justified protocol. |
| Test | Within the joined extraction, verify actual decisions/calls and blocked writes for closure, membership, review, reservation and dependency cases; run document/checkout/role checks and the full status/board/delivery matrix. |

## Board Delivery caller

### Overview

Board Delivery applies proposed Board Status changes and confirms saved state.

### Problem

Its shared Status Changes guidance mixes the derived board-change subject with the operations that acquire evidence, apply calls and confirm writes.

### Proposal

Map every current Status Changes clause to its audit-selected owner and consume Board Status through its public capabilities. Keep evidence gathering, application, retry/readback and convergence in Board Delivery. Preserve review-evidence and write-scope gates and the existing result continuation. Retire the former Status Changes anchor with all consumers updated in the same joined change.

### Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | All current Status Changes callers, commands and policy clauses, including review and dispatch jurisdictions. |
| Plan | Map each clause to a subject owner and each consumer to the supplied decision, transformation or proposed-change contract it actually needs. |
| Implementation | Route board-delivery.md through the extracted capabilities; keep caller selections and continuation, command-owned I/O, concrete Fields and links at use. |
| Review | No forwarding policy field, duplicated decision, implicit I/O or copied lifecycle sequence remains; actual board writes and confirmation retain their owner. |
| Test | In the joined extraction, run actual caller/checkout/contract readers and status/board/delivery tests, including review refusal, absent-item, subsequent-pass, retry and saved-state confirmation cases. |

## Hot-fix caller

### Overview

Hot-fix supplies its lifecycle decisions to the shared board-change contract.

### Problem

Its Board Status guidance cites Board Delivery's shared Status Changes policy, coupling subject-owned lifecycle conditions to the current placement of generic board-change derivation.

### Proposal

Keep hot-fix-specific lifecycle conditions with Hot-fix and consume the extracted Board Status result and capabilities from the settlement operation. Fields describe actual data; policy remains Guidance or owning command/operation conditions. No issue-lifecycle protocol substitutes for the status derivation, and no shared file enumerates hot-fix cases.

### Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | The current closure/status guidance reference, settlement operation and existing hot-fix/status consumers and regressions. |
| Plan | Separate subject lifecycle decisions from proposed board changes and from the steps applying and confirming them. |
| Implementation | Revise hotfix.md contract links and performing calls atomically with Board Status and Board Delivery; preserve current role tags and context selected through links. |
| Review | Every condition has one owner, data fields contain no hidden operation, and the former Board Delivery Status Changes target is absent. |
| Test | In the joined extraction, verify completed and other closure, draft/ready/held state, malformed or missing evidence and status write/readback outcomes with existing hot-fix, board, queue and status fixtures. |
