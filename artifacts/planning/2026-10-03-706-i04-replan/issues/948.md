## Overview

This epic states each value's shape where a check reads it: the fields one entry of a list carries, and the type of each value an activity's contract declares. The checks that hold a step's reads and a contract's types against those declarations exist. The declarations they read are missing or wrong.

## Problem

- **Entry shapes.**
  The binding check holds a step's read of a list entry against the entry the operation declares, and only where that declaration exists. Seven gitnexus operations declare [`#### entry`](https://github.com/m2ux/workflow-server/blob/6355c392/corpus/support/gitnexus/techniques/list-group-members.md). A list-returning operation that describes its entry in prose leaves a wrong read unmeasured.
- **Declared types.**
  [`declared-type-mismatch` holds at 12](https://github.com/m2ux/workflow-server/blob/ab680d9d/guards/check-operation-contract.ts#L30): a contract calls a value a scalar where the technique filling it publishes members.
- **The contract check stands outside the sweep.**
  `guards/check-operation-contract.ts` is not an entry in the guard registry. Enrolling it while the twelve stand would take a hard-zero sweep red.

## Proposal

- **Entry declarations from live responses.**
  Each list-returning code-graph operation with a fixed entry shape declares the fields one entry carries. The field names come from calling the operation against an indexed graph. The prose stays, saying what each field means. An operation that returns whatever its query asks for has no fixed shape, and one that answers with a map keyed by member name is not a list.
- **Each value settled against the operation that fills it.**
  Where the operation publishes members, the contract declares the structure. Where the value is one string and the operation over-declares, the operation changes. The direction is decided per value.
- **The contract check joins the standard sweep** once every value is settled, and its exemption note goes from the guard.
