## Overview

A step can be gated two ways. It can carry an inline boolean expression, `when`, that the executing agent evaluates before deciding whether to run the step, or a structured `condition` that, on a checkpoint, also lets the agent activate the checkpoint and then dismiss it. Both are boolean tests over the same bag of declared variables, both are evaluated by the agent rather than by the server, and both end at the same place when they are false. This epic retires the structured condition, so a step states its gate once.

## Problem

- **Two fields do one job.**
  `when` gates any step. `condition` gates a step and, on a checkpoint, permits a dismissal: the agent activates the checkpoint and then clears it through `respond_checkpoint` with `condition_not_met` ([activity.schema.ts](https://github.com/m2ux/workflow-server/blob/ab680d9d/src/schema/activity.schema.ts#L59-L64)).
- **The inline form says everything the structured form does.**
  The inline grammar covers comparison, negation, conjunction, disjunction, parentheses with stated precedence, and the truthiness of a bare name. The structured form covers a comparison and the three connectives.
- **They route to the same exit.**
  An activity's default exit is the outcome when no `when` matched and no checkpoint option chose an exit, and the definition names a condition-dismissed checkpoint as one of the cases it covers.
- **The one real difference is an unverifiable record.**
  A dismissal makes a round trip through the server and leaves a checkpoint response under the sentinel option `__condition_not_met__`. The server checks only that the checkpoint has a `condition` field, and never evaluates gates.
- **A routine step's gate is `when` alone.**
  A `condition` on a routine reference would make every checkpoint in the body dismissible ([activity.schema.ts](https://github.com/m2ux/workflow-server/blob/ab680d9d/src/schema/activity.schema.ts#L114-L116)).
- **The population.**
  64 of 118 checkpoint steps carry a structured condition. 86 `condition:` lines sit on activity and routine steps, measured on `workflows` at `6355c392`.

## Proposal

- **Survey every site.**
  For each step carrying a structured condition, establish whether its dismissal record is load-bearing for anything downstream, or whether the test is a gate written in the second form. A site whose test can never be false is removed, and the measurement that showed it is recorded per site.
- **Convert the gates.**
  Each surviving structured condition becomes the equivalent `when` expression on the same step. The workflow-engine techniques that teach dismissal drop it in the same change.
- **Remove the field and the resolution it enabled.**
  `condition` leaves the step schemas, so the loader rejects it. The dismissal mode leaves `respond_checkpoint`, with its sentinel option and its `dismissed` response field. Every reader of a step's gate reads `when` alone.
- **A shared body is a routine.**
  A routine reference step's `when` is conjoined onto every step the routine produces, as [the shared checkpoint body](https://github.com/m2ux/workflow-server/issues/738) defines, so a shared checkpoint body declares its gate on the routine.
- **What stays structured.**
  The structured condition type remains where it is not a step gate: a loop's `continueWhile` and `breakCondition`, and an action's `condition`. Retiring those belongs to [the loop and action conditions](https://github.com/m2ux/workflow-server/issues/529). [The formal specification](https://github.com/m2ux/workflow-server/issues/937) specifies `when` as the gate language.

## Acceptance Criteria

- [ ] **AC1.** Every step carrying a structured condition has a recorded disposition, converted or removed.
- [ ] **AC2.** Every converted gate is a `when` expression on the same step that holds exactly when the structured condition it replaces held.
- [ ] **AC3.** No activity or routine file in the corpus carries a structured `condition` on a step.
- [ ] **AC4.** No technique or resource in the corpus describes dismissing a checkpoint or says which gate field confers dismissal.
- [ ] **AC5.** The loader rejects a step carrying `condition`, and the published schemas carry no such field.
- [ ] **AC6.** `respond_checkpoint` accepts exactly one of `option_id` or `auto_advance`.
- [ ] **AC7.** No schema description, tool description or loader message in the server describes dismissing a checkpoint or says which gate field confers dismissal.
- [ ] **AC8.** Every reader of a step's gate reads `when` alone: the validator, the guards, gate liveness and the end-to-end walker.
- [ ] **AC9.** Each checkpoint site records whether anything downstream reads its dismissal record.
- [ ] **AC10.** Each removed site records the measurement showing its test could not be false.
- [ ] **AC11.** No `condition_not_met` input, `__condition_not_met__` record or `dismissed` response field exists.
- [ ] **AC12.** A differential test evaluates each converted gate and its structured original over the variables the site reads, and finds them agreeing on every assignment.
