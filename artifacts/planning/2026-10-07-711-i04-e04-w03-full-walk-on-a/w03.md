## Overview

A trigger that fires when work lands measures the weeks that have work in them. A quiet week has no event at all, so the roster goes unwalked for as long as the repository stays still, and the drift surfaces on whichever pull request happens to touch coverage next. This task gives the workflow that starts the full walk a weekly schedule, with a stated cadence and a reason for it, so the roster is walked whether or not anything was pushed.

## Problem

- **Every trigger the walk has needs a person.**
  [coverage.yml](https://github.com/m2ux/workflow-server/blob/860e107b/.github/workflows/coverage.yml#L13-L15) is triggered by `pull_request` and `workflow_dispatch`. Both wait on somebody opening a pull request or clicking Run workflow, so a week in which neither happens leaves the roster unmeasured.
- **A cron written into that file would never fire.**
  GitHub raises a `schedule` event only for a workflow file on the repository's default branch, which is `main`. `coverage.yml` is a file of the corpus branch. A `schedule:` block added to it reads as a schedule in review and is never a run.
- **The walk is the only thing that measures the roster.**
  It allows [seventy minutes](https://github.com/m2ux/workflow-server/blob/860e107b/.github/workflows/coverage.yml#L28) and its subject is every workflow the roster names, so nothing cheaper stands in for it. An unwalked week is an unmeasured roster, not a roster measured less precisely.

## Proposal

The schedule has to sit on the default branch, because that is the only branch GitHub raises a `schedule` event for. The workflow of that branch that starts the full walk is where it goes.

- **The schedule starts the same dispatch the push trigger starts.**
  `.github/workflows/coverage-walk.yml` takes a `schedule:` block beside its existing triggers. The job it runs is unchanged, so the walk is unchanged: the schedule decides when, and `coverage.yml` still decides what.
- **Weekly, at 03:17 UTC on Monday.** `cron: '17 3 * * 1'`.
  - **A week is the longest the roster should go unwalked.**
    Pushes already cover the weeks that have work in them, so the only gap a schedule has to close is a quiet one, and a quiet week is the unit the repository goes quiet in. A daily cron would spend seven seventy-minute walks a week to shorten the worst-case gap from seven days to one, on a corpus that routinely sits still for several days at a time.
  - **Monday puts the result in front of the week that follows it.**
    A walk that finishes before work starts is read by the people about to change the corpus, rather than landing into a weekend nobody reads.
  - **An off-peak hour and an off-the-hour minute.**
    GitHub delays and drops scheduled runs when its queues are loaded, and the top of the hour is the most contended minute of all. 03:17 avoids both, at the cost of nothing.
- **A scheduled run walks the long-lived corpus branch.**
  GitHub runs a scheduled workflow on the default branch, so the ref the job resolves is the default `workflows`, not an initiative's integration branch. That is the tree the schedule is for: an initiative's half is walked by the pushes that land on it.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | Establish that a `schedule` event is raised only for a workflow file on the repository's default branch, and settle the cadence against what the walk costs and how long the corpus sits still. |
| Implementation | Add the `schedule:` block with the weekly cron to `.github/workflows/coverage-walk.yml`, and record the cadence and its reason in the file's header comment. |
| Review | Confirm the cron parses as the intended day and time, that the scheduled path resolves the long-lived corpus branch, and that the walk's own workflow is unchanged. |
| Test | `tests/coverage-walk-triggers.test.ts` parses the file as workflow YAML and reads its configuration: `on.schedule` carries exactly one entry, its cron is the weekly Monday expression, and the scheduled path runs the same dispatch job as every other trigger. `npm run test:ci` is the suite that runs it, and it is what engine CI runs. A parse and a configuration read are the whole of what is available before the cron has ever fired; neither is evidence that a schedule starts a walk. That evidence is the run itself, on the first Monday after merge. |
