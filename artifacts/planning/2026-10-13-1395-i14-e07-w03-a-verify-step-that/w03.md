# W03 — A Verify Step That Reports Without Gating

## Overview

`verify.yml` runs every check of engine CI in one job, so the first failing step cancels the rest. The definitions-call-the-tools check sits ahead of the suite and the delivery-cost gate and reads an input that moves independently of the change under review, which lets corpus drift blank the only results a reviewer of that change has. This task gives that check a job of its own, so it reports its own verdict and the suite and the gate run whatever it concludes.

## Problem

- **One step decides whether the suite runs.**
  [`verify.yml`](https://github.com/m2ux/workflow-server/blob/efea02fa/.github/workflows/verify.yml#L84-L101) runs `guards/check-tool-call-shape.ts`, then `npm run test:ci`, then the delivery-cost gate, as three steps of one job. A failing step ends the job, so a red guard leaves both unrun and the pull request carries no test result at all.
- **The check's other input is not the change under review.**
  The guard reads the corpus tip against the tools this source registers. A pull request against `main` is paired with the `workflows` tip and one against `iNN/main` with that initiative's corpus, so either side moves the verdict without the change touching it. An undeclared `start_session` argument in `bootstrap-protocol.md` held the suite and the gate skipped on every pull request from 2026-10-07 to 2026-10-09.
- **A skipped step reports nothing.**
  GitHub records a step the job never reached as skipped under a job whose single check has already failed, so the checks list carries one red entry and no statement about the suite or the gate.

## Proposal

Engine CI asks two questions of a change, and they have different second inputs. Whether the engine still typechecks, passes its suite and holds its delivery cost is a question about this tree. Whether the corpus calls the tools this source registers is a question about the pair, and the pair moves on its own. A job is the unit GitHub reports a verdict for, so a question that deserves its own verdict needs a job.

- **The guard is a job.**
  `tool-call-shape` resolves and checks out the paired definitions for itself and runs `guards/check-tool-call-shape.ts` against them. Its pass or fail is a check of its own on the pull request.
- **The suite and the gate do not wait on it.**
  `verify` keeps the typecheck, the schema check, the suite and the delivery-cost gate, and names no `needs`, so the two jobs start together and each concludes on its own subject.
- **Each job resolves its own pairing.**
  Both jobs repeat the pairing step and the definitions checkout. A third job holding the resolution as an output would put both of them behind it, which is the coupling this task removes.
- **The documentation states two jobs.**
  [`docs/development.md`](https://github.com/m2ux/workflow-server/blob/efea02fa/docs/development.md#L120) describes engine CI as one sequence of steps. It names the two jobs and what each concludes on.

## The instrument

A run with the definitions-call-the-tools check red needs a corpus the check concludes failure on, and a branch pair that points engine CI at it. Three branches carry it, and they are deleted once the two runs are recorded:

- `i99/workflows` — the `workflows` tip at `22434a13`, plus `corpus/meta/resources/unregistered-call-specimen.md`, which describes `resume_checkpoint { session_index: 0, unregistered_argument: "x" }`. The pairing step reads the first segment of the base, so a base under `i99/` pairs with this corpus and no other branch's CI reaches it.
- `i99/e00/main` — the `i14/e07/main` tip at `efea02fa`, which carries the one-job workflow. The push that creates it is the control run.
- `i99/e00/w01-two-job-verify` — this branch's head at `000c157f`, which carries the two-job workflow. Pull request [#1412](https://github.com/m2ux/workflow-server/pull/1412) opens it against `i99/e00/main`, and that run is the observation.

The specimen is an argument the tool does not declare rather than a tool name the engine does not register. A span naming an unregistered tool belongs to some other schema — a harness or knowledge-base tool the corpus also describes — and the guard passes over it by design, so a corpus naming one concludes success. An undeclared argument is what the guard reports, and it is the shape of the `start_session` drift that held the suite and the gate skipped for three days.

**AC3 does not hold, and this task's change does not reach it.** What the measurement settles:

- **Three of three integration branches conclude failure, and two of those failures are the suite.**
  `i08/main` and `i10/main` fail at `Run the test suite against the definitions`, against corpora their own initiatives pin. A verdict reported per job does not change a suite that does not pass; the subject is the state of those branches.
- **One of them fails at the definitions-call-the-tools step.**
  `i09/main` reproduces the drift this epic names, 12 days after its last commit. The two-job workflow would report it as a check of its own there too, and that check would still be red, so the branch would still not conclude success.
- **The two workflows do not run on the same branches.**
  `verify.yml` has no run on `workflows`, and `verify-corpus.yml` is not on `main` or on any `iNN/main`. A criterion asking both workflows to conclude success on one set of branches has, for each branch, only one of the two to read.
- **The guard sweep's own latest run is green where it exists.**
  The corpus tip at `22434a13` sweeps clean. It took a hand dispatch to learn that: the sweep declares no `push` trigger, so the tip a merge produces is never graded on the commit that produced it.

AC3's subject is the state of three integration branches and the trigger set of two workflows. Neither is reachable from the job split this task delivers, and inventing that scope here would put work on another initiative's branches under this epic's pull request.
