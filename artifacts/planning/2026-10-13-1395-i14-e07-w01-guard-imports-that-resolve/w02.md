# W02 — A Walk Test Reading a Path That Resolves

## Overview

The walk-protocol test reads its declarations off the corpus checkout, and the guard that exists for a pin the corpus cannot resolve passes over the spelling that read takes. This task makes the guard reach a pin spelled from the corpus root, holds every such pin to a file the corpus holds, and points the two that had rotted at the files that succeed them.

## Problem

- **A retired pin reached the suite as a file-system error.**
  `tests/e2e/walk-protocol.test.ts` read `corpus/midnight-system-review/activities/01-scope-intake.yaml`. The public corpus holds no such workflow, so the read threw and the file errored before the assertion ran. [`a2811492`](https://github.com/m2ux/workflow-server/commit/a2811492) points the check at the five activities the corpus has.
- **The guard never saw the pin.**
  [`check-pinned-corpus-paths.ts`](https://github.com/m2ux/workflow-server/blob/ec05e7f6/guards/check-pinned-corpus-paths.ts#L41-L44) matched a quoted path whose *first* segment is the workflow. A suite reading through `liveCorpusRoot()` spells the corpus checkout's own layout, `corpus/<workflow>/…`, and no such literal matched at all.
- **The workflow-segment exemption would have hidden it anyway.**
  A literal whose workflow segment names no workflow was counted a synthetic fixture id and skipped. A workflow the corpus retires leaves a pin naming no workflow, which is exactly the rot the guard exists for.
- **A multi-file fixture lost its exemption after the first path.**
  The fixture-write exemption looked one line above the literal, so of a `withCorpus({…})` map only the first key was read as a write.
- **Two pins had already rotted unseen.**
  Measured 2026-10-13 against the corpus at `22434a13`: `tests/coverage-scope.test.ts` named `corpus/work-package/activities/01-create-work-package.yaml`, and `tests/corpus-index.test.ts` named `security/audits/prism/activities/patterns/01-pass.yaml`. Neither resolves.

## Proposal

A pin is spelled from whichever root the file reading it resolves against, and the construct directory — `techniques`, `activities`, `resources` — is what locates the workflow segment inside the literal. Everything ahead of it is the root the literal is addressed at, and what the guard reports is the literal as written.

- **The scan reaches a pin behind leading directories.**
  Leading segments are taken lazily, so the first segment fronting a construct directory is read as the workflow and `corpus/meta/techniques/fan/enter-fan.md` names `meta`.
- **A pin spelled from the corpus root resolves whole or is reported.**
  Where the leading segments name a directory the corpus checkout holds, the literal is addressed at that checkout, and the workflow segment buys no exemption. A retired workflow is then a finding rather than a skip.
- **A fixture write is a fixture write for every path it carries.**
  The exemption spans an authoring call's argument list rather than the line above the literal, so every key of a map of path to body is read as the write it is. `withCorpus` joins the calls that author a tree.
- **Each rotted pin names the file that succeeds it.**
  `tests/coverage-scope.test.ts` names `01-start-work-package.yaml`, and `tests/corpus-index.test.ts` names `meta/activities/patterns/02-supervisor.yaml` — a nested activity path the corpus holds, which is the shape that check is about.
