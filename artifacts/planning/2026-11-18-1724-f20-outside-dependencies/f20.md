## Overview

A `Depends on` entry on another repository's issue resolves against that repository. This hot-fix has a linked entry resolve by its link, an unlinked number by the row's own repository, and an entry whose number and link disagree reported by both the dependency check and the board reader. Work Breakdown states the cross-repository form.

## Problem

The board reader resolved a `#750` entry as an issue of the row's own repository whatever its link named, so a cross-repository edge written that way waited on the wrong issue and could read as met. The dependency check took any `#750` as external and checked nothing about it.

## Proposal

- **Board reader.** `Board.met` resolves a `#N` entry to the issue its link names, in whichever repository. An unlinked `#N` names issue N of the row's repository. A `#N` whose link names another issue of that repository, or names no issue, cannot resolve. An issue link may carry a trailing `/`, fragment or query.
- **Dependency check.** `deps.py` reads each Depends on cell with its links kept and reports a `#N` entry whose link names no issue or carries another number, on task rows and initiative rows. It has no home repository, so it applies that rule in every repository: the authoring form is a link whose text is the linked issue's number.
- **Work Breakdown.** `epic-issue-body.md` states that a dependency on another repository's issue is a link to that issue, and that an unlinked `#750` names an issue of the row's own repository.
