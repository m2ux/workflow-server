## Overview

Nothing walks the full coverage roster when work lands. A pull request walks only the workflows its diff can move, and skips altogether when that set is empty, so the roster's unconditional measurement has no run of its own. This task puts a workflow on the repository's default branch that starts the full walk on every push to it, against the corpus the pushed engine serves.

## Problem

- **The full walk runs only when somebody asks for it.**
  [coverage.yml](https://github.com/m2ux/workflow-server/blob/860e107b/.github/workflows/coverage.yml#L13-L15) is triggered by `pull_request` and `workflow_dispatch`. A pull request walks the scope its diff reaches and no more, and a dispatch is somebody remembering.
- **A push trigger written into that file would not fire.**
  GitHub reads a push's workflows from the branch pushed to. `coverage.yml` is a file of the corpus branch, and the repository's default branch, `main`, carries [three workflow files](https://github.com/m2ux/workflow-server/tree/1caa9ff5/.github/workflows) that do not include it. A merge to the default branch therefore reaches no coverage workflow at all.
- **The default branch is where coverage moves without a definition moving.**
  The walker, the policies and the coverage helpers are files of that branch, which is why the corpus job already treats [a change to any of the three](https://github.com/m2ux/workflow-server/blob/860e107b/.github/workflows/coverage.yml#L101-L105) as cause to walk the whole roster. A merge there can change what every walk reaches while no definition changed, and nothing measures it.

## Proposal

The walk already exists and already has a full-roster mode. What is missing is an event that reaches it. A workflow on the default branch supplies that event and nothing else.

- **A workflow of the default branch carries the push trigger.**
  `.github/workflows/coverage-walk.yml` is a file of this tree, so a push to `main`, or to an initiative's `iNN/main`, runs it. The branch list follows [verify.yml](https://github.com/m2ux/workflow-server/blob/1caa9ff5/.github/workflows/verify.yml#L16-L17), so engine work landing on an integration branch is measured the same way as engine work landing on the default branch.
- **Its one step raises a dispatch.**
  `gh workflow run coverage.yml` against the corpus branch. The walk step of that workflow already [runs for every event that is not a pull request](https://github.com/m2ux/workflow-server/blob/860e107b/.github/workflows/coverage.yml#L120-L125), with no scope set, which is the full roster. What the walk measures is untouched.
- **The job needs one permission and no credential.**
  `workflow_dispatch` is one of the two events a job's own `GITHUB_TOKEN` may raise that still start a run, so `actions: write` is enough.
- **The job adds no action.**
  Every step is a `run:` step, so the file introduces no `uses:` reference to pin. An action added to it later takes a full-length commit SHA with its tag as a trailing comment, the form [docker-publish.yml](https://github.com/m2ux/workflow-server/blob/1caa9ff5/.github/workflows/docker-publish.yml#L136-L138) already uses.
- **It walks the corpus the pushed engine serves.**
  The dispatched ref is resolved the way [verify.yml resolves its pairing](https://github.com/m2ux/workflow-server/blob/1caa9ff5/.github/workflows/verify.yml#L48-L61): `iNN/workflows` for a push to `iNN/main` where that branch exists, and `workflows` otherwise. Dispatching a fixed ref would walk one half of an initiative against the other half's counterpart.

## Work Breakdown

| Part | Description |
| --- | --- |
| Analysis | Read where `coverage.yml` lives, which branch a push reaches, and what its walk step does when the event is not a pull request. |
| Implementation | Add `.github/workflows/coverage-walk.yml` with a `push` trigger on the default branch and the integration branches, a step resolving the corpus branch to walk, and a step dispatching `coverage.yml` against it. |
| Review | Confirm the walk's own workflow is unchanged, that the file adds no action, and that the job's permissions are the narrowest that let it dispatch. |
| Test | `tests/coverage-walk-triggers.test.ts` parses the new file as workflow YAML and reads its configuration: `on.push.branches` names the default branch, the dispatch names `coverage.yml`, every step is a `run:` step so there is no action to pin, and no step runs the walk itself. `tests/guard-registry.test.ts` takes the new file into its listing of the engine's workflow files. `npm run test:ci` is the suite that runs both, and it is what engine CI runs. A parse and a configuration read are the whole of what is available before the trigger has ever fired; neither is evidence that a push starts a walk. That evidence is the run itself, on the first push to the default branch after merge. |
