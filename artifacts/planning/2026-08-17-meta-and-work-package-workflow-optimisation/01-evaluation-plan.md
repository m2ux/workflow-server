# Evaluation Plan: workflow-server

## 1. Target Overview

- **Target type:** mixed
- **Target path:** `/home/mike1/projects/dev/workflow-server`
- **Summary:** A TypeScript MCP server that serves a corpus of workflow definitions written in markdown and YAML. The subject of this evaluation is two of the 21 definition trees — `meta`, the session lifecycle orchestrator, and `work-package`, the 15-activity engineering delivery workflow — assessed for how much time and token cost each run spends. `src/` and `scripts/` are in scope as the surface where mechanisation could land: the server registers 16 MCP tools and every one is session control-plane (`get_activity`, `yield_checkpoint`, `record_usage` and kin), so deterministic domain work in these workflows currently has nowhere to live except agent-executed prose.

**Structure inventory**

| Section / Module | Size |
|------------------|------|
| `workflows/meta` — definitions | 171 files (160 md, 11 yaml), 290 KB, ~34,900 words |
| `workflows/meta` — composition | 5 activities, 150 technique files across 9 groups, 7 resources, 5 checkpoints |
| `workflows/work-package` — definitions | 168 files (152 md), 617 KB, ~66,300 words |
| `workflows/work-package` — composition | 15 activities, 112 technique files across 16 groups, 37 resources, 44 checkpoints |
| `src/` — server | 12,343 LOC TypeScript: utils 4,000, tools 2,821, loaders 2,359, schema 1,621, transports 224, middleware 90, resources 66 |
| `src/tools` — MCP surface | 16 registered tools (14 workflow, 2 resource), all session control-plane |
| `scripts/` | 44 scripts, 15,257 LOC, including 26 `check-*.ts` guards |
| `tests/` | 72 test files, 18,420 LOC |

**Key topics:** No domain-computation tool exists on the server, so procedures such as repo/component/issue/PR coordinate resolution run as agent prose. Checkpoint density is uneven — 10 gates in `01-start-work-package`, 9 in `13-submit-for-review`, 0 in `11-validate` and `14-complete`. Individual bodies run large: `dispatch-activity.md` 10.0 KB, `review-summary.md` 9.6 KB, `review-assumptions/reconcile.md` 9.3 KB, resources up to `review-mode.md` 21.6 KB and `codebase-comprehension.md` 18.5 KB. Four technique basenames (`analyze`, `create-pr`, `mark-ready`, `revise-session-metrics`) exist in both trees, alongside eleven parallel `TECHNIQUE.md` group files. The 26 `check-*.ts` guards are reachable only as repo CI, never as a workflow operation. `record_usage` and three benchmark scripts (`run-token-benchmark`, `run-dispatch-benchmark`, `run-batch-benchmark`) already instrument cost.

## 2. Dimension Plan

| Dimension | Pipeline Mode | Lenses | Analysis Focus | Output Location |
|-----------|---------------|--------|----------------|-----------------|
| Mechanisation Potential | full-prism | L12 pipeline (00→01→02) | Evaluate the mechanisation potential of agent-executed technique prose in `workflows/meta` (150 technique files, ~34,900 words) and `workflows/work-package` (112 files, ~66,300 words): find every protocol step that is a deterministic procedure a script or server tool could compute. Use repo/component/issue/PR coordinate resolution (`version-control::resolve-host-repo`, monorepo component matching) as guide, not boundary; examine also path derivation, repo- and project-type detection, artifact link and anchor checking, `sync-progress-status` Progress-table writes, git and worktree state checks, classification steps that are fixed decision tables, and artifact format and schema validation. Judge each against the available surface: 16 registered MCP tools, all session control-plane, no domain-computation tool; 12,343 LOC in `src/`; 26 `check-*.ts` guards reachable only as CI. For each candidate, test whether the procedure is genuinely deterministic or whether the prose hides a judgement call. | `mechanisation-potential/` |
| Context Economy | portfolio | 15 (sdl-abstraction), 20 (optimize) | Assess the context economy of definition delivery — tokens spent shipping technique and resource bodies into agent contexts. Measure body size against what a step actually reads: `dispatch-activity.md` 10.0 KB, `workflow-engine/TECHNIQUE.md` 8.3 KB, `review-summary.md` 9.6 KB, `review-assumptions/reconcile.md` 9.3 KB, `review-mode.md` 21.6 KB, `codebase-comprehension.md` 18.5 KB, against 290 KB of meta and 617 KB of work-package definitions. Name the abstraction that would collapse each duplication. | `dimensions/` |
| Orchestration Topology | portfolio | 14 (sdl-coupling), 51 (architect) | Analyse the orchestration topology of the two workflows — how work is distributed across agents and turns, and where the shape itself is the cost. work-package runs 15 activities carrying 44 checkpoint blocks across 13 of them, concentrated in `01-start-work-package` (10) and `13-submit-for-review` (9); meta runs 5 activities with 5 checkpoints, 3 of them in `00-discover-session`. Examine dispatch granularity and the server-enforced batch bound (`src/utils/batch.ts`, `dispatch.ts`, `fan-out.ts`), worker round trips per activity (`get_activity`, `get_technique`, `get_resource`, yield and resume, `record_usage`), serial steps that could run concurrently, blocking-gate placement, context re-establishment at every activity boundary, and sub-agent spawn overhead. Propose alternative topologies and state what each trades. | `dimensions/` |
| Redundant Work | portfolio | 30 (reachability), 10 (degradation) | Identify redundant work — steps the workflows perform that produce nothing the run consumes. Trace activities and techniques never reached in practice across meta's 5 activities and work-package's 15; artifacts written but never read downstream; verification repeated at multiple stages (26 `check-*.ts` guards alongside in-workflow `verify-artifact-conforms`, `validate-workflow-yaml`, `validate-activities`); optional branches that always resolve the same way. Examine duplication across the two trees, where `analyze.md`, `create-pr.md`, `mark-ready.md` and `revise-session-metrics.md` exist under both and eleven `TECHNIQUE.md` group files carry parallel structure. Distinguish genuinely dead paths from paths that are rare but load-bearing. | `dimensions/` |
| Change Economics | portfolio | 07 (claim), 08 (scarcity) | Evaluate the change economics of each optimisation opportunity — what building it costs and what it risks. For each, classify the implementation surface: a new server tool in `src/tools/` (2,821 LOC, 16 tools today), a script under `scripts/` (44 scripts, 15,257 LOC), or a definition edit in the 907 KB markdown and YAML corpus. Weigh the guard and test coverage protecting the change (72 test files, 18,420 LOC; 26 `check-*.ts` guards), saved-session and backwards compatibility for sessions holding the old shape, whether the saving is measurable with the `record_usage` instrumentation and the `run-token-benchmark` / `run-dispatch-benchmark` / `run-batch-benchmark` scripts already present, and sequencing dependencies between opportunities. Test the scarcity claims: which costs are immovable regardless of redesign. | `dimensions/` |

Mapping rationale: no dimension matches the standard consistency / veracity / plausibility patterns, so four are mapped through prism's own goal-mapping matrix — Context Economy as abstraction quality plus performance, Orchestration Topology as coupling plus architecture exploration, Redundant Work as dead code plus decay. Change Economics matches the standard feasibility / resources / constraints row (scarcity 08) and is also strategy evaluation, which prism maps to claim 07 + scarcity 08. Mechanisation Potential is the run's primary lead and carries the highest false-positive risk — prose that looks deterministic but hides judgement — so it takes the 3-pass pipeline whose adversarial challenge exists to catch exactly that. Lens sets are kept disjoint across dimensions so findings do not duplicate. Lenses 14, 20 and 30 are code-only under prism's `code-vs-general` rule; this target is mixed and each is pointed at the code half (`src/utils` delivery and dispatch machinery, `src/tools`, `scripts/`) as well as the definition prose.
