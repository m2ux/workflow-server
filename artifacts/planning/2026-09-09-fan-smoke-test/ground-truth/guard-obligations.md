# Guard obligations a new corpus workflow incurs

## The registry

"The registry is `scripts/guards.ts` — one exported `GUARDS: GuardSpec[]`, currently 37 entries (the file grew from 36 to 37 during this investigation, gaining `launched-workflows` at commit dbd82286). Each entry is `{ id, script, npmScript, scope, json, proves }`. `scope` is `'corpus' | 'repo'`: 33 corpus-scoped, 4 repo-scoped (`site-links`, `svg-layout`, `source-encoding`, `lockfile-denylist`). `CORPUS_GUARDS` is the filtered export.\n\nThe scope distinction decides two things. `check:all` honours `--corpus-only`. More importantly `check:delta` (scripts/check-delta.ts) passes `--root <tree>/workflows` ONLY to corpus-scoped guards and sets `WORKFLOWS_DIR` for them, so a corpus-scoped guard is re-run against the base tree's corpus (materialised in a throwaway worktree with the submodule pinned to the commit the base tree recorded), while a repo-scoped guard is measured against the base tree's own files and never handed a corpus root. A repo-scoped guard misfiled as corpus would be aimed at a corpus it does not read; tests/guard-registry.test.ts pins that exact four-name list.\n\nRunning one guard individually, three ways: `npm run <npmScript>` (e.g. `npm run check:binding`, `npm run check:activity-variables`, `npm run check:workflow-yaml`); or `npm run check:all -- --only <id>[,<id>]`, which errors on an unknown id; or directly, `npx tsx scripts/check-<name>.ts [--root <workflows-dir>] [--json]`. Every guard reports through `scripts/guard-protocol.ts`: exit 0 clean, 1 findings, 2 could-not-measure (unreachable or empty corpus root — `requireWorkflowsRoot` plus `assertScanned`, so green-because-empty is impossible). 25 of the 37 speak `--json`, which is what gives `check:delta` a per-finding diff rather than an exit-code comparison. Full sweep is ~6 seconds wall clock across 37 guards.\n\nTwo guard scripts sit on disk OUTSIDE the registry, each with a recorded reason in tests/guard-registry.test.ts: `scripts/check-session-contract.ts` (needs a live session, no corpus-wide form) and `scripts/check-message-binding.ts` (reads the corpus and holds at 107 findings, so it runs by path until those are triaged). That test also fails if any `check-*.ts`/`validate-*.ts` on disk is neither registered nor excused, and if a `check:*` package script has no registry entry — so adding a guard for the fan feature must land as a registry entry, an npm script, and nothing else.\n\nA repo-scope note that matters here: `check-source-encoding.ts` has `workflows` in its `SKIP_DIRS`, so it never scans the corpus even when the corpus is checked out at `./workflows` inside the tooling tree. The corpus is exempt from the control-character check by construction."

## The option-coverage walk

"The option-coverage walk is `tests/e2e/option-coverage.test.ts`, wrapped by `describe.skipIf(process.env.WF_OPTION_COVERAGE !== '1')`, so it does NOT run under `npm run test:ci`. It is invoked as `npm run test:coverage-walk` (`WF_OPTION_COVERAGE=1 vitest run tests/e2e/option-coverage.test.ts`) and, in CI, by the separate `.github/workflows/coverage.yml` job with `timeout-minutes: 70`; the test carries its own 3,600,000 ms timeout.\n\nWhat it measures: the DENOMINATOR comes from the definitions (`declaredOptions`/`declaredCheckpoints` in tests/e2e/coverage.ts, loading each workflow through the real loader so fragment-`ref` checkpoints and borrowed activities are resolved), keyed `checkpoint:<activity>:<checkpoint>=<option>`. The numerator is `coveredBranches` from `enumeratePaths`. Options no walk reaches must be listed, with a reason, in `tests/e2e/option-coverage.json` — three reason groups today, 121 listed options. The list can only shrink: an unreached option not on it fails, an option on it that has become covered fails, and (on an unscoped run only) an option on it that no definition declares fails as stale. Current figure is 155 of 276 declared options covered.\n\nThe roster is `WALKED` / `NOT_WALKED` in `tests/e2e/walked-workflows.ts` — 14 walked, 3 not (`remediate-vuln`, `cicd-pipeline-security-audit`, `substrate-node-security-audit`). Crucially `tests/e2e/coverage-roster.test.ts` DOES run in `test:ci` and requires every corpus workflow to appear on exactly one of the two lists, with a reason recorded for `NOT_WALKED`.\n\nWhat adding a new corpus workflow does, in order:\n\n1. `test:ci` goes red the instant the submodule pointer moves, from `coverage-roster.test.ts`: \"this workflow is in the corpus but neither walked nor listed as not walked\". Both lists live on `main`, so the fix is a server-branch edit.\n2. `tests/e2e/all-workflows-walk.test.ts` also runs in `test:ci` and takes its roster from the corpus directory rather than a list, so the new workflow is walked in `mode: 'graph'` with `defaultPolicy` + `autoAdvance`, `maxVisits: 80`, and must reach `path.length > 0` with zero `orchestratorUnresolved`, zero step `unresolved`, and zero `loadErrors`. There is no opt-out from this one at all.\n3. If put on `NOT_WALKED`: an unscoped run still takes its denominator from `corpusWorkflows()`, so every option the new workflow declares becomes an unreached option needing an entry in `option-coverage.json`. A smoke workflow that declares NO checkpoints declares no options and costs nothing here — which is how the two audit workflows sit on `NOT_WALKED`.\n4. If put on `WALKED`: the walk drives it, and its options must be reached or listed. Two budget consequences. The roster is ordered slowest-first and its wall clock is the slowest single walk, not the sum — `work-package` accounts for essentially all of the 1,269 s measured with the roster in flight — so an addition below `work-package` is free and one slower than it sets the cost of the job. And `DRY_WALKS` (default 50, `WF_DRY_WALKS` to override) is the consecutive-no-new-option plateau at which the enumerator calls a workflow done; the comment states plainly that \"the plateau this detects is a property of the graph, so it has to be re-measured whenever the graph grows\" — 36 was the lowest value clearing workflow-design, and 50 sits above it deliberately. A fan multiplies walkable edges out of one activity, so a fan-bearing workflow is precisely the kind of graph growth that wants the plateau re-measured rather than assumed.\n5. Editing either `tests/e2e/walked-workflows.ts` or `tests/e2e/option-coverage.json` puts the coverage job into full-corpus mode: the job's scope step diffs `src tests/e2e/walker.ts tests/e2e/policies.ts tests/e2e/coverage.ts tests/e2e/option-coverage.json tests/e2e/walked-workflows.ts` and, on any hit, walks everything. The fan feature changes `src/` anyway, so every PR in this line runs the full ~21-minute (local) / ~38-minute (shared runner) walk rather than a scoped one.\n6. On a corpus-only PR the coverage job does not run at all (the `workflows` branch carries only `verify-corpus.yml`). On the pointer-bump PR, `scripts/coverage-scope.ts` maps the change: a new `workflow.yaml` scopes to that workflow only `if (walked.includes(id))`, so a `NOT_WALKED` addition resolves to an empty scope, the job prints `scope=none` and SKIPS the walk — the new workflow's declared options are first judged after merge, on the push-to-main full run."

## Snapshots a new workflow invalidates

"Four committed artefacts are corpus-coupled, plus two roster/expectation files. Only one is invalidated by the content of a new workflow; the rest are invalidated by the submodule POINTER moving, which adding a corpus workflow necessarily does.\n\n1. `tests/e2e/__snapshots__/corpus-sha.json` — the corpus stamp. `tests/stamp-freshness.ts` asserts it equals `git -C <corpus> rev-parse HEAD`, and it is checked first by both `tests/e2e/snapshot.test.ts` (`walk baseline corpus stamp`) and the option-coverage test. It goes stale the moment the pointer moves. Regenerate with `npm run baseline:stamp` (scripts/stamp-corpus-baseline.ts), in the SAME commit that bumps the submodule.\n\n2. `tests/e2e/__snapshots__/snapshot.test.ts.snap` — seven walk snapshots, all of `work-package` under six policies plus a per-activity executed-step record. A new independent workflow does not change these, but the stamp check in front of them fails first, so in practice the pair moves together. Regenerate with `npm run test:ci -- -u`, then `npm run baseline:stamp`.\n\n3. `scripts/fixtures/token-benchmark-baseline.json` — the delivery-cost fixture, records `workflowId: work-package` and `workflowsRev`. `verify.yml` gates against it at 1% (`npm run bench:token -- --label=ci --context-mode=fresh --gate`). A new workflow directory adds no delivery to the work-package walk, so this should hold; it moves only if the change edits `meta` or anything work-package composes. Re-record with `npm run bench:token -- --label=rerecord --context-mode=fresh --no-compare`.\n\n4. `scripts/binding-fidelity-triage.json` `corpusSha` — informational rather than gating: `triageStampNote` prints how far the corpus has moved without failing on it. `tests/binding-triage.test.ts` only requires the field be a 40-hex sha, and additionally that every declared rationale is cited and every cited rationale declared, and every verdict be one of `harmless`/`fix-later`/`live-bug`. So adding a triage entry for the smoke workflow means either citing an existing rationale or adding a new one AND citing it.\n\n5. `tests/e2e/walked-workflows.ts` (`WALKED`/`NOT_WALKED`) — not a snapshot but a committed roster that `coverage-roster.test.ts` holds against the corpus directory listing. Adding a corpus workflow invalidates it and reddens `test:ci`.\n\n6. `tests/e2e/option-coverage.json` — the uncovered-option expectation. Invalidated by any option the new workflow declares that no walk reaches (and, for an unscoped run, by any listed option no definition declares).\n\nThere is no checksum over the corpus itself, and no generated index a new workflow must be registered in: `workflows/README.md` carries an \"Available Workflows\" table but nothing verifies it, and `site/` mentions workflow ids only in hand-authored prose that `check:site` checks for link resolution, not for completeness."

## Corpus and server on different branches

"The two branches are checked by two different jobs with opposite tooling provenance, and that is what makes a corpus change and a server change mutually blocking.\n\nCorpus-branch PR (`.github/workflows/verify-corpus.yml`, which lives on the `workflows` branch): it checks out `ref: main` for the tooling — main's `scripts/`, main's `scripts/guards.ts`, main's `package.json` — then checks out the corpus PR's HEAD SHA (the branch TIP, deliberately not the merge result) at `path: workflows`, and runs `npm run check:all`. It runs guards only, never the test suite, because the walk snapshots are stamped against one corpus commit. Consequence: a corpus workflow using the widened graph forms is graded by main's UNWIDENED `GraphSchema` and `validateGraphAgainstActivities`, so `workflow-yaml`, `refs`, `activity-variables`, `audience`, `artifact-guides` and every other loader-backed guard report it as unloadable. The corpus PR is red and stays red until the paired server PR merges to `main`. Nothing on the corpus branch can pin an older or newer tooling commit — the `ref: main` is hardcoded.\n\nServer-branch PR (`.github/workflows/verify.yml`): checks out `submodules: false`, then `./.github/actions/workflows-corpus` resolves `git rev-parse HEAD:workflows` and checks that commit out at `workflows/`, then runs `typecheck`, `test:ci`, `check:all` and the delivery gate. Consequence in the other direction: a server PR that widens the schema cannot demonstrate it against a real corpus workflow, because the gitlink still names a corpus without one — and `coverage-roster.test.ts` plus `all-workflows-walk.test.ts` only see the new workflow once the pointer is bumped.\n\nThe pointer-bump PR is where both sides meet, and it carries its own trap. `.github/actions/workflows-corpus` runs a pull-request-only step comparing the merge tree's gitlink against the branch head's gitlink and FAILS when they differ, on the reasoning that the branch's committed baselines were recorded against the branch's corpus. So if the base moves the submodule while your branch does not, CI stops with an explicit instruction: merge the base in, re-baseline with `npm run test:ci -- -u`, and re-stamp with `npm run baseline:stamp` in the same commit.\n\nWhat an author actually does, ordered:\n\n1. Land the server change on `main` first — the widened `GraphSchema`, the loader's join derivation, every graph reader — with fixture corpora in tmpdir (`createHarness({ workflowDir })`, as tests/exit-destinations.test.ts and tests/enforcement-notes.test.ts do) standing in for the real workflow. Fixture corpora under `/tmp` are invisible to every guard, since guards resolve their root through `--root` / `WORKFLOWS_DIR` / the repo default. This is also where the ILLEGAL fan forms belong: a nested barrier, a one-member list, an instance fan over a non-collection cannot live in a corpus workflow that has to pass the loader, but they are exactly what a fixture-corpus rejection test asserts.\n2. Then land the corpus workflow on the `workflows` branch. Its PR is red for the interval between the two only if it is opened before the server merge; opened after, main's tooling already understands the forms.\n3. Then bump the pointer on `main` in one commit that also: adds the workflow to `WALKED` or `NOT_WALKED`; adds any needed `option-coverage.json` entries; adds any needed `binding-fidelity-triage.json` entries; runs `npm run test:ci -- -u` and `npm run baseline:stamp`.\n4. Verify locally in the interval, because CI cannot. `npm run check:all -- --root <path-to-corpus-worktree>` aims every corpus guard at the branch under review, `npm run check:delta` diffs a whole sweep against the merge-base with the submodule pinned to what that tree recorded (cached under `.guard-cache/`), and `npm run worktree:provision` makes a fresh worktree measurable. Then re-run the corpus-branch sweep by hand after the server merge, which is precisely what the delivery plan's stage 7 already commits to: \"a workflows-branch sweep runs the server's main tooling and stays red until the paired server change merges, so the site is verified locally and the sweep re-run by hand afterwards.\"\n\nOne asymmetry worth planning around: `pinned-corpus-paths` reads the PINNED corpus, so any server-side test that names the smoke workflow's files by literal path fails on `main` until step 3. Either write those literals as fixture-authoring calls, keep them in comments, or land them in the same commit as the pointer bump."
