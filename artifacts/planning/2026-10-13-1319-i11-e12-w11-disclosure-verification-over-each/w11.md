# W11 — Disclosure Verification Over Each Mode

## Overview

This task measures what each mode of Work Planner and of Workflow Canon retrieves when a reader runs it, against the layout before epic E12 and the layout after it, and records the result per mode. The epic's Proposal claims the reader meets an operation at the point of use rather than through a link out; every other row of the epic has tested that claim by counting what the files contain. This row counts what a reader opens, which is the only count the claim is about. It changes no skill file.

## Problem

- **The claim is readability and the evidence is arithmetic.**
  The epic reports a catalog falling from 79 specifications and 870 lines to 34 and 374, 44 specifications moved into 12 files, and a shared check reporting zero findings over both skills. Each is a fact about file contents. None of them is a fact about retrieval.
- **A smaller catalog does not entail a shorter reach.**
  Moving a specification into the file whose procedure runs it removes one link out. Taking the execution conventions into `references/command-conventions.md` adds a file every mode opens. Whether a mode now opens fewer files is the open question, and nothing in the epic answers it.
- **Nothing records retrieval per mode.**
  A mode whose operations were already local gains nothing, and a mode whose operations stayed in the catalog may have gained a file and lost nothing. The epic's counts are totals over a skill, so a mode that got worse is invisible in them.

## Proposal

The walk fixes its scenarios and its measure before either layout is measured, counts both layouts with one instrument, and records the outcome per mode whatever it shows.

### Scenarios

A scenario is one mode run end to end on a task its own file says it is for. The modes are the unit of the criterion — AC6 reads "each mode's retrieval" — and `SKILL.md` enumerates them, so the set is the repository's rather than this walk's. Each scenario below names the concrete task that exercises the mode.

- **Work Planner, ten modes.**
  Propose (scope a problem and raise its proposal), Plan (raise an epic and write its work items), Align (check an epic's criteria against the templates and the rules), Sync (link a merged task pull request and tick what it delivers), Advance (place a board's next epic at Ready), Deliver (merge a passing task pull request, dispatch the next unit), Understand (write a pull request's architecture overview), Hoist (raise a standalone issue and place it), Standup (summarise a board's window), Revise (change the skill's own files).
- **Workflow Canon, four modes.**
  Author (write a new activity definition), Audit (audit a workflow against the canon), Review (assess an integration's readiness), Revise (change the skill's own files).
- **Why these are representative.**
  Six of the fourteen — Plan, Align, Sync, Deliver, Understand and Hoist — are the operations this epic's own delivery ran, once per unit, so they are observed demand rather than supposed demand. The other eight are every remaining mode the two skills offer: taking all of them leaves no room to select the modes that flatter the result. No scenario is dropped, because none rests on a mode either skill does not state.
- **What the set excludes.**
  A reader who opens one reference file to answer one question is not a scenario, since the criterion is about a mode's retrieval and a mode is the thing a reader runs.

### Measure

Three counts, each taken over the same traversal and each recorded per mode. The traversal is depth one: `SKILL.md` to select the mode, the mode file whole, and the files the mode file sends the reader to. Links standing inside the mode file's own command specifications are not part of it, because a specification states how one command runs and a reader reaching it has already arrived.

- **M1, files opened.**
  `SKILL.md`, the mode file, and each distinct further file the mode file cites outside its command specifications. This is the retrieval cost the claim is about.
- **M2, operations reached in file against operations reached by link out.**
  Among the command specifications the mode cites, how many stand in the mode file and how many stand elsewhere. This is the claim stated as a count: "at the point of use rather than through a link out".
- **M3, lines loaded.**
  The total line count of the files M1 names. An agent reader that opens a file reads it whole, so the catalog's size is a retrieval cost and not only a content count.

- **One instrument over both layouts.**
  `walk.py` imports `skills/scripts/check_skill_files.py` at the unit's revision and reuses its `specifications` and `scan` definitions, so "a command specification" means over the before layout exactly what the epic's own check means by it. The script is given a skill directory and prints a row per mode; the before layout and the after layout differ only in the directory given.
- **What the measure cannot see.**
  Depth one counts the files a mode sends a reader to, not the files those files send them to in turn. A specification that moved into a mode file and still cites the catalog is counted as reached in file, which is what the claim asserts, and the second hop it may cost is outside this measure. The limitation is recorded with the result rather than corrected, since correcting it would change the measure after the layouts were known.

### Layouts

- **Before.** `fae97e9e`, the commit the epic's issue body cites throughout as the pre-change state, read in a detached worktree.
- **After.** `f2c26048`, the epic base this task branches from.

### Reporting

The result is recorded per mode for both skills, with the modes that improved, the modes that did not, and any mode that got worse named individually. A layout fault the walk finds is reported as an arising issue; this task fixes none.
