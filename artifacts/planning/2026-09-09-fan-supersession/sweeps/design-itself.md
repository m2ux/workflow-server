## REMOVE — workflows/meta/techniques/orchestration-patterns/dispatch-workers.md — the `dispatch_concurrency` input and its greater-than-1 protocol branch (step 3, the spawn-concurrent batch)

**What it does today.** Lets an activity step dispatch a set of composed worker briefs either sequentially (concurrency 1, one spawn-agent per brief) or as one concurrent batch. It is the corpus's only mechanism for saying 'run these N pieces of work at the same time'.

**Why the fan takes it.** The design establishes, and I confirmed, that all 15 bindings of this operation sit inside activities executed by a dispatched worker, and a dispatched worker holds no agent-dispatch primitive. The concurrent branch cannot execute at any of its call sites and never could. The graph fan is the same capability placed where the dispatch primitive actually is. Once it lands there are two documented ways to express concurrent fan-out, one of which is unreachable.

**Evidence.** dispatch-workers.md:16-18 declares `dispatch_concurrency`, 'Default `1`. `1` = sequential spawn-agent per brief; greater than `1` = one spawn-concurrent batch'; lines 29-30 are the two protocol branches. 15 binding lines across exactly 7 files, which I counted independently and which matches the design's own figure. The specification states the disqualifier itself at README.md:1202: 'every one of its binding sites is a client activity executed by a dispatched worker, so neither of its concurrency branches is executable there. The corpus's whole fan-out vocabulary is unreachable from every one of its call sites.' delivery-plan.md:306 concedes 'the parallel selection on the dispatch-workers operation is retired and the operation states its in-activity sequential contract positively' — then delivery-plan.md:255 and :267 put it out of scope twice.

**Blast radius.** Bindings to retire or reduce to the sequential contract: workflows/substrate-node-security-audit/activities/03-primary-audit.yaml (4), workflows/substrate-node-security-audit/activities/02-reconnaissance.yaml (2), workflows/cicd-pipeline-security-audit/activities/03-primary-scan.yaml (4), workflows/meta/activities/patterns/05-lead-researcher.yaml (2), 01-orchestrator-workers.yaml (1), 02-supervisor.yaml (1), 04-isolated-fan-out.yaml (1). Reader-side: workflows/meta/techniques/orchestration-patterns/TECHNIQUE.md declares the group inputs; workflows/meta/techniques/harness-compat/spawn-concurrent.md loses one caller. One concrete variable dies with it: cicd-pipeline-security-audit/activities/03-primary-scan.yaml binds `dispatch_concurrency: scanners_assigned` (line 29) and declares `scanners_assigned` among its reads (line 9) — the shadow width variable delivery-plan.md:190 already schedules for deletion at stage 7.

**If left alone.** Two documented paths for one job, and the one an author reaches first cannot run. The design's answer is to amend prose so each path 'names the layer it now covers' — a maintained rule policing an overlap, which is the shape the repo's own principle says to design out. It also leaves the operation's `dispatch_concurrency` input live as the second home for a fan's width, directly against the design's 'the width bound has one home' claim.

## REMOVE — workflows/meta/techniques/scatter-gather.md — the parallel scatter mode, plus the two rules that exist to relate it to sequential mode: `one-gather-contract-two-scatter-modes` and `parallelism-is-optimisation`

**What it does today.** Declares scatter-gather as 'one primitive, two scatter modes', where parallel mode is 'sequential mode plus concurrency and isolation' and sequential mode is 'the concurrency = 1 case of parallel mode'. The two rules assert the gather contract and the combine step are mode-independent, and that parallel mode is an optimisation over an always-valid sequential mode.

**Why the fan takes it.** Parallel mode dispatches through the same unreachable primitive as the dispatch-workers concurrency branch, so its parallel arm cannot execute at any binding. The graph fan takes the parallel arm's job. Worse for the design's case: stage 4 adds a *third* scatter mode to this same file rather than deleting the dead second one, so the file ends up carrying three modes of which one cannot run.

**Evidence.** scatter-gather.md:8 'Scatter work units (sequential or parallel), gather an ordered keyed collection, then combine — one primitive, two scatter modes'; :22-24 the `one-gather-contract-two-scatter-modes` rule; :28 and :36 both branch on mode ('per iteration in sequential mode, per instance in parallel mode'; 'in parallel mode inherited from spawn-concurrent's in-input-order collection'); :38-40 the `parallelism-is-optimisation` rule. The addition is delivery-plan.md:51: 'scatter-gather.md gains the graph-fan application of isolate-then-combine, the third scatter mode over one gather contract, and the rule that a meeting point gathers the container rather than naming a slot.'

**Blast radius.** The file itself, its two named rules (any `refs` anchor pointing at them must be re-pointed or dropped — the guard obligations table already lists `refs` for this file at stage 4), and the mode-conditional sentences at :28 and :36. workflows/meta/activities/patterns/README.md:9 names scatter-gather as a 'fan-out primitive'. workflow-design/resources/anti-patterns.md cites `scatter-gather` in the strategy-technique coverage discriminator.

**If left alone.** One technique file states three scatter modes for two executable layers, with one mode that has never been runnable from any binding. `parallelism-is-optimisation` becomes a false statement of where the choice lives: after the fan, choosing parallel is a routing decision in the graph, not an optimisation flag on a step. Every anchor and every author who reads this file has to be told which of the three modes their layer can actually reach — a rule to maintain forever.

**What it does today.** `from_activity` names the activity a transition is exiting. It is optional: 'Omit while one activity is in flight; required while a fan is running.' When omitted, the resolver returns the sole frontier entry — a guess that is correct only because there is one candidate.

**Why the fan takes it.** The optionality exists so that existing sequential callers need no edit — the design says as much: 'the sole entry when a call names none and only one is in flight — every ordinary walk, so a session with no fan open never reaches the named case.' That is an accommodation for existing callers, which the repo's principles put on the same footing as a fallback. It also costs the design's central resolution rule half its cases.

**Evidence.** README.md:1052 the parameter description, 'Omit while one activity is in flight; required while a fan is running'. README.md:1058, step 1 of the five-step rule, carries four cases purely because of the optionality: 'Named and in the frontier: that one. Named and absent: refuse. Unnamed with at most one entry: the sole entry, or none on the first call of a session. Unnamed with several: refuse.' Two of those four exist only to handle omission, and one of the refusals in the verbatim list (README.md:1083, 'Cannot exit challenge-pass: the session is on three instances of it ... Pass from_activity naming the instance') exists only to tell a caller to supply what it could have been required to supply. The resolver doc comment at README.md:1006-1012 states the guess explicitly.

**Blast radius.** Requiring it (except on the session's first call, which has no exiting activity) touches: the parameter declaration, `heldActivity`'s signature and body, step 1 of the resolution rule, one of the four verbatim refusals, and the two definitions that compose the call — workflows/meta/techniques/workflow-engine/evaluate-transition.md and finalize-activity.md, both already on the design's stage-2 file list. Every existing test that calls `next_activity` gains one argument; the design already accepts test churn for the field rename at stage 5 ('no test is rewritten for behaviour — only for the field name').

**If left alone.** The server guesses which activity a call is exiting whenever the caller declines to say, on the code path that retires an activity, records its exit, applies its variable writes under a branch key and stamps its trace. The guess is safe only while the frontier holds one entry, which makes correctness contingent on a count rather than on the call. The design's own justification for refusing a guess elsewhere is the right one and is not applied here: 'the caller refuses rather than guessing, because a guess serves one branch another branch's activity.'

## REMOVE — The unconstrained activity-id alphabet — `id: z.string()` on `ActivitySchema` with no pattern in src/schema/identifiers.ts — and the exact-then-base fallback the design adds to `getActivity` to work around it

**What it does today.** Activity ids are arbitrary strings today; nothing forbids `#`. The design makes `#` a structural separator (`INSTANCE_SEPARATOR`) in frontier entries, history event activity fields, usage rows, trace stamps and delivery keys, and handles the resulting ambiguity with a two-step lookup: exact id match first, base-id match second.

**Why the fan takes it.** The fan promotes `#` from a checkpoint-local convention to load-bearing structure across the session record. The design's response is a fallback lookup; the cheaper answer under the repo's own principles is to remove `#` from the legal alphabet, after which one lookup on the base suffices and the fallback has nothing to fall back to.

**Evidence.** src/schema/activity.schema.ts declares the activity id as a bare `z.string()`; src/schema/identifiers.ts holds only `QUALIFIED_DATA_ID_PATTERN` and `isSingleWord` for *variable* names — there is no activity-id pattern. The design's fallback is at README.md:992-995: `workflow.activities?.find(a => a.id === activityId) ?? workflow.activities?.find(a => a.id === baseId(activityId))`, doc-commented 'An exact id match wins; otherwise an instance-qualified id resolves to its base definition.' The load rule the design does write, L10 (README.md:1735), constrains only the derived *branch key*'s legality, not the id's alphabet. I checked all 122 activity files: no id contains `#`, so the constraint is free at the corpus level. Existing precedent for the separator: src/loaders/workflow-loader.ts:449 `CHECKPOINT_INSTANCE_SEPARATOR = '#'`.

**Blast radius.** Adding the pattern: one schema field, one load message. Zero corpus movement — verified across 122 activity files. Removing the fallback then simplifies `getActivity` to a single `find` on `baseId(activityId)`, and removes the second half of the 'two edits close all six readers' claim at README.md:983.

**If left alone.** `#` is simultaneously a legal activity-id character and the separator that decides which frontier entry a call retires, which slot a branch's outputs land in, and which usage row a figure is attributed to. An id containing `#` truncates under `baseId` and may misparse under `instanceIndex`, silently — and the design's own list of what a composite id does to six readers does not cover it. The fallback lookup makes the ambiguity survivable for the lookup and nowhere else.

## KEEP — The bare-string form of `DestinationSchema` (`z.string()`), and the `min(2)` arity rule on the array form that keeps it unambiguous

**What it does today.** Spells 'this exit leads to one activity' as the activity's id, and 'this exit ends the run' as `__terminal__`. The array form's `min(2)` prevents a one-element list from expressing the same thing a second way, with its own error message directing the author to the bare string.

**Why the fan takes it.** It does not. I looked hard at this one, because a three-form union with a string survivor is the classic shape of a compatibility shim, and the arity rule is a prohibition policing an overlap the union creates. But the string is not a legacy spelling being kept alive alongside a successor — it is the only spelling the corpus has ever had, and it remains the readable one for the case that dominates.

**Evidence.** I re-measured the corpus independently across all 17 workflow.yaml files: 206 scalar destinations, 18 of them terminal, 0 list-valued, 0 object-valued — matching the design's provenance figures (207/18/0/0; one edge differs by indentation). GraphSchema today is `z.record(z.record(z.string()))` at src/schema/workflow.schema.ts:51, so there is no prior second form and no survivor. The alternative — a single list form of one or more members — would rewrite all 206 edges to gain nothing an author can read, and would make the terminal sentinel a one-element list. The arity rule's message (README.md:606) is one line and names the fix site: 'an exit that leads to one activity names that activity'.

**Blast radius.** 206 destinations across 17 files if the string form were collapsed into the list form, plus the terminal sentinel's handling in src/loaders/workflow-loader.ts and every reader of a destination. That is the honest cost of the alternative, and it buys no capability.

**If left alone.** Nothing to maintain beyond one arity message. The vocabulary is genuinely three-form: one destination, several members, one activity over a collection. This is the candidate that looked superseded and is not.

## KEEP — `yield_checkpoint`'s `variables_changed` channel (src/tools/workflow-tools.ts:93-99, 1622, 1721-1722) and `respond_checkpoint`'s option `setVariable` effect — the 'two write paths closed rather than namespaced' by the gate ban
