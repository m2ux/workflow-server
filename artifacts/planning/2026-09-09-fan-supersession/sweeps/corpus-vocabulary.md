## REMOVE — workflows/meta/techniques/orchestration-patterns/dispatch-workers.md — the whole operation

**What it does today.** Takes an ordered array of worker briefs and returns harness results in input order, selecting its dispatch mechanism on `dispatch_concurrency`: 1 (or omitted) applies `harness-compat::spawn-agent` once per brief; greater than 1 applies `harness-compat::spawn-concurrent` once with all agents. It is the operation that chooses between the sequential and parallel modes.

**Why the fan takes it.** A destination's form now says how many workers open, and `workflows/meta/techniques/workflow-engine/dispatch-fan.md` — bound only in `meta/activities/03-dispatch-client-workflow.yaml`, where the dispatch primitive actually is — mints one identity and one prompt per branch and spawns the batch in one turn. That is this operation's entire job, relocated to the layer that holds the primitive. And this operation has never been able to do it: BOTH branches need an agent-dispatch tool, and every one of its call sites is an activity step. The delivery plan proposes keeping it with 'its in-activity sequential contract stated positively' — there is no such contract, because the sequential branch is `spawn-agent`, which `depth-1-only` denies a worker exactly as it denies `spawn-concurrent`.

**Evidence.** 15 bindings across 7 files, measured: `cicd-pipeline-security-audit/activities/03-primary-scan.yaml:27,50,56,62`; `substrate-node-security-audit/activities/02-reconnaissance.yaml:37,49`; `substrate-node-security-audit/activities/03-primary-audit.yaml:48,75,81,87`; `meta/activities/patterns/01-orchestrator-workers.yaml:43`, `02-supervisor.yaml:48`, `04-isolated-fan-out.yaml:47`, `05-lead-researcher.yaml:47,76`. Unexecutability chain, all quoted: `workflow-orchestrator.md:35` — "Always dispatch a worker — never execute activity steps inline"; `spawn-agent.md:44` — "Spawned sub-agents do not inherit the orchestrator's dispatch primitive"; `spawn-agent.md:46` — "A spawned agent therefore has no dispatch primitive"; `claude-code.md:12-15` confirms the harness primitive is the orchestrator's `Agent` call. `dispatch-workers.md:29-30` names spawn-agent for mode 1 and spawn-concurrent for mode 2. The only inline-executed activity in the corpus, `meta/activities/03-dispatch-client-workflow.yaml:57`, binds `workflow-engine::dispatch-activity` and not this.

**Blast radius.** 15 step bindings in 7 YAML files (above). ## REMOVE — workflows/meta/techniques/scatter-gather.md — the parallel scatter mode (Protocol step 1 parallel bullet, step 2 parallel bullet)

**What it does today.** Declares the second of the primitive's two scatter modes: build one instance prompt per work unit from the per-unit operation, dispatch all at once via `harness-compat::spawn-concurrent` as a single batch, block until every instance yields, then assemble spawn-concurrent's in-input-order `results` into the gathered collection under the iteration key.

**Why the fan takes it.** This is in-activity fan-out — several agents opened from inside one activity's step list. The graph fan is that capability at the layer where routing is decided and where the dispatch primitive lives, and it adds what this mode never had: each branch is a real activity with its own exits, artifacts commit, usage figure and progress row. The mode is also dead at every site: the 7 activity files that use the parallel branch are exactly the 7 that bind `dispatch-workers`, and none can spawn.

**Evidence.** `scatter-gather.md:14` (step 1 parallel) and `:17` (step 2 parallel) are the two bullets. `scatter-gather` is declared at 26 activity sites; the 7 that bind `dispatch-workers` carry no loop step at all (measured: ripgrep for `kind: loop` returns nothing in `cicd-pipeline-security-audit/activities/03-primary-scan.yaml`, `substrate-node-security-audit/activities/02-reconnaissance.yaml`, `03-primary-audit.yaml`, `meta/activities/patterns/01`, `02`, `04`; `05-lead-researcher.yaml`'s only loop is the gap-followup `while` whose body binds dispatch again), so those 7 use the parallel bullet and nothing else. The remaining 19 carry `forEach`/`while`/`doWhile` steps and use the sequential bullet.

**Blast radius.** `scatter-gather.md` itself; the two rules that exist only to relate the modes (separate entries below); `harness-compat/spawn-concurrent.md:38-40` and `orchestration-patterns/TECHNIQUE.md:60-62`, whose `parallelism-is-optimisation` back-references cite it; `work-package/techniques/analyse-challenge/challenge.md:27`, which dispatches 'via scatter-gather' and defers mode choice to `depth-1-only`; descriptive prose in `midnight-system-review/techniques/README.md:27`, `prism-audit/techniques/README.md:85`, `prism-evaluate/techniques/README.md:72`, `meta/README.md:141`. The 26 activity-level declarations do NOT change — 19 keep the technique for the sequential contract, and the 7 lose it along with their dispatch steps.

**If left alone.** The corpus keeps two ways to open several workers over a collection, and the older one is unreachable from every place it can be written. `parallelism-is-optimisation` then tells an author the in-activity parallel mode is the optimisation to reach for, which is the wrong construct and an unrunnable one — the design's cost section says the fan buys wall clock and bounded contexts at a token premium, not efficiency.

## REMOVE — workflows/meta/techniques/scatter-gather.md — rule `one-gather-contract-two-scatter-modes`

**What it does today.** Asserts that sequential-loop accumulation and parallel fan-out are the same primitive: 'Parallel mode is sequential mode plus concurrency and isolation; sequential mode is the `concurrency = 1` case of parallel mode.' It is the rule that makes a single concurrency setting a legitimate way to choose between them.

**Why the fan takes it.** The equivalence stops being true. A graph fan is not an in-context loop with concurrency turned up: it opens N worker contexts, gives each branch its own activity identity, exits, artifacts commit and usage entry, and derives its barrier from the graph's own bindings. The design states the discontinuity outright — a loop step contains its body as a list of steps, a destination names an activity the graph already routes; there is no continuation test, no early exit, no body. And the collapse runs the wrong way on cost: the fan pays a whole further delivery per branch where the loop pays one for the entire walk.

**Evidence.** `scatter-gather.md:22-24`. Cited nowhere else — measured: `rg one-gather-contract-two-scatter-modes workflows/` returns exactly one hit, its own heading. Design README's rebuttal is explicit: 'it is not a loop step wearing a graph's clothes… There is no continuation test, no early exit, no nesting, no body' and 'A fan pays a whole further delivery for every branch past the first, so it costs more tokens than the sequential walk it replaces — substantially more for instances, where the alternative pays one delivery for the whole loop.'

**Blast radius.** Zero external citations, so removal is local to `scatter-gather.md`. What the rule was holding up goes with it: `dispatch_concurrency` as a mode selector, and the framing in `orchestration-patterns/TECHNIQUE.md:18` ('`1` = sequential dispatch; greater than `1` = parallel fan-out'). Nothing in the guard suite keys on the rule name.

**If left alone.** A false invariant sits in a strategy technique that 26 activities declare, and it reads as current fact. Worse, it is the rule that licenses the design's own new mode being described as 'a third scatter mode over one gather contract' — three modes under one contract when one of the three lives at a different layer, obeys a different cost model, and cannot express the cross-iteration reads the other two can. That is a rule that has to be maintained against the system rather than describing it.

## REMOVE — workflows/meta/techniques/scatter-gather.md — rule `parallelism-is-optimisation`, and its two `Honor` back-references

**What it does today.** States that sequential mode is always valid for correctness, parallel mode is an optimisation adding concurrency and isolation, and 'Where genuine parallel fan-out is not needed, sequential mode (the `concurrency = 1` case) is the correct default.' `spawn-concurrent.md` and `orchestration-patterns/TECHNIQUE.md` each restate it as a Honor rule.

**Why the fan takes it.** Its subject is the in-activity parallel mode, which goes. Its claim is also false of the fan on the design's own arithmetic: a fan costs more tokens than the sequential walk it replaces and buys wall clock and N bounded contexts instead of one unbounded one — correctness and latency, not optimisation. The choice the rule was making for an author is now made by writing a chain rather than a fan in the graph, at authoring time, in the routing file — not by a setting on a dispatch operation.

**Evidence.** `scatter-gather.md:38-40`; back-references at `harness-compat/spawn-concurrent.md:38-40` ('sequential fallback via spawn-agent remains valid') and `orchestration-patterns/TECHNIQUE.md:60-62` ('a `{dispatch_concurrency}` of 1 remains correct'). Three occurrences total, measured. Design README §3: 'it costs more tokens than the sequential walk it replaces… That is correctness and latency, not efficiency.'

**Blast radius.** Three files: the rule and its two Honor restatements. `spawn-concurrent.md`'s restatement is the odder of the two — it names a fallback in a sibling operation that also cannot run from an activity, and after the change the 'fallback' is an authoring choice in `workflow.yaml`, not a mode of any operation. `orchestration-patterns/TECHNIQUE.md`'s restatement goes with `dispatch_concurrency`.

**If left alone.** Three files carry a cost claim the design measured as backwards, in the exact place an author looks when deciding whether to fan. It also leaves `spawn-concurrent` — which the fan makes executable for the first time — carrying a rule about a sequential fallback that no longer exists at its layer.

## REMOVE — `dispatch_concurrency` — the concurrency setting, declared at orchestration-patterns/TECHNIQUE.md:16-18 and dispatch-workers.md:16-18

**What it does today.** Optional positive integer, default 1. It is the single switch that selects between the sequential and parallel scatter modes, read by three pattern activities and bound at two call sites.

**Why the fan takes it.** A destination's authored FORM now says how many workers open — one id opens one, a list of N opens N, an instance fan opens one per element of its collection. Ten mentions total, measured.

**Blast radius.** The two declarations, three `variables.reads` entries, two bindings, and the README sentence. At the cicd site the session variable `scanners_assigned` is the shadow width the delivery plan says the migration deletes; it survives there only as the thing the removed step read. `02-supervisor.yaml:50` is the corpus's only literal binding and disappears with that activity.

**If left alone.** A second width authority sits on an operation, able to disagree with the destination form and with `maxInstances`, in direct contradiction of the design's 'the width bound has one home'. `patterns/README.md:58` keeps instructing authors to set it above 1 to get parallel fan-out — an instruction that has never produced fan-out from where it is bound.

**Blast radius.** No borrowers. `patterns/README.md` rows 20 and 68-70; `schema-construct-inventory.md` row 41 ('subagent-isolation / isolated parallel workers').
