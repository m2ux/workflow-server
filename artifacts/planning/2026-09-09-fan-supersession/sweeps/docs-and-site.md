## REMOVE — docs/artifact-management-model.md:35 — "Ordering artifacts by name then orders them by the activity that wrote them, and two activities cannot collide over one filename." Also line 31 (the progress-table rhythm) and line 45 (the commit point)

**What it does today.** States the artifact-naming invariant: the server infers a two-digit prefix from the activity's filename, a worker prepends it, so ordering by name orders by activity and no two activities can resolve one filename. This is the doc that establishes artifact collision is structurally impossible.

**Why the fan takes it.** The guarantee is a consequence of one activity owning one prefix. An instance fan runs one activity N times, so N branches share one prefix and one composed artifact contract and can resolve one literal filename concurrently — which is exactly why the design adds the `fan-artifact-collision` check on the safety floor and requires an instance-fanned activity's artifact name to interpolate the fan's parameter as a token. Line 31's "marks a row in progress before it dispatches and complete once the activity's work is committed" describes a per-dispatch rhythm that a fan replaces with one publish before the spawn and one persist at convergence; line 45's "when the orchestrator reaches the point after an activity where its artifacts are committed" is the same beat, and a fanned activity stages nothing in the checkout at all.

**Evidence.** Line 35 states the collision claim verbatim. The design's "Where a fan may not go" section requires that "Two branches of one fan must not resolve one artifact filename, which is the one-artifact-two-producers case met at fan grain: a fan branch declares no artifact and the join writes the document, or, where a branch genuinely must persist one, its artifact name carries the fan's parameter as a token so each instance's file is its own logical artifact" — and the delivery plan's guard table lands `fan-artifact-collision` at stage 4 with two arms, one of them "an instance-fanned activity whose artifact names do not interpolate the fan's parameter". `docs/technique-protocol-specification.md` lines 96-97 already permit a `{token}`-templated artifact name, so the mechanism exists; only this doc's guarantee contradicts it. Neither `docs/artifact-management-model.md` nor its site mirror appears anywhere in the delivery plan.

**Blast radius.** `site/specs/artifact-management.html` is the required site mirror per `docs/documentation-system.md` line 45. The prefix rule itself is computed server-side from the activity filename, so the code does not change — only the stated guarantee and the fan's token requirement. The progress-table and commit sentences are the doc counterpart of the corpus's `commit-and-persist` operation and the drive loop, which stage 6 amends.

**If left alone.** A safety invariant that the fan breaks stays written as a structural fact, in the document a reviewer reads to decide whether artifact collision is possible. The new guard then contradicts the model document it is supposed to mechanise, and an author reading only this page has no reason to token-template a fanned activity's artifact name — which is data loss, not hygiene.

## REMOVE — docs/resource-resolution-model.md:211 — "**A second copy of one activity is visible.** … the server also records `activity_redelivered` … That is either a replaced worker or a resume that arrived under a fresh identity, and it leaves no other trace"

**What it does today.** Documents an instrument. **Evidence.** The paragraph's trigger condition is quoted above and matches an instance fan literally. The same document's lines 149-155 and 178-180 confirm the scoping that makes this so: "Two workers sharing one `session_index` are two contexts" and "several workers can hold that index at once". This file appears nowhere in the delivery plan.

**Blast radius.** The claim is repeated in substance on `site/specs/resource-resolution.html`. The decision is not purely editorial: either the event's definition changes to exclude fan instances (touching the delivery path in `src/tools/resource-tools.ts`, which stage 5 already edits for the per-instance projection) or the doc names the fan as a third and ordinary cause. Whoever tunes dispatch behaviour from history counts reads this paragraph to interpret the tally.

**If left alone.** A diagnostic that means "a worker was replaced" starts firing N-1 times per healthy fan while its documentation still says it has two causes, both bad. That is a false alarm with a written justification, and the first person to investigate one will trust the doc over the run.
