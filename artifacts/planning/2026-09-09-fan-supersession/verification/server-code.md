# Server code the fan replaces — verified

**Refutation pass.** I reproduced all eighteen candidates from the repository — reading each construct in full, measuring its references myself, and testing each against the design README and delivery plan rather than against the finder's summary. Nine survive as REMOVE (six with corrections to blast radius or failure mode), three were downgraded to DEPRECATE, and six are KEEP (four confirmed as the finder had them, two downgraded from removal verdicts). Nothing was withdrawn outright: every candidate names something real, but five named it at the wrong severity.

The five downgrades share one shape: the finder reasoned from what the post-fan code will look like if the change is made carelessly, and then reported that as duplication existing today. `validateActivityTransition` is the clearest case — it is not a "strictly weaker duplicate" of `validateReportedExit` in either direction (it is the only check when `exit` is omitted, which T2 leaves possible on every ordinary transition; and it never warns on the wrong-exit-name case the reported-exit check exists for), and its initial-activity arm is BF-09, a named requirement with three of its own tests. `get_technique`'s position check is presented as one of two implementations when it is today the only one, because `get_activity` has no such check at all. And `get_activity`'s parameterless call is retained by the design itself — `heldActivity`'s sole-entry arm covers every ordinary walk — so what goes is the exclusivity and one sentence in the description, not the calling convention.

Three of the surviving REMOVEs needed their measurements fixed in ways that matter. `schemas/state.schema.json` is not merely generated and documented: it is a required member of `readAllSchemas` (`src/loaders/schema-loader.ts:13,16`) and is served over MCP at `workflow-server://schemas/state`, so the false scalar model is handed to agents on request and removing the file without editing `SCHEMA_IDS` breaks the combined resource for every caller. The `currentActivity` and `currentTechnique` removals both trip `tests/fixtures/inspect-session/inspect_session.py:61`, the Python parity oracle the identity projection is asserted against — a test failure the finder's blast radius does not predict. And `ExitBinding.to`'s failure mode is only `[object Object]` at one of the three sites named; the other two are JSON fields where a widened value serialises structurally, and the delivery plan already covers all four sites the finder thought it had discovered.

Two findings deserve to outlive their verdicts. First, the migration module is a KEEP — the fan takes none of its purpose, it has a live `start_session` caller, and its population is four legacy folders rather than the one claimed — but the plan defect the finder found inside it is real and verified: `migratePlanningFolder` short-circuits at `migration.ts:281-282` whenever a `session.json` exists, so the stage-5 acceptance criterion "a session recorded before this stage migrates and resumes, its single recorded activity converting to a one-entry frontier" cannot be met by the edit the design names. A pre-frontier record is parsed instead by `safeValidateSessionFile`, gets an empty frontier from the default, has its `currentActivity` key stripped, and resumes with no position. Second, `validateActivityTransition` acquires a genuine new false positive under the frontier — an empty list cannot distinguish "nothing has run" from "the run finished", so a stray call on a completed session would newly warn about the initial activity where today it returns null. Both are fixes the plan owes, not removals.

One last note on scope discipline: `src/utils/fan-out.ts` is a nominal collision only, and I pinned its four consumers in `scripts/run-batch-benchmark.ts` so a future sweep can see it is live rather than dead-and-unrelated. `SessionFile.exit` is confirmed KEEP for the design's stated reason, and is stronger than stated — it has no reader in `src/` at all, which makes its behaviour under a fan moot and its dead-field status a separate question from this feature.

A verdict of REMOVE means the fan does this job now and leaving the construct means two paths do one job. DEPRECATE means it keeps a caller for the moment. KEEP means it looked superseded and is not — those are the entries a confident implementer would delete by mistake.
