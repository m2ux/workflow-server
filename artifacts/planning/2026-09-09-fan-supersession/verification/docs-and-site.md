# Documentation that describes the superseded model — verified

**Refutation pass.** Twenty-one candidates re-derived from the repository. Two withdrawn outright, four downgraded to KEEP, one REMOVE downgraded to DEPRECATE, four constructs narrowed by dropping bundled items that survive the fan, and three blast radii widened with live dependencies the finder missed.

The two withdrawals are the sweep's two claims that the fan breaks a live instrument. The `activity_redelivered` finding fails because the design already handles it: `priorDeliveryScope` in `src/utils/dispatch.ts:70-77` filters on `e.activity === activityId`, and design README line 2142 puts the instance-qualified composite into every history event's activity field precisely so that "the redelivery detector fires exactly on a genuine replacement or a duplicated claim" — the clause the finder read as the outcome is the design's counterfactual. The `orchestra-specification.md:5` finding fails on a phrase check: "where each outcome leads" is the exact wording the design's own executive summary uses for the post-fan system, so it is not a stale singular.

Four candidates were downgraded because the construct is load-bearing FOR the fan rather than superseded by it. The per-session checkpoint bound is the premise the fan's gate ban rests on and is quoted as such at design line 523. The `schemas/README.md` enforcement row is correct as written: design line 1100 keeps both destination checks advisory on purpose, so `next_activity` still moves anywhere and the refusals stage 5 adds are fan-scoped additions beside it. The workflow-fidelity transition diagram depicts the sequential handover, which the design commits to keeping byte-identical. And the state-schema cluster keeps a caller the finder measured as absent — `schemas/state.schema.json` is a live MCP resource, hardcoded into `SCHEMA_IDS`, required by `readAllSchemas` (which errors for the whole combined resource if the file is missing), asserted by `tests/schema-loader.test.ts`, and enumerated by the site generator; only the Zod-side `validateState`/`safeValidateState` cluster is genuinely callerless.

Three findings came out stronger. `scripts/generate-site-data.ts` hand-maintains the very claims stage 5 falsifies — "No `activity_id` parameter — the server reads it from session state", the current-activity status return, and the read-its-destination-from-the-graph instruction — and sits in no stage's file list, so `npm run build:site` would faithfully regenerate a false page. `renderSchemasRegion` at line 690 reads the COMMITTED `schemas/*.schema.json` rather than the Zod sources, which proves the finder's claim that a missed `build:schemas` fails nothing while a missed `build:site` fails loudly. And the dead `transitions` vocabulary is not confined to the site: it is in the live wire descriptions at `src/tools/workflow-tools.ts:696` and `src/resources/schema-resources.ts:7-8`.

Two corrections to the sweep's framing of guard coverage. `tests/docs-drift.test.ts` exists, walks `docs/`, `site/` and `scripts/generate-site-data.ts`, and carries four narrow patterns — so the slot for a mechanical check on this class is unfilled rather than absent, and it explicitly exempts `README.md`. Separately, `site/design/session-store.html:139` claims "twenty-three event types" against an enum of 32, which is pre-existing and violates the documentation-system's own no-brittle-counts convention; it is not a fan consequence and should not be carried as one.

The trap held: nothing in the surviving set argues the fan replaces an in-context sequential loop, and the design's own line 387 ("it is not a loop step wearing a graph's clothes") plus its stated negative token arithmetic were checked against every candidate that touched dispatch or batching.

A verdict of REMOVE means the fan does this job now and leaving the construct means two paths do one job. DEPRECATE means it keeps a caller for the moment. KEEP means it looked superseded and is not — those are the entries a confident implementer would delete by mistake.
