# W02 — Answer Continue at the Boundary

## Overview

A worker that finishes an activity is either continued onto the next one or replaced, and the answer is taken today from a field the completion envelope carries. That field is a copy of a reading made when the finished activity was opened, so everything the worker fetched while carrying it is uncounted. The server already answers the same question at the advance, counting those fetches, and already tells the caller to act on it. This task moves the answer to that call: the advance reads the standing, the envelope stops carrying one, and the loop stops gating on a field that is no longer there.

## Problem

- **The envelope answers from before the activity ran.**
  A worker reads `may_continue` off the `batch:` block of its `get_activity` response and hands it to [finalize-activity](https://github.com/m2ux/workflow-server/blob/860e107b/corpus/meta/techniques/workflow-engine/activity-worker.md#L49), which [folds it into the completion envelope and carries it unchanged](https://github.com/m2ux/workflow-server/blob/860e107b/corpus/meta/techniques/workflow-engine/finalize-activity.md#L82). The reading is taken as the activity opens; every technique and resource the activity then fetches draws down the same budget without moving it.
- **The server answers the same question at the advance, and nobody reads it.**
  `next_activity` [reports where the exiting context stands](https://github.com/m2ux/workflow-server/blob/1caa9ff5/src/tools/workflow-tools.ts#L1647-L1660), asked of the activity being advanced onto and against [what the context has actually been delivered](https://github.com/m2ux/workflow-server/blob/1caa9ff5/src/utils/batch.ts#L195-L209) — the finished activity's lazy fetches included. The parameter that turns it on [says what to do with it](https://github.com/m2ux/workflow-server/blob/1caa9ff5/src/tools/workflow-tools.ts#L1240-L1242): continue on true, spawn a fresh identity otherwise.
- **Two answers reach one decision, and they can disagree.**
  The client loop gates [its continuation](https://github.com/m2ux/workflow-server/blob/860e107b/corpus/meta/routines/activity-loop.yaml#L105) and [its release](https://github.com/m2ux/workflow-server/blob/860e107b/corpus/meta/routines/activity-loop.yaml#L316) on the envelope's copy, while a refusal of the advanced activity reaches the same decision as [a continuation that comes back with nothing](https://github.com/m2ux/workflow-server/blob/860e107b/corpus/meta/techniques/workflow-engine/continue-batch.md#L56). A batch therefore ends two ways: cleanly on the stale copy, or as a recovery from an error the fresh reading would have predicted.
- **The stale copy is written down as the rule.**
  [`batch-is-bounded-by-the-server`](https://github.com/m2ux/workflow-server/blob/860e107b/corpus/meta/techniques/workflow-engine/dispatch-activity.md#L133) tells the orchestrator to continue while the envelope reports the field true, and then states that the answer can be wrong by the time it is read.

## Proposal

The question is asked at the activity boundary, so it is answered by the call that crosses it. One answer, read where it is freshest, and no copy travelling in an envelope to be read later.

- **The advance asks for the standing.**
  `continue-batch` declares the window of the context it carries the batch under and passes it with the identity, so the advancing `next_activity` returns the batch reading for the activity it is advancing onto.
- **That reading decides continue or respawn.**
  The held context is continued where the reading admits it, and replaced where it does not — before a refused `get_activity` has to surface the same fact as a worker that returned nothing. The recovery branch stays for a context that dies.
- **The envelope carries no continue field.**
  `finalize-activity` loses the input and the output field; the worker stops passing one. What a worker does with its own `get_activity` reading is unchanged: it finishes the activity it holds and does not ask for another.
- **The loop stops reading a field that is gone.**
  The continuation fires on a held identity and a completed activity; the release fires where the destination is terminal or fans. Neither consults the envelope, because the decision that used to need them is made at the advance.
- **What does not move.**
  The bound, the activity cap, the delivery budget, and the carve-out that always serves an activity a context already holds. A destination that fans still ends the batch. No engine source changes: the reading, the parameter, and the instruction to act on it are already there.
