# W01 — Displacement Named, the Serving Bind Recorded

## Overview

One experiment sidecar serves every session that walks a specimen, and a reload moves its corpus bind for all of them at once. The reload stops the container without reading what that container serves or who is on it, and readiness answers with the bind and no session, so a bind taken while another session walks leaves no trace in either place. This task makes the instance report the corpus it holds and the sessions standing on it, has the reload name that displacement before it stops anything, and puts the serving corpus pin on the response that opens a walk, so a run record cites the instance that answered rather than the reload that preceded it.

## Problem

- **The reload stops the container without saying what it serves.**
  [`capture_log` and the stop](https://github.com/m2ux/workflow-server/blob/c2bfb89e/tests/scripts/reload-exp-sidecar.sh#L605-L606) run straight after the banner for the incoming pairing. Nothing in the run reads the corpus the outgoing container binds, and nothing asks it whether a session is mid-walk.
- **Readiness reports the bind and nobody standing on it.**
  [`GET /ready`](https://github.com/m2ux/workflow-server/blob/c2bfb89e/src/transports/http.ts#L97-L111) answers with its checks and a corpus report of directory, host directory, workflow count and ambiguous ids. The payload carries no session, so a sidecar at rest and a sidecar mid-walk answer alike.
- **Readiness names the tree and not the commit.**
  The corpus report names the host directory behind the mount. Two reloads of one directory at different commits serve different definitions and report the same `/ready`, while the commit the container was labelled with is reachable only through `docker inspect`.
- **The pin a walk cites is read before the walk.**
  The run record is pinned from the [reload banner](https://github.com/m2ux/workflow-server/blob/c2bfb89e/tests/scripts/reload-exp-sidecar.sh#L591) and the container labels, both produced before any tool call. The [response that opens a session](https://github.com/m2ux/workflow-server/blob/c2bfb89e/src/tools/resource-tools.ts#L589-L616) names the workflow, the session index and the planning folder, and says nothing about the corpus it was resolved against, so a rebind between the reload and the walk leaves the record's pin unchanged and the walk reads as a pass.

## Proposal

The instance is the only party that knows which corpus answered a call and which sessions are on it. It reports both, the reload asks it before it displaces anything, and the response that opens a walk carries the pin a record cites.

- **The instance holds the pin of the corpus it serves.**
  `CORPUS_PIN` reaches `ServerConfig.corpusPin` the way `HOST_WORKFLOWS_DIR` reaches `hostWorkflowsDir`, and the reload passes the pin it labels the container with as that variable. Absent, the instance reports no pin rather than a guessed one.
- **Readiness reports the pin and the sessions standing on the bind.**
  `GET /ready` carries `corpus.pin` when the instance holds one, and a `sessions` array naming each session this instance has advanced: its index, its workflow, its planning folder and when it was last seen. A session the instance has finished is not standing and leaves the array.
- **The sessions are registered where sessions are written.**
  The session store is the one module that creates and replaces `session.json`, so a running session registers and a completed one releases on the write that records it. No tool call carries the registration itself.
- **The reload names the displacement before it stops anything.**
  Before the preflight, the compile and the stop, the reload reads the labels of the container it is about to replace and asks that container's readiness endpoint for the sessions on it, and prints the corpus and those sessions. An instance that does not answer is reported as unknown, which is a different line from none.
- **The response that opens a walk carries the serving pin.**
  `start_session` answers with `serving.corpus_pin`, read from the instance that resolved the call. A record pinned from that response names the corpus that served the walk, and a record whose pin disagrees with the container's label is a walk that was displaced.
- **The run is the instrument.**
  A reload run against a stubbed container and readiness endpoint shows the displacement named ahead of the stop. A walk opened on an instance configured with a pin shows that pin on the opening response and on readiness, and a session store write shows the session standing on readiness and leaving it when the session completes.

| Part | Description |
| --- | --- |
| Config | `CORPUS_PIN` to `ServerConfig.corpusPin`, with its row in the configuration reference. |

| Readiness | `corpus.pin` and the `sessions` array on `GET /ready`. |
