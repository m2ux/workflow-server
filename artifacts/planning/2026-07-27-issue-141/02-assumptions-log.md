## Open Assumptions

### DP-5: Section-path delimiter
**Assumption:** The path delimiter inside a section ref is `/`, giving `id#parent/child`.  
**Decision space:** (a) `/` — the issue's proposal; unused inside a section part today and visually distinct from the technique `::`. (b) `::` — floated and rejected in the issue for overloading the technique-ref delimiter and blurring resource-vs-technique refs. (c) `>` or `.` — neither appears in slugs, but `.` collides with the `.md` strip and `>` needs escaping in YAML and markdown. The trade-off that actually differentiates them is not aesthetics but *where the ref may legally appear* — see DP-12.  
**Why not code-resolvable:** The issue states "Decide on adoption". It is a public syntax commitment across a corpus of 400+ refs and every future workflow author, not a fact recoverable from the code.  
**Technical context:** `/` is parse-safe — `parseResourceRef` strips the section at `#` before locating the workflow-prefix slash, so `meta/bootstrap-protocol#a/b` parses correctly (DP-13, verified). No `a/b` section ref exists in the corpus today, so adoption is greenfield. But `/` is invisible to the anchor guard's current `LINK_RE` and unnavigable on GitHub (DP-12), which constrains all three candidates equally and is the fact worth deciding against.  
**Agent's position:** `/` — it is parse-safe, greenfield, reads as a path, and the GitHub-navigability limit in DP-12 applies to every candidate, so it is not a discriminator. Confine path refs to tool calls and `resources: [...]` entries rather than prose links.  
**Reversibility:** path-committing

### DP-6: Slugger unification strategy
**Assumption:** AC 1's "one slugger" is satisfied by extracting a shared internal module that both the guard and the runtime import.  
**Decision space:** (a) Shared internal module — no new dependency, but the project owns GitHub-slug fidelity forever. (b) Guard resolves through the runtime resolver — parity by construction, and the guard gains fence-awareness for free, but the guard's job becomes validating the resolver with the resolver, weakening it as an independent check. (c) Adopt `github-slugger` — exact upstream fidelity, at the cost of a new runtime dependency.  
**Why not code-resolvable:** A dependency-policy judgement. The evidence constrains it but does not settle it.  
**Technical context:** The project deliberately carries five runtime dependencies and no `github-slugger`; the sandbox is offline, so adding one is not free. The guard's existing `slugify` (`scripts/check-resource-anchors.ts:42-48`) is already GitHub-accurate and is the natural extraction source. Option (b) is attractive but note the guard must keep its own `-N` dedupe *counting* pass, which the runtime resolver has no equivalent of.  
**Agent's position:** (a) *plus* the strong half of (b) — extract the shared module seeded from the guard's implementation, and additionally have the guard assert that the runtime resolver returns non-`null` for every link it approves. The rejected-paths perspective showed this hybrid is strictly stronger than either option alone and is what would have caught all five runtime-`null` links; independence is preserved because the guard keeps its own slug and `-N` counting pass.  
**Reversibility:** easily-reversible

### DP-7: Scope of the pre-existing red baseline
**Assumption:** The three pre-existing guard-red anchors and the `wp-plan.md` missing-file link are in scope for this package.  
**Decision space:** (a) Fix all four here — the hard-zero guard test passes on merge, but the package absorbs unrelated corpus edits in a second repo. (b) Fix none and leave the guard red — impossible if AC 6 strengthens the guard, since a stronger guard cannot land red. (c) Fix the three red anchors here and defer the `wp-plan.md` link (it sits inside a template body and is only reachable once AC 6's fence handling improves).  
**Why not code-resolvable:** A scope decision about what this package owns.  
**Technical context:** `tests/resource-anchors.test.ts` asserts hard-zero and fails today with exactly the three links the issue lists. The `wp-plan.md` link is a fourth, currently invisible to the guard, and becomes visible the moment AC 6 lands — so AC 6 cannot merge green without addressing it. All four are corpus edits, therefore submodule work (DP-9).  
**Agent's position:** (c) — the three red anchors are a precondition for any guard work, and the fourth is genuinely caused by this change making the guard see more, so it belongs here too unless the corpus worktree proves costly to set up.  
**Reversibility:** easily-reversible

### DP-10: Whether path support has a consumer in this package
**Assumption:** Hierarchical addressing delivers value within this package.  
**Decision space:** (a) Ship the capability alone, out-of-scope corpus adoption as the issue states — value is deferred to later refactors that may not happen. (b) Ship it and migrate the 7 live duplicate-slug referencers as proof — small, in the same submodule, and turns the feature from latent to exercised. (c) Ship AC 1 only (the defect fix) and defer path-scoping until a consumer needs it. (d) Ship AC 1 plus an ambiguity error (DP-15) and defer paths — addresses all measured harm loudly, adds no syntax.  
**Why not code-resolvable:** A value judgement about deferred capability, and it partly contradicts the issue's own "Out of scope" section.  
**Technical context:** There is a live precedent for build-and-never-adopt: `extractResourceIds` supports `resources: [id#section]` array entries and the corpus contains **zero** of them. Three findings narrowed the evidentiary base for paths during the challenge pass. Every measured duplicate-slug case is already reachable via AC 1's `-N` dedupe (DP-11). The 7 live over-delivering refs — the only live wrong-behaviour case Defect 2 cites — are also fixable by renaming three H2 headings, though DP-14 shows those headings are a deliberate convention, so a rename needs that workflow owner's agreement. And DP-15 found an ambiguity error resolves the same harm with no new syntax at all. Note too that for this particular case the path form is degenerate (`x/x`, parent and child share a slug). The consumer that would most benefit (`load-patterns.md:14`, loading all 326 lines of `injection-pattern-catalog.md`) sits behind the out-of-scope line.  
**Agent's position:** (b) if path-scoping is built at all — the capability is sound and cheap once AC 1's slugger work is done, but it should land with at least one real consumer or it repeats the `resources: [...]` precedent. Given DP-11, DP-14 and DP-15 together, I would put (d) to the user first: it clears every measured harm, and it leaves path-scoping to be justified by a consumer rather than by the cases in the issue, all of which turn out to be reachable without it.  
**Reversibility:** easily-reversible

## Wrap-Up

15 assumptions raised at Design Philosophy: 4 validated, 3 partially validated, 4 invalidated, 2 confirmed by user, 4 open (carried into requirements elicitation). One analyse–challenge–combine pass; challenge perspectives (stakeholder-gap, rejected-paths, evidence-strength) run sequentially — this worker cannot spawn agents, and sequential scatter is the `concurrency = 1` case.

- **DP-3 invalidated** — the delivery-hash invariant is token efficiency, not correctness; the real exposure is a single-segment ref resolving to a different section. Constraint corrected in the philosophy doc.
- **DP-12 invalidated** — path refs cannot be written in prose markdown links: the guard's anchor pattern excludes `/` and GitHub renders no such anchor. Constrains the delimiter decision and AC 6's implementation.
- **DP-14 invalidated** (stakeholder-gap) — the duplicate title heading is a deliberate convention in all three `prism-evaluate` templates, not an accident, so heading renames need that workflow owner's agreement.
- **DP-15 invalidated** (rejected-paths) — erroring on an ambiguous flat slug addresses all 7 measured over-deliveries with no new syntax; an option neither the issue nor this log had considered.
- **DP-11 partially validated** — AC 1's GitHub `-N` dedupe alone reaches every duplicate-slug case measured in the corpus. Its untested half, flagged by evidence-strength: the claim that paths buy *stability* over positional `-N` anchors is argued, not measured — no test of what an inserted heading does to existing `-N` refs. Elicitation or research should settle it, since it is the whole remaining case for Defect 2.
- **DP-9 partially validated** — the submodule worktree mechanism is house-standard but not yet prepared; a setup step is owed before any corpus criterion can be met.
- **Evidence-strength notes:** all corpus figures come from purpose-built probes rather than project tooling, though the probe's link count matched the guard's own extraction exactly (403 both ways), and each of the 5 runtime-`null` links is individually named and reproducible. Severity rests on 2 hard failures in core workflow READMEs plus 7 over-deliveries confined to one workflow — real, but narrow in breadth rather than broad.
- **Takeaway:** the issue's two defects are unequally evidenced. Defect 1 is measured, live, and cheap. Defect 2 is well-designed, but by the end of the challenge pass every case the issue cites for it turned out reachable three other ways — AC 1's dedupe, a three-heading rename, or an ambiguity error — while the one consumer that genuinely wants hierarchy sits behind the issue's own out-of-scope line. The pattern to watch is inheriting a proposal's framing when its own fix-first advice already covers the evidence.
