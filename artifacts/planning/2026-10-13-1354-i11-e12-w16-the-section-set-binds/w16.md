# W16 — The Sections a File Carrying a Procedure Takes

## Overview

This task makes the shared skill-file check select the files its section rule binds by what they carry rather than by what they are called. A file carrying a procedure takes the top-level set the shared guidelines name, in the order they name them, and names its procedure Procedure. A file carrying no procedure keeps its own shape. The guidelines state that test once, so the next author of a reference file holding steps places a heading by reading the rule rather than copying a sibling.

## Problem

- **A procedure is not confined to a mode file.**
  The check reads a procedure as a top-level section carrying a numbered step, whatever its heading names it, so a reference file holding steps is a caller of the commands those steps run and receives their specifications under the placement rule.
- **The section rule reaches only a file name.**
  The named set and its order are applied where the file name ends in `-mode.md`. `references/audit-dispatch.md` carries a procedure, carries the three specifications its steps run, and is measured by none of it.
- **The placement of its Commands section was a judgment.**
  Nothing stated where a Commands section goes in a file whose other sections are not the named set, so the choice was argued in a planning record rather than read from a rule.

## Proposal

The check already computes, for every file, which of its top-level sections carry numbered steps — that is the test the epic settled for the caller rule. The section rule reads the same measurement, so one definition of a procedure selects both.

### The options weighed

- **Select the set by the procedure spans the check already measures.** Taken.
  One definition of a procedure serves the caller rule and the section rule, so a file cannot run commands as a procedure and escape the section set as prose. No new vocabulary, no second test to keep in step.
- **Name the procedure-carrying files in the check.**
  A list is a precedent in another spelling. It answers which files are bound today and nothing about the next one, which is the friction the task names.
- **Rename the procedure-carrying reference files to `-mode.md`.**
  It would bind them, and would also say a reference file is a mode of its skill. `audit-dispatch.md` is reached from Audit mode's steps, not selected from SKILL.md, so the name would be false.
- **Bind only the section's order, leaving the names free.**
  Order over a free vocabulary measures nothing a reader can predict. The point of the set is that the reader knows what the file holds before opening it.

### What the widened rule reports

Run over `skills/gitnexus`, `skills/server-in-the-loop`, `skills/work-planner` and `skills/workflow-canon`, the check reports 34 findings against the 6 the name-selected rule reported. Four reference files are selected that no section rule had measured before, and the rule's first widening, before the entry point was excluded and Rules left to modes, reported 58.

- **Four reference files carry a procedure and take the set.**
  `workflow-canon/references/audit-dispatch.md`, `workflow-canon/references/change-surface.md`, `work-planner/references/review-passes.md` and `work-planner/references/work-breakdown.md`. Each is restructured on this branch: every heading keeps its text, so every anchor cited across the skills resolves unchanged, and the top-level headings become the named set with the file's other sections as sub-sections of Reference.
- **The procedure gets its name.**
  The dispatch route, the capture steps, the three review passes and the task merge sit under a `## Procedure` in their files. A reader who opens any of the four now meets the same names in the same order.
- **Five operations reach the mode that runs them.**
  The Work Breakdown Guide's delivery prose sat inside the span the task merge's steps made a procedure, so every command that prose named counted as run. With the steps named as the guide's own procedure, that prose runs nothing and the placement rule reports five catalog specifications with one caller each: Update Review Pull Request, Link Pull Request to Issue and Plan Board Changes move to Sync mode, Find Available Work to Deliver mode, Summarise Progress to Standup mode.
- **The run ends where it started.**
  The check reports the same 6 findings it reported before this change, all of them in `gitnexus/gitnexus-cli/SKILL.md`, and no section finding anywhere.

### Where the set did not fit

- **A skill's entry point takes the structure the guidelines already give it.**
  `gitnexus-cli/SKILL.md`, `gitnexus-guide/SKILL.md` and `server-in-the-loop/SKILL.md` carry numbered steps, and the first widening reported 21 section findings against them. SKILL.md has a named structure of its own in the shared guidelines — Opening, Modes, Rules, Dependencies, Commands — and requiring Procedure and Reference of it would set the two statements against each other. The entry point is excluded by name, as it already is from the command-specification rule.
- **Rules stays a mode's obligation, not every procedure file's.**
  A mode states what binds it whatever step it is on, so a mode file carries Rules. A reference file carrying a procedure may have nothing that binds beyond its steps, and `review-passes.md` and `change-surface.md` are two such files: requiring the heading there would have each grow a section whose content had to be invented. The set and its order bind every file carrying a procedure; Procedure is required of each; Rules is required of a mode file.
- **`gitnexus-cli/SKILL.md` carries six findings this row does not fix.**
  Five command specifications in the entry point and one over-wide bold lead, all of them reported before this change and none of them a section finding. The gitnexus skills are not written to the shared guidelines, which is a condition this row records rather than resolves.
