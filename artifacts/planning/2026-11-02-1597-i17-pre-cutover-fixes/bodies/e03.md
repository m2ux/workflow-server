## Overview

A board can be delivered by more than one session at once, each serving its own lane of rows. Work Planner has no way to say which lane a row belongs to: Deliver mode selects the next unit by priority and dependencies alone, so two sessions select the same row. A work item declares a lane id, Plan mode assigns it, and a Deliver run that names a lane takes no other lane's rows. The epic lands before the skill's extraction, so the skill moves with lanes.

## Problem

- **No row says which lane delivers it.**
  A [work item](https://github.com/m2ux/workflow-server/blob/b2844c821ce800ed3d12735bdf339049594e5ec5/skills/work-planner/artifacts/work-item.md#component) declares only its Component ahead of its first heading.
- **Every session sees one queue.**
  [Task Eligibility](https://github.com/m2ux/workflow-server/blob/b2844c821ce800ed3d12735bdf339049594e5ec5/skills/work-planner/artifacts/board-queue.md#task-eligibility) makes a task Ready on its epic's status and its Depends on cell, and Deliver mode takes the highest-priority Ready unit, so two sessions running Deliver mode on one board select the same unit.
- **A label cannot carry it.**
  A label marks an issue; most rows are table rows with no task issue, and one epic's rows can sit in different lanes.
- **Observed in prosiform delivery (I10, 2026-11-03).**
  Two sessions are to deliver I10 side by side. Its work items now carry a `**Lane:** <n>` line under their Component, and the queue ignores it.

## Proposal

These are the user's decisions (interview, 2026-11-03).

- **A work item may declare a lane.**
  [Work Item](https://github.com/m2ux/workflow-server/blob/b2844c821ce800ed3d12735bdf339049594e5ec5/skills/work-planner/artifacts/work-item.md#fields) gains an optional `**Lane:** <id>` declaration line beside Component. The id is an opaque index: it says the rows differ in who delivers them, never why.
- **A lane is board-wide.**
  Lane 2 is one lane across the theme board, so a session serving it takes lane-2 rows from any initiative.
- **The run names its lane.**
  A Deliver run names the lane it serves in its request ("deliver next, lane 2"); nothing is stored per session. A run naming no lane takes only unlaned rows.
- **An unlaned row is open to every run.**
  A laned run takes its own lane's rows and unlaned rows, never another lane's, and picks among them by priority alone, as today.
- **Plan mode assigns lanes.**
  When Plan mode writes work items, it asks whether the initiative uses lanes and proposes each row's lane for the user to confirm.
- **Joined rows share a lane.**
  Plan and Align modes report joined rows that declare different lanes as a finding to settle, by moving a lane or unjoining; the dependency check refuses such a unit, so Deliver mode never meets one. Both modes already run that check, so the rule has one home, in the dependency graph.
- **The queue reports lanes.**
  Advance and the board queue report each Ready unit's lane id.

## Acceptance Criteria

- [ ] **AC1.** The Work Item artifact states the optional `**Lane:** <id>` declaration beside Component, that the id is an opaque board-wide index and that a work item states no reason for it, and Populate Work Item writes a supplied lane, as a read of the artifact shows.
- [ ] **AC2.** The Delivery Plan artifact states that a run naming a lane is offered the units whose rows declare that lane or no lane, by priority alone, that a run naming none is offered only unlaned units, and that each unit line names its lane, as a read of the artifact shows.
- [ ] **AC3.** The Dependency Graph artifact states that joined rows share one lane, that a joined unit across lanes is settled by moving a lane or unjoining, and that Check Dependencies refuses such a unit, as a read of the artifact shows.
- [ ] **AC4.** The dependency check reads each work item's lane and refuses a joined unit whose rows declare different lanes, naming each row and its lane, as `test_deps.py` fixtures show.
- [ ] **AC5.** The available-work survey run for a lane offers only units whose rows declare that lane or none, a run naming no lane offers only unlaned units, and each unit line names its lane, as a `test_deliver.py` fixture with rows in two lanes and rows in none shows.
- [ ] **AC6.** Deliver mode passes the lane its request names to every Plan Available Work call, passes none when the request names none, and stores no lane per session, as a read of the mode shows.
- [ ] **AC7.** Plan mode asks whether an initiative uses lanes, proposes each row's lane for the user to confirm and passes each confirmed lane to Populate Work Item, as a read of the mode shows.
- [ ] **AC8.** The Board Queue artifact states that the queue reads each Ready row's work item in the engineering worktree and reports each Ready unit's lane id, as a read of the artifact shows.
- [ ] **AC9.** The board-queue script prints each Ready unit's lane id, and its placement calls are the same with lanes as without, as a `test_board_queue.py` fixture with laned rows shows.
- [ ] **AC10.** Advance mode passes the engineering worktree to every Plan Board Queue call and reports each Ready unit's lane, as a read of the mode shows.
