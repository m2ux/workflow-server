# W09 — Caller Test: One Rule for Every Citing File

## Overview

The shared skill-file check decides where a command specification belongs by counting the files that cite it. The shared guidelines say a caller is a procedure that runs the command, and the check applies that reading to the file holding the specification alone: every other citing file enters the count whatever its citation is doing, and the holding file enters it only from an h2 literally titled `Procedure`. One call test, asked of every file alike and recognising a procedure by its numbered steps, answers both halves at once.

## Problem

- **The exclusion is one-sided.**
  [`check_skill_files.py`](https://github.com/m2ux/workflow-server/blob/b2fb799b/skills/scripts/check_skill_files.py#L202-L208) drops the holding file from the caller set unless a Procedure of it cites the specification, and takes every other citing file from [`cited()`](https://github.com/m2ux/workflow-server/blob/b2fb799b/skills/scripts/check_skill_files.py#L105-L116), which reads every fragment link wherever it sits. A sibling specification's cross-reference therefore counts for nothing in the holding file and counts as a caller in any other.
- **The guidelines draw no such distinction.**
  The [placement rule](https://github.com/m2ux/workflow-server/blob/b2fb799b/skills/guidelines.md#L106) states that a caller is a procedure that runs the command, and that a sibling specification or a passage of reference prose naming it does not make its file a caller. It says nothing about which file holds the specification.
- **A heading is neither necessary nor sufficient for a procedure.**
  [`procedure_spans()`](https://github.com/m2ux/workflow-server/blob/b2fb799b/skills/scripts/check_skill_files.py#L135-L149) recognises only an h2 titled `Procedure`. Work Planner runs its delivery procedure under `Delivery` and its ordering procedure under `Ordering Pass`, so neither is seen; its own [`references/guidelines.md`](https://github.com/m2ux/workflow-server/blob/b2fb799b/skills/work-planner/references/guidelines.md#L24) carries a `## Procedure` that is a bullet of prose about procedures and runs nothing, so the title is read where there is no procedure.
- **Three specifications standing where they belong are reported as misplaced.**
  `Merge Pull Request`, `Capture Issue Development` and `Renumber Epics` sit with the procedures that run them. Each is named by a sibling specification left in the catalog, and the check reports that catalog as the one caller, naming a destination that would undo the placement.
- **A file barred from holding a specification can absorb one unseen.**
  The guidelines state that [SKILL.md holds no command of its own](https://github.com/m2ux/workflow-server/blob/b2fb799b/skills/guidelines.md#L44). Nothing measures that, so a specification moved into a skill's entry point draws no finding at all.

## Proposal

- **One call test, asked of every file.**
  A file counts among a specification's callers only where a procedure of that file carries the citation, whether or not it holds the specification. The citation index records the section each citation sits in, and the holding file stops being a special case.
- **A procedure is a section of numbered steps.**
  For the purpose of this rule, a procedure is a top-level section of a file that carries a numbered step — an ordered-list item outside any fence — counting the sub-sections beneath it to the next heading of its level or above. `Delivery` and `Ordering Pass` are procedures; a `Procedure` heading over a bullet of prose is not. The guidelines already describe a mode's Procedure as numbered steps, so the test reads what the guidelines say a procedure looks like rather than what an author titled it.
- **A citation inside a command specification is never a call.**
  A specification names a sibling to tell the reader where the companion operation is stated; it does not run it. Those lines are excluded before a section is read for its numbered steps, so a catalog whose entries carry numbered steps is still not a procedure.
- **A specification no procedure runs stands where it is.**
  Zero callers stays silent. The report names only a specification exactly one procedure elsewhere runs, which is the only case that has a destination.
- **A skill's entry point is reported for any specification it holds.**
  The check reports a command specification standing in a `SKILL.md`, whatever cites it, so the guideline that the entry point carries no command is measured rather than remembered. That is the guard the caller test cannot give: a specification there would otherwise be invisible, since the entry point's prose is not a procedure.
- **`List Initiative Titles` stands in the catalog, and the check falls silent on it.**
  Its one citation is from `SKILL.md`'s Themes and Boards, a passage of reference prose. The semantics make that no call, so the specification has no caller and nowhere to be moved to, which is exactly the case the rule leaves alone. The blind spot the silence would otherwise open — a specification hidden in an entry point — is closed by the entry-point report instead, not by counting that prose as a call.

## Work Breakdown

| Part | Description |
| --- | --- |
| Citation index | The index records, per cited anchor, the files that cite it and the files whose procedures run it, so the caller count reads calls alone while the duplicate-anchor rule keeps reading every citation |
| Procedure recognition | A procedure is a top-level section carrying a numbered step outside a fence and outside any command specification, counted to the next heading of its level or above |
| Caller rule | A specification exactly one procedure cites, in a file other than its own, is reported against that file; the holding file is read by the same test as every other |
