## Overview

The delivery plan states which units a lane is offered, so a Deliver run serving one lane never takes another lane's rows. This is the rule the available-work survey implements and Deliver mode passes its lane to.

## Problem

- **Every run sees one set of units.**
  [Work Units](https://github.com/m2ux/workflow-server/blob/b2844c821ce800ed3d12735bdf339049594e5ec5/skills/work-planner/artifacts/delivery-plan.md#work-units) offers every available unit of a Ready or In Progress epic to every run, so two sessions delivering one board are offered, and confirm, the same unit.

## Proposal

Two sessions deliver one board, one asked for lane 1 and one for lane 2.

- **A lane admits its own rows and unlaned rows.**
  A run naming a lane is offered the units whose Lane cells contain that index or are empty, never another lane's. A run naming no lane is offered only unlaned units.
- **Priority alone orders what a lane is offered.**
  The lane filters the units; it does not rank them.
- **A unit’s lane comes from its task rows.**
  The Lane cells in the epic Work Breakdown table supply the lane. A row can be laned when it links no work item. A hot-fix unit is unlaned.
- **The unit line names its lane.**
  Report Lines adds the lane id to each `unit` line, or names it unlaned.
- **Compute Available Work takes the lane.**
  A `--lane <id>` input names the lane the run serves; without it the run serves unlaned units only.
