## Overview

The guard sweep grades the corpus, and it runs only against a proposed merge. The commit a merge produces is never swept, so the branch the corpus lives on carries no verdict of its own and the question "is the corpus green?" is answered by whatever was dispatched by hand last. This task gives `verify-corpus.yml` a push trigger for the corpus branches, so each tip a merge produces is swept by the push that produced it.

## Problem

- **The sweep has no trigger for the branch it grades.**
  `verify-corpus.yml` declares `pull_request` and `workflow_dispatch`. A merge into a corpus branch reaches neither.
- **The branch's latest run is a hand dispatch.**
  Measured 2026-10-13: every run of `Verify corpus` on `workflows` outside a pull request is a `workflow_dispatch` — run 38379321639 at `22434a13` today, and run 35365680975 on 2026-09-18 against a tip 23 commits behind. A hand dispatch states what someone chose to measure, not what the branch received.
- **A merge can redden the branch with nothing to show it.**
  A pull request is swept against its own head. Two pull requests that each sweep clean can merge into a tip that does not, and no run states that.
- **Engine continuous integration already has the trigger the sweep lacks.**
  `verify.yml` pushes to `main` and to the integration and epic bases, because a branch that takes a merge directly reaches no pull request of its own. The corpus branches take merges the same way.

## Proposal

The sweep is triggered by what reaches the branch it grades, so its latest run reads that branch's tip.

- **A push trigger covers the corpus branches.**
  `verify-corpus.yml` declares `push` with `branches: [workflows, 'i[0-9]+/workflows', 'i[0-9]+/e[0-9]+/workflows']`, the three depths a corpus branch takes a merge at. A glob does not cross a slash, so each depth is its own pattern. A task branch matches none of them, and its work is swept by the pull request it opens.
- **The job needs nothing further.**
  The engine-pairing step reads `github.base_ref || github.ref_name`, which on a push is the branch pushed to; the corpus checkout reads `github.event.pull_request.head.sha || github.sha`, which on a push is the commit pushed. Both already describe the push case.
- **The file's prose states the push.**
  The header and the corpus-checkout comment name the three events the job serves, so a reader of the file learns what triggers it from the file.
